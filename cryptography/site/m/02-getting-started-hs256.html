Module 02 · Getting Started with HS256

🧠 Mental Model — Behind the Scenes

HS256 is the shared-secret workhorse, and the key word is symmetric: the same secret both signs and verifies. There is no public half, no private half — just one key that does both jobs. That symmetry is HS256's superpower (dead simple, blazing fast) and its sharpest edge (anyone who can verify can also forge). The entire security of the scheme collapses to one question: is the secret unguessable, and is it kept on the server only?

Under the hood, encode() and decode() are mirror images of one HMAC computation. encode() builds the header.payload string and computes HMAC_SHA256(secret, "header.payload"), attaching the result as the signature. decode() does not "decrypt" anything — it re-runs the exact same HMAC over the received header.payload and compares its result to the signature that came in, byte-for-byte (using a constant-time comparison to resist timing attacks). Match → claims returned. Mismatch → InvalidSignatureError. Verification is just re-signing and comparing.

Two PyJWT 2.x details trip people up. First, encode() returns a str, not bytes — so the old token.decode('utf-8') line from 1.x tutorials crashes. Second, decode() requires algorithms=[...]. This isn't bureaucratic; it's a security boundary. If PyJWT trusted the token's own alg header, an attacker could set alg: none or swap algorithms to bypass verification. The allow-list says "I will only accept these algorithms" before looking at the token.

Secrets are bytes to HMAC. A str secret is UTF-8 encoded internally, so "abc" and b"abc" are the same key. But a real secret should be high-entropy random bytes (≥ 32 for HS256, matching SHA-256's output). PyJWT 2.13 actively nudges you: a key shorter than the hash size triggers an InsecureKeyLengthWarning, because short keys are brute-forceable offline.

🔍 A concrete analogy

HS256 is a shared house key cut from a secret pattern. Everyone trusted gets an identical copy. To check a guest's key you don't inspect it — you try it in the lock (re-compute the HMAC) and see if it turns. Because the key both opens and could be copied to make new keys, you'd never hand it to a stranger at the door. Keep it inside the house.

⚙️ What actually happens when you run the code

  1. jwt.encode({"user": "alice"}, secret, algorithm="HS256") serializes claims, builds header.payload, and computes the HMAC-SHA256 using the UTF-8 bytes of the secret.
  2. The digest is base64url-encoded and appended; a single str token is returned.
  3. jwt.decode(token, secret, algorithms=["HS256"]) re-splits the token and recomputes the HMAC over the received header.payload.
  4. PyJWT compares the freshly computed signature to the token's signature in constant time.
  5. On a match it returns the claims dict; on any mismatch (wrong secret, tampering) it raises InvalidSignatureError.
  6. Omitting algorithms= raises DecodeError — the call refuses to guess which algorithm to trust.

👀 What to notice when you run the examples

  • 03_str_vs_bytes.py shows encode() returns a str, and that a str and bytes secret with the same characters verify each other — UTF-8 makes them identical keys.
  • 04_wrong_secret_fails.py produces InvalidSignatureError even though the token is perfectly well-formed — the signature simply doesn't match.
  • 05_must_specify_algorithms.py fails loudly without algorithms=, making the security requirement impossible to forget.
  • 07_secret_strength.py generates 32-byte secrets via secrets.token_urlsafe/token_hex/os.urandom; weak words would invite offline brute force.
  • 08_full_login_simulation.py ties it together: issue on "login", verify on each "request" — the real-world loop.

⚠️ Common misconceptions

  • ❌ "decode() decrypts the token." False — it re-computes the HMAC and compares. Nothing is decrypted.
  • ❌ "encode() returns bytes, so I should call .decode('utf-8')." False in PyJWT 2.x — it already returns str.
  • ❌ "algorithms= is optional boilerplate." False — it's mandatory and your defense against alg=none and algorithm-confusion attacks.
  • ❌ "Any string works as a secret." False — short/guessable keys are forgeable; PyJWT 2.13 even warns with InsecureKeyLengthWarning for keys under the hash size.

🚀 Module 02 · Getting Started with HS256

You understand what a JWT is (Module 01). Now let's actually use one. This module is your hands-on introduction to issuing and verifying tokens with HS256 — the shared-secret workhorse of JWT signing.

🎯 What you'll learn

HS256 = HMAC with SHA-256. It's a symmetric algorithm: the same secret both signs and verifies a token. It's simple, fast, and perfect when one party (or a set of trusted services sharing a secret) issues and checks tokens.

You'll learn the two core calls and the habits that keep them safe:

token  = jwt.encode({"user": "alice"}, secret, algorithm="HS256")   # issue
claims = jwt.decode(token, secret, algorithms=["HS256"])            # verify

…plus str vs bytes, why algorithms= is mandatory, what value types a payload accepts, how to generate a strong secret, and a tiny end-to-end login.

🔑 Key takeaways

  1. Two calls do everything. encode() issues, decode() verifies + reads.
  2. encode() returns str in PyJWT 2.x (it was bytes in 1.x — beware old tutorials that call .decode('utf-8') on the result).
  3. Secrets can be str or bytes — a str is UTF-8 encoded internally, so "abc" and b"abc" are the same key. Be consistent.
  4. Always pin algorithms=[...] on decode. It's required and it's your defense against alg=none and algorithm-confusion attacks.
  5. Secret strength is everything. HS256 is only as strong as its key — use ≥ 32 random bytes from secrets/os.urandom.

⚠️ Common pitfalls

  • ❌ Copy-pasting token.decode('utf-8') from a PyJWT 1.x guide → crashes, because encode() already returns str.
  • ❌ Weak/guessable secrets ("secret", "password123") → tokens forgeable via offline brute force. The HMAC math can't save a bad key.
  • ❌ Deriving algorithms= from the token's own header → reintroduces the exact attack the allow-list exists to prevent.
  • ❌ Putting the verify secret on the client. With HS256 the secret both signs and verifies — anyone who has it can forge tokens. Keep it server-side only. (Need clients to verify without forging? That's asymmetric signing — RSA/ECDSA/EdDSA, coming in later modules.)

02 First Decode02_first_decode.py ▾

Decoding verifies the signature AND returns the claims. You must supply:

jwt.decode(token, key, algorithms=["HS256"])

  • token — the compact JWT string.
  • key — the SAME shared secret used to sign it.
  • algorithms — a list of algorithms you are willing to accept. REQUIRED.

If the signature checks out, you get the original claims dict back. If anything is wrong (bad secret, tampered token, disallowed algorithm), decode() raises.

04 Wrong Secret Fails04_wrong_secret_fails.py ▾

HS256 is symmetric: the SAME secret both signs and verifies. If you try to verify a token with the wrong secret, the recomputed HMAC won't match the signature in the token, and PyJWT raises InvalidSignatureError.

This is the property that makes JWTs trustworthy: only a holder of the secret can produce a token that verifies.

05 Must Specify Algorithms05_must_specify_algorithms.py ▾

When verifying, PyJWT requires you to pass algorithms=[...] — the explicit allow-list of algorithms you accept. This is a SECURITY feature, not a nuisance.

Why pin algorithms? * The 'alg' value lives in the token HEADER, which is attacker-controlled. * If a verifier blindly trusted the header's 'alg', an attacker could switch it (e.g. to 'none', or perform an RSA->HMAC "algorithm confusion" attack). * By passing your OWN allow-list, you decide what's acceptable — the token can't talk you into using a weaker/none algorithm.

This script shows that omitting algorithms= raises, and that an algorithm NOT in your allow-list is rejected.

06 Payload Types06_payload_types.py ▾

A JWT payload is JSON, so claim VALUES must be JSON-serializable. PyJWT happily accepts the standard JSON types:

  • list (array) and dict (object), nested as deep as you like

"""
06 · Payload value types
========================

A JWT payload is JSON, so claim VALUES must be JSON-serializable. PyJWT happily
accepts the standard JSON types:

  * str, int, float, bool, None
  * list (array) and dict (object), nested as deep as you like

Additionally, for the *date-related registered claims* (exp, nbf, iat), PyJWT
lets you pass a Python `datetime` and converts it to a NumericDate (a Unix
timestamp integer) for you. This script demonstrates both behaviours.
"""

import datetime

import jwt

SECRET = "teaching-secret-at-least-32-bytes-long!!"

print("=" * 60)
print("STANDARD JSON VALUE TYPES IN A PAYLOAD")
print("=" * 60)
payload = {
    "a_string": "hello",
    "an_int": 42,
    "a_float": 3.14,
    "a_bool": True,
    "a_none": None,
    "a_list": [1, 2, "three"],
    "a_dict": {"nested": {"deeply": True}},
}
token = jwt.encode(payload, SECRET, algorithm="HS256")
decoded = jwt.decode(token, SECRET, algorithms=["HS256"])
for key, value in decoded.items():
    print(f"  {key:10} -> {value!r:30} ({type(value).__name__})")

print("JSON has no tuple type).")

print("datetime IS CONVERTED FOR DATE CLAIMS (exp, nbf, iat)")

exp = now + datetime.timedelta(hours=1)

    "user": "alice",

print("which is the JWT spec's 'NumericDate' format. On decode you get the int")
print("back; PyJWT uses it internally to enforce expiry (covered in module 03).")

07 Secret Strength07_secret_strength.py ▾

HS256 security rests ENTIRELY on the secret being unguessable. A weak secret (like "password" or "secret") can be brute-forced or dictionary-attacked offline, letting anyone forge valid tokens.

Guidelines: * Use a HIGH-ENTROPY random secret, not a memorable word. * For HS256 (HMAC-SHA256) aim for at least 256 bits (32 bytes) of entropy — matching the hash output size. * Generate it with a CRYPTOGRAPHICALLY SECURE source: - secrets.token_urlsafe(n) -> URL-safe text, ~1.3n chars for n bytes - secrets.token_hex(n) -> hex text, 2n chars for n bytes - os.urandom(n) -> raw random bytes * NEVER use random.random()/random.choice() — those are NOT secure.

This script generates strong secrets and uses one to sign a token.

"""
08 · A tiny login simulation
============================

Time to tie module 02 together with a realistic mini-flow:

  LOGIN:   user authenticates -> server issues a signed JWT ("access token").
  REQUEST: user later presents the token -> server verifies it and greets them.

No web framework, no network — just the JWT mechanics you've learned, wrapped
in functions that mimic a login endpoint and a protected endpoint.
"""

import datetime

import jwt
from jwt.exceptions import InvalidTokenError

# The server's signing secret. In production: load from env/secret manager.
SERVER_SECRET = "server-only-hmac-secret-keep-safe"
ALGORITHM = "HS256"

# A pretend user database (username -> password). Never store plaintext
# passwords in real life — hash them. This is illustrative only.
USERS = {"alice": "wonderland", "bob": "builder"}


def login(username: str, password: str) -> str:
    """Authenticate a user and return a signed access token."""
    if USERS.get(username) != password:
        raise ValueError("invalid username or password")
    now = datetime.datetime.now(tz=datetime.UTC)
    payload = {
        "sub": username,                       # subject: who the token is about
        "iat": now,                            # issued-at
        "exp": now + datetime.timedelta(minutes=15),  # short-lived token
    }
    return jwt.encode(payload, SERVER_SECRET, algorithm=ALGORITHM)


def protected_greeting(token: str) -> str:
    """Verify a presented token and return a personalized greeting."""
    # Verifies signature AND expiry; pins the algorithm.
    claims = jwt.decode(token, SERVER_SECRET, algorithms=[ALGORITHM])
    return f"Hello, {claims['sub']}! Your token is valid. 👋"


print("=" * 60)
print("STEP 1 — alice logs in")
print("=" * 60)
access_token = login("alice", "wonderland")
print(f"Issued access token:\n{access_token}\n")

print("=" * 60)
print("STEP 2 — alice calls a protected endpoint with her token")
print("=" * 60)
print(protected_greeting(access_token))
print()

print("=" * 60)
print("STEP 3 — a bad login is rejected")
print("=" * 60)
try:
    login("alice", "wrong-password")
except ValueError as exc:
    print(f"Login refused: {exc}")
print()

print("=" * 60)
print("STEP 4 — a tampered/garbage token is rejected at the endpoint")
print("=" * 60)
try:
    protected_greeting(access_token + "tampered")
except InvalidTokenError as exc:
    print(f"Endpoint refused token: {type(exc).__name__}: {exc}")
print()

print("That's the essence of token-based auth: issue on login, verify on every")
print("request. Modules ahead add claim validation, asymmetric keys, and more.")
