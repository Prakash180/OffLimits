Module 14 · Security Best Practices

🧠 Mental Model — Behind the Scenes

A JWT is a bearer credential: the verifier treats whoever presents a valid token as the subject, no questions asked. That makes the verifier's configuration the entire security boundary — and almost every JWT disaster reduces to one root cause: the verifier trusted something the attacker controls. The token header, the alg field, the claims, the absence of an expiry — all of these are attacker-influenced inputs until a correct signature check proves otherwise.

The most famous footgun is alg: none. The JOSE spec defines an "unsecured" token type with an empty signature. A naive verifier that reads the algorithm from the token's own header will happily accept a token whose signature was simply deleted — letting an attacker forge any payload. The defense is to never let the token choose its own algorithm: always pass an explicit algorithms=[...] allowlist to jwt.decode. PyJWT refuses none unless you dangerously opt in, but you should pin regardless.

The subtlest attack is RS256→HS256 algorithm confusion. An RS256 server verifies with a public key that is, by design, known to everyone. HS256 is symmetric — the same key signs and verifies. So an attacker takes the public key, uses its PEM bytes as an HMAC secret, forges an HS256 token, and a server misconfigured to allow algorithms=["HS256","RS256"] "verifies" it using that public key as the HMAC secret. Forgery complete, no private key required. Module 14 demonstrates all three outcomes for real: a deliberately vulnerable hand-rolled verifier accepts the forgery; PyJWT 2.13 blocks it at the API by refusing to use an asymmetric PEM as an HMAC secret (InvalidKeyError); and the fix you own — pinning algorithms=["RS256"] — rejects it outright. Don't lean on the library's guard alone; pin explicitly.

The remaining rules follow the same logic. Decoding without verification is plumbing, not trust — verify_signature=False is only for reading a kid to choose a key, never for reading claims you'll act on. exp is mandatory — a token with no expiry is valid forever, so use options={"require": ["exp"]} and short TTLs. Secrets must be strong — generate them with secrets.token_urlsafe, store them in env/secret managers, and rotate. And critically: the payload is readable by anyone. Signing is not encryption; base64url is reversible with no key, so never place passwords, PII, or secrets in claims.

🔍 A concrete analogy

A JWT is a backstage wristband: security only checks the band, never your face. alg: none is a band with the hologram peeled off that a lazy guard still waves through. Algorithm confusion is photocopying the public hologram pattern (the public key) and gluing it onto a fake band that a confused guard "validates" against that same pattern. And the payload being readable is the band's printed text — anyone standing near you can read your name and section, so you'd never write your PIN on it.

⚙️ What actually happens when you run the code

  1. An attacker takes a legitimate token, swaps the header to {"alg":"none"}, edits the payload, and drops the signature segment.
  2. A verifier that trusts the token's own alg accepts it — the forgery succeeds against the naive path.
  3. For algorithm confusion: the server's RSA public key is exported as PEM and handed to the attacker (it's meant to be public).
  4. The attacker computes HMAC-SHA256("header.payload", public_pem_bytes) and base64url-encodes it — a valid HS256 signature for that secret.
  5. The deliberately vulnerable verifier recomputes the same HMAC with the public PEM and the signatures match → forged token accepted.
  6. jwt.decode(forged, public_pem, algorithms=["HS256","RS256"]) is rejected by modern PyJWT with InvalidKeyError (asymmetric PEM can't be an HMAC secret).
  7. Pinning algorithms=["RS256"] rejects the forged HS256 token while genuine RS256 tokens still verify.

👀 What to notice when you run the examples

  • 01_alg_none_attack.py: PyJWT refuses none unless you explicitly opt in — the safe default in action.
  • 03_algorithm_confusion_rsa_hmac.py: the three labeled results — forgery accepted (vulnerable), InvalidKeyError (PyJWT guard), rejected (your RS256 pin) — tell the whole story.
  • 04_never_trust_unverified_claims.py: claims pulled with verify_signature=False show role=admin with no signature check — proof that decoding ≠ trusting.
  • 07_dont_put_secrets_in_payload.py: the payload is extracted with no key at all, hammering home that base64url is not encryption.

⚠️ Common misconceptions

  • "PyJWT blocks confusion attacks, so I'm safe." Its guard helps, but you must still pin algorithms=[...] explicitly — never echo the token's own alg.
  • "verify_signature=False is fine for reading claims." Only for routing (picking a key by kid); never trust those claims.
  • "Signing hides the payload." Signing proves integrity/authenticity; the payload stays readable by anyone.
  • "A long-lived token is convenient and harmless." No exp (or a huge one) means a leaked token works forever — short TTL plus require: ['exp'].

💥 The star of the show: algorithm confusion (script 03)

The exploit in one breath: an RS256 server's public key is public. HS256 is symmetric (same key signs and verifies). So an attacker uses the public key as an HMAC secret to forge an HS256 token — and a server that allows algorithms=["HS256","RS256"] with that public key "verifies" it.

Script 03 demonstrates all three outcomes for real:

  1. ✅ Forgery succeeds against a naive/legacy verifier (models the historically vulnerable behavior).
  2. 🛡️ Modern PyJWT blocks it — it refuses to use an asymmetric PEM as an HMAC secret (InvalidKeyError). A genuinely valuable built-in defense.
  3. 🔒 The fix you own: pin algorithms=["RS256"] only → the forged token is rejected with InvalidAlgorithmError, while genuine RS256 tokens still pass.

Don't rely on the library's guard alone — pin your algorithms explicitly.

🔑 Key takeaways

  1. Pin the algorithm. jwt.decode(token, key, algorithms=["RS256"]) — exact and minimal. Never read alg from the token, never include none, never mix symmetric and asymmetric.
  2. Verify the claims. exp (and require it), aud, iss. Fail closed.
  3. Guard the keys. Strong random secrets, env/secret-manager storage, rotation, kid allowlists, asymmetric keys for third-party verification.
  4. The payload is public. Signing ≠ encryption. Never place secrets/PII in claims.
  5. Unverified ≠ trusted. Decode-without-verify is plumbing for choosing a key; trust only flows from a signature you validated.

⚠️ Pitfalls

  • Allowing none "just for testing" and shipping it.
  • Copy-pasting algorithms=[jwt.get_unverified_header(t)["alg"]] from a blog.
  • Forgetting audience=/issuer=, so a valid token from another app passes.
  • Long-lived (or eternal) access tokens with no revocation plan.
  • Treating base64url as if it were encryption.

"""
01 · The "alg: none" attack — unsecured JWTs
=============================================

The JWT spec defines an *unsecured* token: ``"alg": "none"`` with an EMPTY
signature. It exists for cases where integrity is guaranteed by another layer,
but it is a notorious footgun: if a verifier accepts ``none``, an attacker can
strip the signature, rewrite the payload, and walk straight in.

This script shows:

1. How to (deliberately) build a ``none`` token with PyJWT.
2. That PyJWT REFUSES to decode it unless you *explicitly* opt in with
   ``algorithms=["none"]`` AND disable signature verification.
3. Why you must NEVER allow ``none`` for tokens from untrusted sources.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/14-security-best-practices/01_alg_none_attack.py
"""

import jwt


def main() -> None:
    print("=" * 70)
    print("STEP 1 — Build an unsecured 'alg: none' token (no signature)")
    print("=" * 70)
    # PyJWT lets you create one, but only when you pass algorithm="none" and a
    # None key. Note the token ENDS WITH A DOT: the signature segment is empty.
    none_token = jwt.encode({"user": "attacker", "role": "admin"}, None, algorithm="none")
    print(f"none token: {none_token}")
    print(f"ends with empty signature segment? {none_token.endswith('.')}\n")

    print("=" * 70)
    print("STEP 2 — A safe verifier pins a real algorithm -> rejected")
    print("=" * 70)
    try:
        jwt.decode(none_token, "any-secret", algorithms=["HS256"])
        print("UNEXPECTED: none token accepted by an HS256 verifier?!")
    except jwt.InvalidAlgorithmError as exc:
        print(f"algorithms=['HS256'] -> rejected: {type(exc).__name__}: {exc}")
    except jwt.InvalidTokenError as exc:
        print(f"rejected: {type(exc).__name__}: {exc}")
    print("Because 'none' is not in the allow-list, the token is refused.\n")

    print("=" * 70)
    print("STEP 3 — Even allowing 'none' requires disabling signature checks")
    print("=" * 70)
    # PyJWT guards you twice: you must allow "none" AND turn off the signature
    # verification, otherwise it still raises.
    try:
        jwt.decode(none_token, algorithms=["none"])
        print("UNEXPECTED: decoded with just algorithms=['none']?!")
    except jwt.DecodeError as exc:
        print(f"algorithms=['none'] alone -> {type(exc).__name__}: {exc}")

    decoded = jwt.decode(
        none_token,
        algorithms=["none"],
        options={"verify_signature": False},  # explicit, scary opt-in
    )
    print(f"\nOnly with verify_signature=False does it decode: {decoded}")
    print("Notice: ZERO cryptographic proof was checked. Anyone wrote this.\n")

    print("=" * 70)
    print("THE LESSON")
    print("=" * 70)
    print("- NEVER include 'none' in `algorithms=[...]` for untrusted input.")
    print("- An attacker would flip role->admin, drop the signature, and submit.")
    print("- Always pin the exact signing algorithm(s) you actually issue.")


if __name__ == "__main__":
    main()

import jwt

SECRET = "a-strong-shared-secret-at-least-32-bytes-long!!"


def main() -> None:
    token = jwt.encode({"sub": "alice"}, SECRET, algorithm="HS256")
    print(f"HS256 token: {token[:50]}...\n")

    print("=" * 70)
    print("GOOD — pin the exact algorithm you issued")
    print("=" * 70)
    decoded = jwt.decode(token, SECRET, algorithms=["HS256"])
    print(f"algorithms=['HS256'] -> {decoded}\n")

    print("GOOD — pinning the wrong algorithm rejects the token")
    print("=" * 70)

    print("DANGEROUS ANTI-PATTERN — echoing the token's own 'alg'")

    print("Why it's bad: the attacker picks 'alg', so they pick how you verify.")
    print("It opens the door to the RS256->HS256 confusion attack (script 03).\n")

    print("=" * 70)
    print("RULE")
    print("=" * 70)
    print("Hard-code the algorithm(s) your system issues. Treat the token header")
    print("as a routing hint at most (e.g. selecting a key by 'kid'), never as")

03 Algorithm Confusion RSA HMAC03_algorithm_confusion_rsa_hmac.py ▾

This is the most famous JWT attack. Setup:

  • A server issues RS256 tokens (asymmetric: private key signs, PUBLIC key verifies). The public key is, by design, known to everyone.
  • The server's verification is misconfigured to allow BOTH algorithms: algorithms=["HS256", "RS256"] and it passes the RSA public key as the verification key.

The exploit: HS256 is symmetric — the same key signs and verifies. So the attacker takes the well-known public key and uses it as the HMAC secret to forge an HS256 token. The misconfigured server then "verifies" that token using the public key as the HMAC secret... and it matches. Forgery complete — no private key required.

What this script demonstrates, all actually running:

  1. Forgery SUCCEEDS against a naive verifier that treats the public key as an HMAC secret (this models historically-vulnerable libraries / hand-rolled verification).
  2. PyJWT's built-in guard blocks the same bad config: modern PyJWT refuses to use an asymmetric PEM as an HMAC secret (InvalidKeyError).
  3. The real fix you control: pin algorithms=["RS256"] only — the forged HS256 token is rejected outright.

"""
03 · Algorithm-confusion attack — the classic RS256 -> HS256 forgery
=====================================================================

This is the most famous JWT attack. Setup:

* A server issues **RS256** tokens (asymmetric: private key signs, PUBLIC key
  verifies). The public key is, by design, known to everyone.
* The server's verification is misconfigured to allow BOTH algorithms:
  ``algorithms=["HS256", "RS256"]`` and it passes the **RSA public key** as the
  verification key.

The exploit: HS256 is *symmetric* — the same key signs and verifies. So the
attacker takes the well-known **public key** and uses it as the **HMAC secret**
to forge an HS256 token. The misconfigured server then "verifies" that token
using the public key as the HMAC secret... and it matches. Forgery complete —
no private key required.

What this script demonstrates, all actually running:

1. **Forgery SUCCEEDS** against a naive verifier that treats the public key as
   an HMAC secret (this models historically-vulnerable libraries / hand-rolled
   verification).
2. **PyJWT's built-in guard** blocks the same bad config: modern PyJWT refuses
   to use an asymmetric PEM as an HMAC secret (``InvalidKeyError``).
3. **The real fix you control:** pin ``algorithms=["RS256"]`` only — the forged
   HS256 token is rejected outright.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/14-security-best-practices/03_algorithm_confusion_rsa_hmac.py
"""

import base64
import hashlib
import hmac

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def b64url_nopad(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode("ascii")


def forge_hs256_with_public_key(payload_json: bytes, public_pem: str) -> str:
    """Attacker: build an HS256 token using the RSA *public key* as the secret."""
    header = b64url_nopad(b'{"alg":"HS256","typ":"JWT"}')
    payload = b64url_nopad(payload_json)
    signing_input = f"{header}.{payload}".encode("ascii")
    # The public key PEM bytes ARE the HMAC secret here — that's the attack.
    sig = hmac.new(public_pem.encode("utf-8"), signing_input, hashlib.sha256).digest()
    return f"{header}.{payload}.{b64url_nopad(sig)}"


def vulnerable_verify(token: str, public_pem: str) -> dict:
    """A naive/legacy verifier that allows HS256 with the public key as secret.

    This reproduces the verification logic of historically-vulnerable JWT
    libraries (pre-mitigation) that did not refuse asymmetric keys for HMAC.
    """
    header_seg, payload_seg, sig_seg = token.split(".")
    signing_input = f"{header_seg}.{payload_seg}".encode("ascii")
    expected = hmac.new(
        public_pem.encode("utf-8"), signing_input, hashlib.sha256
    ).digest()
    presented = base64.urlsafe_b64decode(sig_seg + "=" * (-len(sig_seg) % 4))
    if not hmac.compare_digest(expected, presented):
        raise ValueError("signature mismatch")
    payload_json = base64.urlsafe_b64decode(payload_seg + "=" * (-len(payload_seg) % 4))
    import json

    return json.loads(payload_json)


def main() -> None:
    # --- The legitimate server's RSA key pair ---
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    ).decode()
    public_pem = (
        private_key.public_key()
        .public_bytes(
            encoding=serialization.Encoding.PEM,
            format=serialization.PublicFormat.SubjectPublicKeyInfo,
        )
        .decode()
    )

    print("=" * 72)

05 Expiration Is Mandatory05_expiration_is_mandatory.py ▾

A JWT is a bearer credential: whoever holds it is treated as the subject. If a token never expires and it leaks (logs, browser history, a proxy, a breach), the attacker has permanent access. There is no server-side session to revoke unless you build extra infrastructure.

Defenses shown here:

  1. A token with NO exp validates forever — demonstrate it.
  2. Add a short-lived exp; an expired token is rejected with ExpiredSignatureError.
  3. Force the issue: options={"require": ["exp"]} makes a missing exp an error, so you can never accidentally mint an eternal token.
