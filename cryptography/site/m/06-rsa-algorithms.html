Module 06 — RSA Algorithms (RS256 / RS384 / RS512)

🧠 Mental Model — Behind the Scenes

RSA signing rests on a trapdoor function: multiplying two large primes is trivial, but factoring the product back into those primes is computationally infeasible. Your key pair is two views of that same secret number. The private key knows the factors (and a derived "private exponent" d); the public key only knows the product n and a small "public exponent" e (almost always 65537). Anyone can run the easy direction; only the private-key holder can run the hard direction. That one-way asymmetry is the whole game — and it's why you can publish the public key to the entire internet without ever risking forgery.

When PyJWT signs with RS256, it does not encrypt your payload. It builds the signing input base64url(header) + "." + base64url(payload), hashes that with SHA-256, wraps the digest in PKCS#1 v1.5 padding (a fixed, deterministic byte template), and then applies the private-key trapdoor to the padded block. The result is the signature — the third segment of the JWT. Because the padding is fixed, RS256 is fully deterministic: the same payload and key always produce byte-for-byte the same token.

Verification reverses it: the public key transforms the signature back into the padded digest, the verifier independently re-hashes the header+payload it received, re-applies the same padding template, and checks for an exact match. If even one bit of the header or payload was tampered with, the recomputed digest won't match and PyJWT raises InvalidSignatureError. Notice what the signature size tracks: it equals the modulus size, not the hash. A 2048-bit key produces a 256-byte signature whether you choose RS256, RS384, or RS512 — the hash choice only changes which SHA digest gets padded inside.

🔍 A concrete analogy

Think of a wax seal pressed by a signet ring. The ring (private key) is unique and you never let it leave your hand. The imprint it leaves (signature) can be examined by anyone holding a reference photo of your seal (public key) — they can confirm "yes, this is genuinely her ring" — but no amount of staring at the photo lets them carve a matching ring of their own.

⚙️ What actually happens when you run the code

  1. rsa.generate_private_key(public_exponent=65537, key_size=2048) picks two ~1024-bit primes and derives the private exponent d and modulus n.
  2. private_key.public_key() strips away the secret factors, keeping only (n, e) — the safely shareable half.
  3. jwt.encode(payload, private_key, algorithm="RS256") SHA-256-hashes the header.payload string, applies PKCS#1 v1.5 padding, and runs the private-key trapdoor to produce the 256-byte signature.
  4. The three base64url segments are joined with dots into the final token string.
  5. jwt.decode(token, public_key, algorithms=["RS256"]) re-hashes the received header+payload and uses the public key to confirm the signature wraps that exact digest.
  6. A match returns the claims dict; any mismatch raises InvalidSignatureError.

👀 What to notice when you run the examples

  • In 02_rs256_sign_verify.py, signing uses private_key and decoding uses public_key — two different objects, the heart of asymmetric crypto.
  • In 03_rs384_rs512.py, the signature length stays 256 bytes across all three RS variants — proof that size follows the key, not the hash.
  • In 04_private_signs_public_verifies.py, handing the public key to jwt.encode fails: it simply has no signing material.
  • In 05_wrong_public_key_fails.py, a foreign but perfectly valid public key still yields InvalidSignatureError — only the paired key validates.
  • In 07_key_sizes.py, the 3072-bit key is noticeably slower to generate and produces a larger 384-byte signature.

⚠️ Common misconceptions

  • "RSA encrypts the JWT." No — it signs. The payload stays fully readable via base64url decode; signing only proves authenticity and integrity.
  • "The number in RS256 is the key size." It's the SHA hash (256/384/512). Key size is chosen separately at generation (2048, 3072, …).
  • "Bigger hash means bigger signature." Signature size equals the modulus length; the hash only changes the digest padded inside it.
  • "The public key is a secondary secret." It's meant to be published (via JWKS). Its safety to share is the entire point of going asymmetric.

🗝️ Module 06 — RSA Algorithms (RS256 / RS384 / RS512)

The asymmetric family. A private key signs; a public key verifies. Publish the public key to the whole world and they can confirm your tokens are genuine — yet none of them can forge one. This is the foundation of OAuth2 / OpenID Connect.

🧠 Why asymmetric signing matters

HMAC (Module 05) uses one shared secret, so verify == sign. That breaks down the moment you need untrusted third parties to verify tokens without being able to mint their own.

RSA solves this with a key pair:

  • 🔒 Private key — kept secret. Signs tokens. Never leaves the issuer.
  • 🌍 Public key — shared freely. Verifies tokens. Cannot sign.
flowchart LR subgraph Issuer ["Issuer (e.g. OAuth provider)"] PK[Private key 🔒] end PK -- "sign" --> JWT[JWT] JWT -- "verify" --> V1[Service A 🌍] JWT -- "verify" --> V2[Service B 🌍] JWT -- "verify" --> V3[Mobile app 🌍] PUB[Public key 🌍] -. "distributed via JWKS" .-> V1 PUB -.-> V2 PUB -.-> V3

Anyone with the public key can verify; only the holder of the private key can sign. That asymmetry is what makes federated identity possible.

🔐 Naming note: RS = RSASSA-PKCS1-v1_5 + SHA. So RS256 = RSASSA-PKCS1-v1_5 signatures using SHA-256. The number is the hash; the signature size is governed by the key size (2048-bit key → 256-byte signature), not the hash.

✨ Key takeaways

  • Private signs, public verifies. The public key can be published; it enables verification, never forgery.
  • Signature size = key size / 8. A 2048-bit key always yields a 256-byte signature regardless of RS256/384/512.
  • Wrong/foreign public key ⇒ InvalidSignatureError. Only the paired key validates.
  • 2048-bit is the modern minimum. 3072-bit adds margin at a CPU cost; keys under 2048 are considered weak.

⚠️ Pitfalls

  • 🚫 Leaking the private key. Game over — anyone can forge. Store it in a secret manager / HSM, never in source control.
  • 🚫 Confusing the keys. Sign with private, verify with public. Handing jwt.encode a public key fails (it has no signing material).
  • 🚫 Trusting the header's alg. Always pin accepted algorithms in algorithms=[...]; never let a token dictate none or downgrade you from RS256 to HS256.
  • 🚫 Unencrypted private PEMs in transit. The demo uses NoEncryption() for clarity; protect real private keys at rest.

"""01_generate_rsa_keypair.py — Create an RSA-2048 keypair and serialize it.

RSA is an *asymmetric* algorithm: you get a PAIR of keys.
  - PRIVATE key: kept secret; used to SIGN tokens.
  - PUBLIC key:  shared freely; used to VERIFY tokens.

To move keys between systems we serialize them to PEM text:
  - Private key -> PKCS#8 PEM  ("-----BEGIN PRIVATE KEY-----")
  - Public key  -> SubjectPublicKeyInfo PEM ("-----BEGIN PUBLIC KEY-----")

This script generates a fresh 2048-bit keypair entirely in memory (no network,
no files) and prints both PEMs so you can see exactly what they look like.
"""

from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa

# --- Generate the keypair ------------------------------------------------
# public_exponent=65537 is the standard, recommended choice.
# key_size=2048 is the modern minimum for RSA.
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()  # derived from the private key

# --- Serialize the PRIVATE key to PKCS#8 PEM -----------------------------
private_pem = private_key.private_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PrivateFormat.PKCS8,
    encryption_algorithm=serialization.NoEncryption(),  # unencrypted for the demo
)

# --- Serialize the PUBLIC key to SubjectPublicKeyInfo PEM ----------------
public_pem = public_key.public_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PublicFormat.SubjectPublicKeyInfo,
)

print("=== PRIVATE KEY (PKCS#8 PEM) — keep this SECRET ===")
print(private_pem.decode())
print("=== PUBLIC KEY (SubjectPublicKeyInfo PEM) — safe to share ===")
print(public_pem.decode())

print("Key size (bits):", private_key.key_size)

"""02_rs256_sign_verify.py — Sign with the private key, verify with the public.

RS256 = "RSASSA-PKCS1-v1_5 using SHA-256".

The whole point of RSA for JWTs:
  - The Issuer SIGNS with its PRIVATE key (which it never shares).
  - Anyone holding the PUBLIC key can VERIFY, but cannot forge new tokens.

PyJWT accepts either PEM bytes/strings OR cryptography key objects. Here we
pass the cryptography key objects directly for simplicity.

from cryptography.hazmat.primitives.asymmetric import rsa

# --- One keypair -------------------------------------------------------
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

payload = {"user": "ada", "role": "admin"}

# --- Sign with the PRIVATE key ------------------------------------------
token = jwt.encode(payload, private_key, algorithm="RS256")
print("Encoded JWT (RS256):")
print(token)
print()

header = jwt.get_unverified_header(token)
print("Algorithm in header (alg):", header["alg"])  # -> "RS256"
print()

# --- Verify with the PUBLIC key -----------------------------------------
decoded = jwt.decode(token, public_key, algorithms=["RS256"])
print("Decoded payload:", decoded)

03_rs384_rs512.py — The other RSA/SHA-2 variants: RS384 and RS512.

Just like the HMAC family had HS256/384/512, the RSA family has: RS256 -> RSASSA-PKCS1-v1_5 + SHA-256 RS384 -> RSASSA-PKCS1-v1_5 + SHA-384 RS512 -> RSASSA-PKCS1-v1_5 + SHA-512

The KEY stays the same; only the hash used inside the signature changes. Note that, unlike HMAC, the RSA signature length is governed by the KEY SIZE (2048-bit key -> 256-byte signature), not by the hash — so all three produce the same signature size for a given key.

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa

private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

payload = {"user": "ada", "role": "admin"}


def raw_signature_len(token: str) -> int:
    segment = token.split(".")[2]
    padding = "=" * (-len(segment) % 4)
    return len(base64.urlsafe_b64decode(segment + padding))


for alg in ["RS384", "RS512"]:
    token = jwt.encode(payload, private_key, algorithm=alg)
    header = jwt.get_unverified_header(token)
    decoded = jwt.decode(token, public_key, algorithms=[alg])

    print(f"--- {alg} ---")
    print("  header alg:", header["alg"])
    print("  signature size (bytes):", raw_signature_len(token), "(= key size / 8)")
    print("  decoded payload:", decoded)
    print()

04_private_signs_public_verifies.py — Only the public key is needed to verify.

This is the defining superpower of asymmetric signing:

  • You SIGN with the PRIVATE key.
  • You VERIFY with the PUBLIC key.
  • The public key CANNOT be used to sign.

So you can hand your public key to the whole world, and they can confirm your tokens are genuine — yet none of them can mint a token that appears to come from you. That is impossible with HMAC, where verify == sign.

We prove both halves below.

"""04_private_signs_public_verifies.py — Only the public key is needed to verify.

This is the defining superpower of asymmetric signing:

  * You SIGN with the PRIVATE key.
  * You VERIFY with the PUBLIC key.
  * The public key CANNOT be used to sign.

So you can hand your public key to the whole world, and they can confirm your
tokens are genuine — yet none of them can mint a token that appears to come
from you. That is impossible with HMAC, where verify == sign.

We prove both halves below.
"""

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa

private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

payload = {"iss": "auth.example.com", "sub": "user-123"}

# --- 1) Private key signs; public key verifies (the normal flow) ---------
token = jwt.encode(payload, private_key, algorithm="RS256")
decoded = jwt.decode(token, public_key, algorithms=["RS256"])
print("Verified with PUBLIC key only:", decoded)
print("(The verifier never needs — and never sees — the private key.)\n")

# --- 2) You CANNOT sign with just the public key -------------------------
# Signing requires the private key. Handing jwt.encode a public key fails.
try:
    jwt.encode(payload, public_key, algorithm="RS256")
    print("Unexpected: signing with the public key succeeded?!")
except Exception as exc:  # cryptography/PyJWT raises when no private material
    print("Attempt to SIGN with the public key failed, as expected:")
    print(f"  {type(exc).__name__}: {exc}")

print()
print("Conclusion: distributing the public key is safe; it only enables")
print("verification, never forgery.")

05 Wrong Public Key Fails05_wrong_public_key_fails.py ▾

05_wrong_public_key_fails.py — A mismatched public key rejects the token.

A signature only verifies against the public key that PAIRS with the private key that produced it. If you try to verify a token using an unrelated public key, PyJWT raises InvalidSignatureError.

This is exactly what protects you from forgeries: an attacker's key pair produces signatures that your trusted public key will reject.

06_load_keys_from_pem.py — Serialize keys to PEM and load them back.

In the real world your keys live OUTSIDE your program — in files, secret managers, or environment variables — as PEM text. This script shows the full round trip:

  5. Use the loaded keys with PyJWT.

PyJWT can also take the raw PEM bytes directly; we demonstrate that too.

"""06_load_keys_from_pem.py — Serialize keys to PEM and load them back.

In the real world your keys live OUTSIDE your program — in files, secret
managers, or environment variables — as PEM text. This script shows the full
round trip:

  1. Generate a keypair.
  2. Serialize to PEM (private = PKCS#8, public = SubjectPublicKeyInfo).
  3. Write the PEMs to temporary files (tempfile).
  4. Read them back and re-parse with
     serialization.load_pem_private_key / load_pem_public_key.
  5. Use the loaded keys with PyJWT.

PyJWT can also take the raw PEM bytes directly; we demonstrate that too.
"""

import os
import tempfile

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa

# --- 1) Generate + 2) serialize -----------------------------------------
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
private_pem = private_key.private_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PrivateFormat.PKCS8,
    encryption_algorithm=serialization.NoEncryption(),
)
public_pem = private_key.public_key().public_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PublicFormat.SubjectPublicKeyInfo,
)

# --- 3) Write the PEMs to temporary files --------------------------------
tmpdir = tempfile.mkdtemp(prefix="jwt-keys-")
priv_path = os.path.join(tmpdir, "private.pem")
pub_path = os.path.join(tmpdir, "public.pem")
with open(priv_path, "wb") as fh:
    fh.write(private_pem)
with open(pub_path, "wb") as fh:
    fh.write(public_pem)
print("Wrote PEM files to:")
print(" ", priv_path)
print(" ", pub_path, "\n")

# --- 4) Load them back into key objects ----------------------------------
with open(priv_path, "rb") as fh:
    loaded_private = serialization.load_pem_private_key(fh.read(), password=None)
with open(pub_path, "rb") as fh:
    loaded_public = serialization.load_pem_public_key(fh.read())
print("Reloaded key objects:")
print("  private:", type(loaded_private).__name__)
print("  public :", type(loaded_public).__name__, "\n")

# --- 5a) Use the LOADED key objects with PyJWT ---------------------------
token = jwt.encode({"sub": "from-loaded-keys"}, loaded_private, algorithm="RS256")
print("Signed with loaded private key:")
print(" ", jwt.decode(token, loaded_public, algorithms=["RS256"]), "\n")

# --- 5b) Hand the raw PEM bytes straight to PyJWT ------------------------
# PyJWT parses PEM strings/bytes for you, so files aren't strictly required.
token2 = jwt.encode({"sub": "from-raw-pem"}, private_pem, algorithm="RS256")
print("Signed using raw PEM bytes directly:")
print(" ", jwt.decode(token2, public_pem, algorithms=["RS256"]))

# --- Cleanup -------------------------------------------------------------
os.remove(priv_path)
os.remove(pub_path)
os.rmdir(tmpdir)
print("\nTemporary key files cleaned up.")

07 Key Sizes07_key_sizes.py ▾

07_key_sizes.py — RSA key size: 2048 vs 3072 bits.

The RSA key size is the length of the modulus. Bigger keys are harder to break but cost more CPU to generate, sign, and verify, and produce larger signatures (signature size = key_size / 8 bytes).

Rough guidance: - 2048-bit: the modern minimum; fine for most systems today. - 3072-bit: higher security margin (~128-bit security level); slower. - <2048-bit: considered weak — avoid.

This script builds a token with each size, confirms it still verifies, and prints the signature size so you can see the cost.

"""07_key_sizes.py — RSA key size: 2048 vs 3072 bits.

The RSA key size is the length of the modulus. Bigger keys are harder to
break but cost more CPU to generate, sign, and verify, and produce larger
signatures (signature size = key_size / 8 bytes).

Rough guidance:
  - 2048-bit: the modern minimum; fine for most systems today.
  - 3072-bit: higher security margin (~128-bit security level); slower.
  - <2048-bit: considered weak — avoid.

This script builds a token with each size, confirms it still verifies, and
prints the signature size so you can see the cost.
"""

import base64
import time

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa

payload = {"user": "ada"}


def raw_signature_len(token: str) -> int:
    segment = token.split(".")[2]
    padding = "=" * (-len(segment) % 4)
    return len(base64.urlsafe_b64decode(segment + padding))


for key_size in (2048, 3072):
    # Time the keygen to illustrate the perf tradeoff.
    start = time.perf_counter()
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=key_size)
    gen_ms = (time.perf_counter() - start) * 1000
    public_key = private_key.public_key()

    token = jwt.encode(payload, private_key, algorithm="RS256")
    decoded = jwt.decode(token, public_key, algorithms=["RS256"])

    print(f"--- RSA-{key_size} ---")
    print(f"  keygen time:      {gen_ms:7.1f} ms")
    print(f"  signature size:   {raw_signature_len(token)} bytes (= {key_size}/8)")
    print(f"  verifies OK:      {decoded == payload}")
    print()

print("Tradeoff: larger keys = stronger but slower and bigger tokens.")
print("2048-bit is a sound default; step up to 3072-bit for long-lived,")
print("high-value keys where the extra margin is worth the cost.")

08 RSA Vs HMAC When To Use08_rsa_vs_hmac_when_to_use.py ▾

08_rsa_vs_hmac_when_to_use.py — Choosing between HMAC and RSA.

Both HMAC (HS) and RSA (RS) produce signed, tamper-evident JWTs. The difference is the TRUST MODEL, and that is what should drive your choice.

HMAC (symmetric): - ONE shared secret signs and verifies. - Whoever can verify can also forge. - Great when the SAME party / mutually trusting services issue & check. - Simple: no key pairs, no PEM.

RSA (asymmetric): - PRIVATE key signs; PUBLIC key verifies. - You can publish the public key to untrusted third parties. - They can verify but NEVER forge. - This is why OAuth2 / OIDC providers (Google, Microsoft Entra ID, Auth0) sign with RSA/ECDSA and publish public keys via JWKS endpoints.

This script demonstrates both side by side.

DECISION GUIDE
  Use HMAC  when one party (or tightly trusted services) issues AND verifies.
  Use RSA   when others must verify but must NOT be able to sign
            (public APIs, OAuth/OIDC providers, microservices across teams).

"""08_rsa_vs_hmac_when_to_use.py — Choosing between HMAC and RSA.

Both HMAC (HS*) and RSA (RS*) produce signed, tamper-evident JWTs. The
difference is the TRUST MODEL, and that is what should drive your choice.

  HMAC (symmetric):
    - ONE shared secret signs and verifies.
    - Whoever can verify can also forge.
    - Great when the SAME party / mutually trusting services issue & check.
    - Simple: no key pairs, no PEM.

  RSA (asymmetric):
    - PRIVATE key signs; PUBLIC key verifies.
    - You can publish the public key to untrusted third parties.
    - They can verify but NEVER forge.
    - This is why OAuth2 / OIDC providers (Google, Microsoft Entra ID, Auth0)
      sign with RSA/ECDSA and publish public keys via JWKS endpoints.

This script demonstrates both side by side.
"""

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.exceptions import InvalidSignatureError

payload = {"sub": "user-123", "scope": "read"}

print("=" * 60)
print("HMAC (HS256): one shared secret — same-party trust")
print("=" * 60)
shared_secret = "one-secret-shared-between-trusted-services"
hs_token = jwt.encode(payload, shared_secret, algorithm="HS256")
print("Issuer signs with the secret.")
print("Verifier (same secret) ->", jwt.decode(hs_token, shared_secret, algorithms=["HS256"]))
# Anyone with the secret could ALSO mint tokens — that is the catch:
forged = jwt.encode({"sub": "attacker", "scope": "admin"}, shared_secret, algorithm="HS256")
print("Anyone holding the secret can also FORGE:", jwt.decode(forged, shared_secret, algorithms=["HS256"]))
print("=> Only safe to share the secret with fully trusted parties.\n")

print("=" * 60)
print("RSA (RS256): private signs, public verifies — third-party trust")
print("=" * 60)
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()
rs_token = jwt.encode(payload, private_key, algorithm="RS256")
print("Provider signs with its PRIVATE key (kept secret).")
print("Third party (PUBLIC key) ->", jwt.decode(rs_token, public_key, algorithms=["RS256"]))
# A third party holding only the public key CANNOT forge:
try:
    jwt.encode({"sub": "attacker"}, public_key, algorithm="RS256")
except Exception as exc:
    print("Third party tries to forge with the public key:", type(exc).__name__, "-> cannot sign")
# And a wrong public key would reject the token:
other_public = rsa.generate_private_key(public_exponent=65537, key_size=2048).public_key()
try:
    jwt.decode(rs_token, other_public, algorithms=["RS256"])
except InvalidSignatureError:
    print("Wrong public key -> InvalidSignatureError (forgeries rejected)")
print("=> Publish the public key freely; only you can sign.\n")

print("DECISION GUIDE")
print("  Use HMAC  when one party (or tightly trusted services) issues AND verifies.")
print("  Use RSA   when others must verify but must NOT be able to sign")
print("            (public APIs, OAuth/OIDC providers, microservices across teams).")
