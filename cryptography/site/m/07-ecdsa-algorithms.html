Module 07 · ECDSA Algorithms (ES256 / ES384 / ES512 / ES256K)

🧠 Mental Model — Behind the Scenes

ECDSA swaps RSA's "factoring is hard" trapdoor for a different one: the elliptic-curve discrete logarithm problem. Picture a fixed point G on a curve and an operation that lets you "add" the point to itself many times. Your private key is a secret integer d; your public key is the point Q = d·G. Computing Q from d is fast, but recovering d from Q — undoing all those additions — is infeasible. The astonishing payoff is size: a 256-bit elliptic-curve key delivers roughly the same security as a 3072-bit RSA key, so keys, signatures, and therefore tokens all shrink dramatically.

The catch that trips up everyone is that each ES* algorithm is welded to exactly one curve and one hash. ES256 means P-256 (SECP256R1) with SHA-256; ES384 means P-384 with SHA-384; ES512 means SHA-512 over P-521 — not "P-512", which doesn't exist; and ES256K means the Bitcoin/Ethereum Koblitz curve secp256k1 with SHA-256. You cannot mix a key on one curve with an algorithm expecting another — PyJWT raises InvalidKeyError.

There's a sharp security edge hiding in the signing step. Every ECDSA signature (r, s) requires a fresh, secret, uniformly random nonce k. If k ever repeats — or is even slightly predictable — an attacker can solve a little algebra and recover your private key outright. This is exactly how the 2010 Sony PS3 signing key was extracted: they reused k. So unlike RSA's deterministic padding, classic ECDSA's correctness depends on a healthy random number generator at the moment of signing. (Module 09's EdDSA was designed specifically to remove this footgun by deriving k deterministically.)

🔍 A concrete analogy

Imagine a combination dial on a colossal circular track. Spinning forward d clicks from the start lands you at a marked spot (your public point Q). Anyone can check you ended up at that spot, but staring at the spot tells them nothing about how many clicks you turned — the track is far too large to count backward. The secret nonce k is like a single-use scratch-off code you must never reuse on a second lock.

⚙️ What actually happens when you run the code

  1. ec.generate_private_key(ec.SECP256R1()) chooses a random secret integer d and computes the public point Q = d·G on the P-256 curve.
  2. The keys are serialized to PEM (PKCS#8 private, SubjectPublicKeyInfo public) so PyJWT can consume the bytes directly.
  3. jwt.encode(payload, private_pem, algorithm="ES256") SHA-256-hashes the signing input, draws a random nonce k, and computes the signature pair (r, s).
  4. PyJWT encodes (r, s) in the JOSE/raw concatenated format (not ASN.1 DER) and base64url-packs it as the token's third segment.
  5. jwt.decode(token, public_pem, algorithms=["ES256"]) re-hashes the input and uses the public point Q to confirm (r, s) is mathematically consistent.
  6. A valid pair returns the claims; a wrong curve or tampered token fails.

👀 What to notice when you run the examples

  • In 02_es256.py, the signature segment is strikingly short — compare it mentally to RSA's 256-byte signatures from Module 06.
  • In 04_es512.py, the curve is SECP521R1 (521 bits) even though the algorithm is named ES512 — that's the SHA-512 hash talking.
  • In 06_curve_must_match_alg.py, a P-256 key handed to ES384 raises InvalidKeyError — hard proof the algorithm fixes the curve.
  • In 05_es256k.py, ES256K uses secp256k1, a different 256-bit curve from ES256's P-256 — same key size, not interchangeable.
  • In 07_ecdsa_vs_rsa_size.py, the EC key and signature are a fraction of the RSA equivalents at matching security levels.

⚠️ Common misconceptions

  • "ES512 uses a 512-bit curve." It uses P-521. The 512 is the hash (SHA-512). There is no SECP512R1.
  • "ES256 and ES256K are the same." Both are 256-bit + SHA-256, but on different curves (P-256 vs secp256k1). Keys don't cross over.
  • "ECDSA is deterministic like RSA." It is not — it needs a secure random nonce per signature, and reuse leaks the private key.
  • "Smaller keys mean weaker security." A 256-bit EC key matches RSA-3072. The compactness comes from harder math, not less safety.

🟢 Module 07 · ECDSA Algorithms (ES256 / ES384 / ES512 / ES256K)

Elliptic-curve signatures: the same security as RSA, in a fraction of the size. This module covers the entire ECDSA JWT family and the single most important rule that trips everyone up — each algorithm is welded to one specific curve.

🧠 What is ECDSA?

ECDSA (Elliptic Curve Digital Signature Algorithm) is an asymmetric signing scheme. You sign with a private key and anyone can verify with the matching public key — exactly like RSA. The difference is the underlying math: elliptic curves instead of large-integer factorisation. The payoff is dramatic size savings:

Security level RSA key EC curve
~112-bit RSA-2048 —
~128-bit RSA-3072 P-256
~192-bit RSA-7680 P-384
~256-bit RSA-15360 P-521

A 256-bit elliptic-curve key matches a 3072-bit RSA key. Smaller keys ⇒ smaller signatures ⇒ smaller tokens ⇒ faster crypto.

🔗 The golden rule: algorithm ↔ curve

Every ECDSA JWT algorithm is bound to exactly one curve and one hash. You cannot mix them.

Algorithm Curve (cryptography name) NIST / common name Hash
ES256 SECP256R1 P-256 SHA-256
ES384 SECP384R1 P-384 SHA-384
ES512 SECP521R1 P-521 ⚠️ SHA-512
ES256K SECP256K1 secp256k1 (Bitcoin) SHA-256

⚠️ Pitfalls

  • ES512 uses P-521, not "P-512". There is no SECP512R1 curve. The 512 refers to SHA-512; the curve is the 521-bit SECP521R1. This is the most common ECDSA beginner trap.
  • Wrong curve = hard failure. Signing with a key whose curve doesn't match the algorithm raises InvalidKeyError (see script 06).
  • ES256 ≠ ES256K. Both are 256-bit + SHA-256, but they use different curves (NIST P-256 vs Koblitz secp256k1). They are not interchangeable.
  • ECDSA needs a good RNG at sign time. A repeated/predictable nonce can leak the private key. (EdDSA — Module 09 — fixes this by being deterministic.)
  • Always pin algorithms=[...] in jwt.decode(). Never accept an open list.

🔑 Key takeaways

  • ECDSA gives RSA-grade security with much smaller keys, signatures, and tokens.
  • Each ES* algorithm is locked to one curve + one hash — memorise the table.
  • ES256K is the blockchain/DID curve (Bitcoin & Ethereum).
  • PyJWT happily accepts PEM bytes/str or cryptography key objects for both signing and verifying.

The headline benefit: equivalent security with much smaller keys (a 256-bit EC key is roughly as strong as a 3072-bit RSA key).

"""
07 · ECDSA · 01 — Generate an EC (Elliptic Curve) keypair
==========================================================

ECDSA (Elliptic Curve Digital Signature Algorithm) is a public-key signature
scheme — just like RSA — but built on *elliptic curve* math instead of large
integer factorisation. The headline benefit: **equivalent security with much
smaller keys** (a 256-bit EC key is roughly as strong as a 3072-bit RSA key).

In JWT land, the ECDSA family is: ES256, ES384, ES512, ES256K. Each one is
*bound to a specific curve* (more on that in later scripts). This first script
just teaches the mechanics of creating an EC keypair with the `cryptography`
library and serialising it to PEM — the text format PyJWT happily consumes.

We use the **P-256** curve here (named SECP256R1 in `cryptography`), which is
the curve required by the most common ECDSA JWT algorithm, ES256.
"""

from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec


def main() -> None:
    # ------------------------------------------------------------------
    # 1. Generate the private key on a named curve.
    #    The private key is the secret signing key; the matching public
    #    key (derived from it) is what verifiers use to check signatures.
    # ------------------------------------------------------------------
    private_key = ec.generate_private_key(ec.SECP256R1())
    public_key = private_key.public_key()

    print("=" * 70)
    print("Generated an EC keypair on curve:", private_key.curve.name)
    print("Key size (bits):", private_key.key_size)
    print("=" * 70)

    # ------------------------------------------------------------------
    # 2. Serialise the PRIVATE key to PEM.
    #    - PKCS8 is the modern, standard container for private keys.
    #    - NoEncryption() means we don't wrap it in a passphrase (fine
    #      for a teaching demo; encrypt at rest in production!).
    # ------------------------------------------------------------------
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )

    # ------------------------------------------------------------------
    # 3. Serialise the PUBLIC key to PEM.
    #    - SubjectPublicKeyInfo is the standard public-key container.
    # ------------------------------------------------------------------
    public_pem = public_key.public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    print("\n--- PRIVATE KEY (PEM, PKCS8) ---")
    print(private_pem.decode())
    print("--- PUBLIC KEY (PEM, SubjectPublicKeyInfo) ---")
    print(public_pem.decode())

    # Notice how short these PEM blocks are compared with an RSA key —
    # that compactness is ECDSA's signature super-power (script 07).
    print("Private PEM length:", len(private_pem), "bytes")
    print("Public  PEM length:", len(public_pem), "bytes")


if __name__ == "__main__":
    main()

02 ES25602_es256.py ▾

ES256 = ECDSA using the P-256 curve (SECP256R1) with SHA-256.

It is by far the most widely deployed ECDSA JWT algorithm — it's what most OAuth2 / OpenID Connect providers reach for when they want elliptic-curve tokens. The "256" refers to both the curve size (P-256) and the hash (SHA-256); for ES256 they happen to line up neatly.

Key fact to memorise: ES256 REQUIRES a P-256 key. Hand PyJWT a key on a different curve and signing will fail. We'll prove that gotcha in script 06.

"""
07 · ECDSA · 02 — Signing & verifying with ES256
=================================================

**ES256** = ECDSA using the **P-256** curve (SECP256R1) with **SHA-256**.

It is by far the most widely deployed ECDSA JWT algorithm — it's what most
OAuth2 / OpenID Connect providers reach for when they want elliptic-curve
tokens. The "256" refers to *both* the curve size (P-256) and the hash
(SHA-256); for ES256 they happen to line up neatly.

Key fact to memorise:  **ES256 REQUIRES a P-256 key.**  Hand PyJWT a key on a
different curve and signing will fail. We'll prove that gotcha in script 06.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec


def make_p256_pems() -> tuple[bytes, bytes]:
    """Generate a P-256 keypair and return (private_pem, public_pem)."""
    private_key = ec.generate_private_key(ec.SECP256R1())
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )
    return private_pem, public_pem


def main() -> None:
    private_pem, public_pem = make_p256_pems()

    payload = {"sub": "alice", "role": "admin", "iss": "es256-demo"}

    # SIGN: PyJWT accepts the PEM bytes directly and signs with the private key.
    token = jwt.encode(payload, private_pem, algorithm="ES256")
    print("=" * 70)
    print("ES256 token (curve P-256 + SHA-256):")
    print(token)
    print("=" * 70)

    # The JOSE header records the algorithm so verifiers know what to expect.
    header = jwt.get_unverified_header(token)
    print("\nDecoded JOSE header:", header)  # -> {'alg': 'ES256', 'typ': 'JWT'}

    # VERIFY: use the PUBLIC key. We must whitelist the expected algorithm.
    decoded = jwt.decode(token, public_pem, algorithms=["ES256"])
    print("Verified payload:", decoded)

    # The signature is short — ECDSA produces compact signatures.
    signature_b64 = token.split(".")[2]
    print("\nSignature segment length (base64url chars):", len(signature_b64))


if __name__ == "__main__":
    main()

05 ES256K05_es256k.py ▾

ES256K = ECDSA using the secp256k1 curve with SHA-256.

The trailing K stands for Koblitz — the secp256k1 curve is a special Koblitz curve famous for being the signing curve of Bitcoin and Ethereum. It is a different curve from the NIST P-256 (SECP256R1) used by ES256, even though both are 256-bit and both use SHA-256.

ES256   ->  SECP256R1   (NIST "P-256", the random/prime curve)
ES256K  ->  SECP256K1   (Koblitz curve, Bitcoin/Ethereum)

ES256K was added to the JOSE registry largely to support blockchain / DID (decentralised identity) use cases. PyJWT supports it out of the box.

07 · ECDSA · 05 — Signing & verifying with ES256K  (Bitcoin's curve)
====================================================================

**ES256K** = ECDSA using the **secp256k1** curve with **SHA-256**.

The trailing **K** stands for *Koblitz* — the secp256k1 curve is a special
Koblitz curve famous for being the signing curve of **Bitcoin** and **Ethereum**.
It is a *different* curve from the NIST P-256 (SECP256R1) used by ES256, even
though both are 256-bit and both use SHA-256.

    ES256   ->  SECP256R1   (NIST "P-256", the random/prime curve)
    ES256K  ->  SECP256K1   (Koblitz curve, Bitcoin/Ethereum)

ES256K was added to the JOSE registry largely to support blockchain / DID
(decentralised identity) use cases. PyJWT supports it out of the box.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec


def main() -> None:
    # secp256k1 — the Koblitz curve. Note the 'K' suffix in SECP256K1.
    private_key = ec.generate_private_key(ec.SECP256K1())
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    print("Curve in use:", private_key.curve.name, "(Bitcoin / Ethereum curve)")

    payload = {"sub": "dave", "wallet": "0xDEADBEEF", "alg_note": "Koblitz curve"}

    token = jwt.encode(payload, private_pem, algorithm="ES256K")
    print("\nES256K token (secp256k1 + SHA-256):")
    print(token)

    print("\nJOSE header:", jwt.get_unverified_header(token))

    decoded = jwt.decode(token, public_pem, algorithms=["ES256K"])
    print("Verified payload:", decoded)


if __name__ == "__main__":
    main()

06 Curve Must Match Alg06_curve_must_match_alg.py ▾

This is the single most important operational fact about ECDSA in JWTs:

ES256   <->  SECP256R1  (P-256)
ES384   <->  SECP384R1  (P-384)
ES512   <->  SECP521R1  (P-521)
ES256K  <->  SECP256K1  (secp256k1)

You cannot mix and match. If you generate a P-256 key and try to sign with ES384, PyJWT (via the cryptography backend) rejects it, because ES384's SHA-384 + P-384 contract is violated. The RFC 7518 spec ties each algorithm to exactly one curve so that verifiers know precisely what to validate.

This script demonstrates the failure and the success, catching the error so the script still exits 0.

"""
07 · ECDSA · 06 — Each ES algorithm is BOUND to one specific curve
==================================================================

This is the single most important operational fact about ECDSA in JWTs:

    ES256   <->  SECP256R1  (P-256)
    ES384   <->  SECP384R1  (P-384)
    ES512   <->  SECP521R1  (P-521)
    ES256K  <->  SECP256K1  (secp256k1)

You cannot mix and match. If you generate a **P-256** key and try to sign with
**ES384**, PyJWT (via the cryptography backend) rejects it, because ES384's
SHA-384 + P-384 contract is violated. The RFC 7518 spec ties each algorithm to
exactly one curve so that verifiers know precisely what to validate.

This script demonstrates the failure *and* the success, catching the error so
the script still exits 0.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec


def pem_pair(curve: ec.EllipticCurve) -> tuple[bytes, bytes]:
    key = ec.generate_private_key(curve)
    priv = key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    pub = key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )
    return priv, pub


def main() -> None:
    payload = {"sub": "erin"}

    # A P-256 key — correct for ES256, WRONG for ES384.
    p256_priv, _ = pem_pair(ec.SECP256R1())

    print("=" * 70)
    print("Attempt 1: sign with ES384 using a P-256 key  (EXPECTED TO FAIL)")
    print("=" * 70)
    try:
        jwt.encode(payload, p256_priv, algorithm="ES384")
        print("!! Unexpected success — this should not happen.")
    except Exception as exc:  # noqa: BLE001 — we want to teach via the message
        print("Caught", type(exc).__name__, ":", exc)
        print("Reason: ES384 demands a P-384 (SECP384R1) key; we gave it P-256.")

    print("\n" + "=" * 70)
    print("Attempt 2: sign with ES384 using the CORRECT P-384 key  (SUCCEEDS)")
    print("=" * 70)
    p384_priv, p384_pub = pem_pair(ec.SECP384R1())
    token = jwt.encode(payload, p384_priv, algorithm="ES384")
    decoded = jwt.decode(token, p384_pub, algorithms=["ES384"])
    print("Token:", token)
    print("Verified payload:", decoded)

    print("\nLesson: match the curve to the algorithm — always.")


if __name__ == "__main__":
    main()

07 ECDSA Vs RSA Size07_ecdsa_vs_rsa_size.py ▾

Why bother with elliptic curves at all? Size and speed.

A 256-bit EC key (P-256) offers roughly the same security level as a 3072-bit RSA key (~128-bit security). Even compared with a 2048-bit RSA key (~112-bit security, weaker than P-256), the EC key and its signatures are dramatically smaller. Smaller keys & signatures mean:

- smaller tokens on the wire
- less storage / bandwidth
- faster signing on constrained devices

This script measures it concretely: PEM sizes for the public keys, and the signature segment length of an actual JWT signed with each scheme.

"""
07 · ECDSA · 07 — ECDSA vs RSA: tiny keys, equivalent security
==============================================================

Why bother with elliptic curves at all? **Size and speed.**

A 256-bit EC key (P-256) offers roughly the same security level as a
**3072-bit** RSA key (~128-bit security). Even compared with a 2048-bit RSA key
(~112-bit security, *weaker* than P-256), the EC key and its signatures are
dramatically smaller. Smaller keys & signatures mean:

    - smaller tokens on the wire
    - less storage / bandwidth
    - faster signing on constrained devices

This script measures it concretely: PEM sizes for the public keys, and the
signature segment length of an actual JWT signed with each scheme.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec, rsa


def ec_pems() -> tuple[bytes, bytes]:
    key = ec.generate_private_key(ec.SECP256R1())
    return (
        key.private_bytes(
            serialization.Encoding.PEM,
            serialization.PrivateFormat.PKCS8,
            serialization.NoEncryption(),
        ),
        key.public_key().public_bytes(
            serialization.Encoding.PEM,
            serialization.PublicFormat.SubjectPublicKeyInfo,
        ),
    )


def rsa_pems() -> tuple[bytes, bytes]:
    key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    return (
        key.private_bytes(
            serialization.Encoding.PEM,
            serialization.PrivateFormat.PKCS8,
            serialization.NoEncryption(),
        ),
        key.public_key().public_bytes(
            serialization.Encoding.PEM,
            serialization.PublicFormat.SubjectPublicKeyInfo,
        ),
    )


def sig_len(token: str) -> int:
    """Length of the base64url signature segment of a JWT."""
    return len(token.split(".")[2])


def main() -> None:
    ec_priv, ec_pub = ec_pems()
    rsa_priv, rsa_pub = rsa_pems()

    payload = {"sub": "frank"}

    es256 = jwt.encode(payload, ec_priv, algorithm="ES256")
    rs256 = jwt.encode(payload, rsa_priv, algorithm="RS256")

    # Sanity: both verify.
    jwt.decode(es256, ec_pub, algorithms=["ES256"])
    jwt.decode(rs256, rsa_pub, algorithms=["RS256"])

    print("=" * 70)
    print("PUBLIC KEY PEM SIZE")
    print("=" * 70)
    print(f"  EC P-256   : {len(ec_pub):>5} bytes")
    print(f"  RSA-2048   : {len(rsa_pub):>5} bytes")
    print(f"  RSA is {len(rsa_pub) / len(ec_pub):.1f}x larger for *weaker* security.")

    print("\n" + "=" * 70)
    print("JWT SIGNATURE SEGMENT SIZE (base64url chars)")
    print("=" * 70)
    print(f"  ES256 sig  : {sig_len(es256):>5}")
    print(f"  RS256 sig  : {sig_len(rs256):>5}")

    print("\n" + "=" * 70)
    print("WHOLE TOKEN SIZE")
    print("=" * 70)
    print(f"  ES256 token: {len(es256):>5} chars")
    print(f"  RS256 token: {len(rs256):>5} chars")

    print(
        "\nTakeaway: P-256 matches ~3072-bit RSA security, yet keys, signatures,"
        "\nand tokens are all far smaller. That is the ECDSA value proposition."
    )


if __name__ == "__main__":
    main()
