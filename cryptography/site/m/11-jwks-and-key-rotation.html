Module 11 · JWKS & Key Rotation

🧠 Mental Model — Behind the Scenes

When Google, Microsoft, or any OIDC provider signs a token with a private key, the whole world needs a way to find the matching public key to verify it — without phoning the provider's support desk. The answer is delightfully boring: the provider publishes its public keys as plain JSON on an HTTPS URL. That document is a JWKS (JSON Web Key Set), and each entry inside it is a JWK (JSON Web Key). A JWK is just a public key turned inside-out into JSON fields: kty (key type), n and e (the RSA modulus and exponent, base64url-encoded), plus metadata like kid (key ID), use, and alg. There is no secret in it — that's the entire point.

The magic glue is the kid. When a token is signed, the provider stamps the signing key's kid into the token's header. So verification becomes a lookup: read the unverified header, pull out the kid, find the JWK in the set whose kid matches, turn that JWK back into a usable key, and only then run jwt.decode. PyJWT exposes this as PyJWKSet.from_dict(jwks) to load the set and jwks_set[kid].key to grab the verification key. Under the hood RSAAlgorithm.to_jwk() serializes a key into JWK JSON and RSAAlgorithm.from_jwk() reverses it.

PyJWKClient is not a new algorithm or protocol — it is a thin convenience wrapper that adds exactly two things to the flow above: fetch the JWKS over HTTPS and cache it so you aren't hammering the jwks_uri on every request. get_signing_key_from_jwt(token) internally does get_unverified_header → kid → lookup → return PyJWK. That's it. Module 11 proves this by reimplementing the method by hand against a local in-memory set.

Because a set can hold many keys at once, key rotation becomes downtime-free: publish the old and new keys together, switch signing to the new key, and only retire the old key once every token it signed has expired. The overlap window is what keeps verification from ever breaking.

🔍 A concrete analogy

A JWKS is like a company's public lobby directory of notary stamps. Every notarized document carries a stamp number (kid). To check a document is genuine you don't call the notary — you look up that stamp number in the public directory, compare the impression, and you're done. When the firm hires a new notary, they simply add the new stamp to the directory while leaving the retiring notary's stamp posted until their last documents expire.

⚙️ What actually happens when you run the code

  1. A provider generates one or more RSA key pairs, each assigned a unique kid.
  2. Each public key is serialized to JWK JSON via RSAAlgorithm.to_jwk(), then bundled into {"keys": [...]} — the JWKS.
  3. A token is signed with a private key, and that key's kid is written into the token header (headers={"kid": "key-a"}).
  4. The verifier calls jwt.get_unverified_header(token) to read the kid without trusting anything yet.
  5. PyJWKSet.from_dict(jwks) parses the set; jwks_set[kid] returns the matching PyJWK, and .key yields a ready cryptographic key object.
  6. jwt.decode(token, signing_key.key, algorithms=["RS256"]) performs the real signature check against that public key.
  7. PyJWKClient wraps steps 4–5 with an HTTPS fetch plus an in-memory cache.

👀 What to notice when you run the examples

  • In 01_what_is_a_jwk.py, the JWK is human-readable JSON with no private material — you can paste it anywhere safely.
  • In 04_pyjwkset_from_dict.py, indexing the set by string kid (jwks_set["key-a"]) returns a PyJWK object; .key is what jwt.decode actually wants.
  • 06_key_rotation_flow.py shows the overlap phase where both an A-signed and a B-signed token verify simultaneously — and the moment A is dropped, lingering A-tokens finally fail.
  • 07_pyjwkclient_explained.py reimplements get_signing_key_from_jwt in three lines, revealing the "client" as pure convenience around a flow you already know.

⚠️ Common misconceptions

  • "A JWKS contains secrets." No — it contains only public keys. Publishing it is intentional and safe.
  • "PyJWKClient does something cryptographically special." It only fetches and caches JSON; the verification logic is identical to manual kid lookup.
  • "Rotation means swapping one key for another instantly." Real rotation overlaps keys so in-flight tokens keep verifying until they expire.
  • "You can skip algorithms=[...] because the right key was selected." Never — always pin the expected algorithm even after resolving the key by kid.

🔑 Module 11 · JWKS & Key Rotation

How does Google verify a token you've never sent it before, signed with a key it rotated last week? The answer is JWKS — a published set of public keys, addressable by kid. This module builds the whole machine locally, no network required.

🧠 The big idea

Asymmetric tokens (RS256, ES256, …) are verified with a public key. Providers need a standard, web-friendly way to publish those public keys so any client can verify tokens. That standard is:

  • JWK (JSON Web Key) — one key, expressed as JSON (kty, n, e, kid, …).
  • JWKS (JSON Web Key Set) — {"keys": [jwk, jwk, …]}, served at a jwks_uri.
  • PyJWKSet / PyJWKClient — PyJWT's tools to load a JWKS and pick the right key for a token by its kid.

Because a set can hold many keys at once, providers can rotate keys with zero downtime: publish old + new together, switch signing to the new key, then drop the old one once its tokens have expired.

🔄 JWKS verification flow

flowchart TD T[Incoming token] --> H[get_unverified_header] H --> K{kid} subgraph JWKS [PyJWKSet from jwks_uri] A[PyJWK key-a] B[PyJWK key-b] end K -->|matches| B B --> KEY[signing_key.key] KEY --> D[jwt.decode algorithms=RS256] D --> OK[✅ verified claims]

PyJWKClient is just this flow plus "fetch the JWKS over HTTPS and cache it."

🔁 Key rotation timeline

flowchart LR P1["Phase 1<br/>JWKS = {A}<br/>sign with A"] P2["Phase 2 · overlap<br/>JWKS = {A, B}<br/>sign with B"] P3["Phase 3<br/>JWKS = {B}<br/>A retired"] P1 --> P2 --> P3

During Phase 2, both old (A-signed) and new (B-signed) tokens verify. Only when A is dropped in Phase 3 do lingering A-tokens finally fail.

✅ Key takeaways

  • A JWK is a key as JSON; a JWKS is a list of JWKs under "keys".
  • kid ties a token to a specific key in the set — rotation depends on it.
  • PyJWKSet.from_dict + jwks_set[kid].key is the manual JWKS verification path.
  • PyJWKClient adds HTTPS fetching and caching on top of that exact path.
  • Rotate by overlapping keys, then dropping the old one after its tokens age out.

⚠️ Pitfalls

  • No kid in the token (or the set). If the token's kid isn't published, verification must fail — handle the lookup miss explicitly.
  • Caching too aggressively. If you cache a JWKS forever, you'll reject tokens signed by a freshly rotated key. PyJWKClient caches with sane defaults; respect rotation.
  • Re-fetching on every request. The opposite mistake — hammering the jwks_uri. Cache it.
  • Trusting the JWKS source. Always fetch over HTTPS from the provider's well-known URL; a poisoned JWKS means forged tokens.
  • Forgetting the algorithm whitelist. Even with the right key, always pass algorithms=["RS256"] (or your expected set) to jwt.decode.

01 · What is a JWK?

A JWK (JSON Web Key, RFC 7517) is just a JSON representation of a cryptographic key. Instead of a PEM blob, a key becomes a JSON object whose fields depend on the key type (kty):

For an RSA public key you'll see: - kty — key type, "RSA". - n — the modulus (base64url). - e — the public exponent (base64url, usually "AQAB" = 65537). - optional metadata like kid (key id), use ("sig"), alg.

Why bother? Because JSON is web-native. A server can publish its public keys as a JWK Set at an HTTPS URL, and any client can fetch and parse them with nothing but a JSON parser — no PEM/ASN.1 tooling required. That's the whole basis of JWKS.

PyJWT can produce a JWK straight from a cryptography public-key object via jwt.algorithms.RSAAlgorithm.to_jwk. This script generates a keypair and prints the resulting JWK.

"""01 · What is a JWK?

A **JWK** (JSON Web Key, RFC 7517) is just a JSON representation of a
cryptographic key. Instead of a PEM blob, a key becomes a JSON object whose
fields depend on the key type (``kty``):

For an RSA public key you'll see:
- ``kty`` — key type, ``"RSA"``.
- ``n``   — the modulus (base64url).
- ``e``   — the public exponent (base64url, usually ``"AQAB"`` = 65537).
- optional metadata like ``kid`` (key id), ``use`` (``"sig"``), ``alg``.

Why bother? Because JSON is web-native. A server can publish its public keys as a
JWK **Set** at an HTTPS URL, and any client can fetch and parse them with nothing
but a JSON parser — no PEM/ASN.1 tooling required. That's the whole basis of
JWKS.

PyJWT can produce a JWK straight from a cryptography public-key object via
``jwt.algorithms.RSAAlgorithm.to_jwk``. This script generates a keypair and
prints the resulting JWK.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/11-jwks-and-key-rotation/01_what_is_a_jwk.py
"""

import json

from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def main() -> None:
    # Generate an RSA keypair locally (no network, no files).
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    public_key = private_key.public_key()

    # Convert the PUBLIC key into a JWK. to_jwk returns a JSON *string*.
    jwk_json = RSAAlgorithm.to_jwk(public_key)
    jwk = json.loads(jwk_json)

    print("RSA public key as a JWK:")
    print(json.dumps(jwk, indent=2))
    print()

    # Explain the fields we got back.
    print("Field-by-field:")
    print(f"  kty = {jwk['kty']!r}   (key type — RSA)")
    print(f"  e   = {jwk['e']!r}   (public exponent, base64url; 'AQAB' == 65537)")
    print(f"  n   = <{len(jwk['n'])} base64url chars>  (the 2048-bit modulus)")
    print()
    print("✅ A JWK is just a key expressed as JSON — web-native and easy to publish.")


if __name__ == "__main__":
    main()

"""02 · Round-tripping an RSA key through a JWK.

A JWK isn't a one-way export format — it's a faithful representation you can
convert *back* into a usable key. This is exactly what a verifier does: it
receives a JWK (as JSON), turns it into a public key, and verifies tokens with it.

The two functions:
- ``RSAAlgorithm.to_jwk(public_key)``  -> JWK JSON string.
- ``RSAAlgorithm.from_jwk(jwk_json)``  -> a cryptography public-key object.

This script:
    1. Generates an RSA keypair.
    2. Signs a token with the PRIVATE key (RS256).
    3. Exports the PUBLIC key to a JWK, then imports it back with ``from_jwk``.
    4. Verifies the token using the *round-tripped* key — proving it's identical.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/11-jwks-and-key-rotation/02_jwk_from_rsa_key.py
"""

import json

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def main() -> None:
    # 1. Keypair.
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    public_key = private_key.public_key()

    # 2. Sign with the private key.
    token = jwt.encode({"user": "dave"}, private_key, algorithm="RS256")
    print("Token signed with RS256 private key:")
    print(token)
    print()

    # 3. Export public key -> JWK -> back to a key object.
    jwk_json = RSAAlgorithm.to_jwk(public_key)
    print("Public key as JWK:")
    print(json.dumps(json.loads(jwk_json), indent=2))
    print()

    roundtripped_key = RSAAlgorithm.from_jwk(jwk_json)

    # 4. Verify using the key we reconstructed from the JWK.
    claims = jwt.decode(token, roundtripped_key, algorithms=["RS256"])
    print(f"✅ Verified with round-tripped JWK key: {claims}")
    print("   to_jwk -> from_jwk preserves the key perfectly.")


if __name__ == "__main__":
    main()

03 · Building a JWKS document.

A JWKS (JSON Web Key Set, RFC 7517) is simply a JSON object with one field, keys, whose value is a list of JWKs:

{"keys": [ <jwk1>, <jwk2>, ... ]}

This is what identity providers publish at their jwks_uri (e.g. https://.../discovery/v2.0/keys). Having multiple keys in the set is the whole point: it lets a provider serve an old key and a new key simultaneously during rotation, so tokens signed by either remain verifiable.

Each key needs a unique kid so tokens can reference it. to_jwk doesn't add a kid for us, so we attach one to each JWK ourselves.

"""03 · Building a JWKS document.

A **JWKS** (JSON Web Key *Set*, RFC 7517) is simply a JSON object with one field,
``keys``, whose value is a list of JWKs:

    {"keys": [ <jwk1>, <jwk2>, ... ]}

This is what identity providers publish at their ``jwks_uri`` (e.g.
``https://.../discovery/v2.0/keys``). Having *multiple* keys in the set is the
whole point: it lets a provider serve an old key and a new key simultaneously
during rotation, so tokens signed by either remain verifiable.

Each key needs a unique ``kid`` so tokens can reference it. ``to_jwk`` doesn't add
a ``kid`` for us, so we attach one to each JWK ourselves.

This script generates two RSA keypairs and assembles a two-key JWKS, entirely
locally.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/11-jwks-and-key-rotation/03_build_a_jwks.py
"""

import json

from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def public_jwk(public_key, kid: str) -> dict:
    """Convert an RSA public key to a JWK dict and tag it with kid/use/alg."""
    jwk = json.loads(RSAAlgorithm.to_jwk(public_key))
    # Add the metadata a real JWKS carries.
    jwk["kid"] = kid
    jwk["use"] = "sig"   # this key is for signatures (not encryption)
    jwk["alg"] = "RS256"
    return jwk


def main() -> None:
    # Two independent keypairs.
    key_a = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    key_b = rsa.generate_private_key(public_exponent=65537, key_size=2048)

    jwks = {
        "keys": [
            public_jwk(key_a.public_key(), kid="key-a"),
            public_jwk(key_b.public_key(), kid="key-b"),
        ]
    }

    print("JWKS document ({'keys': [...]}):")
    print(json.dumps(jwks, indent=2))
    print()

    print(f"Number of keys in the set: {len(jwks['keys'])}")
    print(f"kids present: {[k['kid'] for k in jwks['keys']]}")
    print()
    print("✅ A JWKS is just a list of JWKs under a 'keys' field, each with its own kid.")


if __name__ == "__main__":
    main()

import json

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def public_jwk(public_key, kid: str) -> dict:
    jwk = json.loads(RSAAlgorithm.to_jwk(public_key))
    jwk.update({"kid": kid, "use": "sig", "alg": "RS256"})
    return jwk


def main() -> None:

    key_b = rsa.generate_private_key(public_exponent=65537, key_size=2048)

    jwks = {
        "keys": [
            public_jwk(key_a.public_key(), "key-a"),
            public_jwk(key_b.public_key(), "key-b"),
        ]
    }

    # Load the whole set in one call.
    jwks_set = jwt.PyJWKSet.from_dict(jwks)
    print(f"Loaded a PyJWKSet with {len(jwks_set.keys)} PyJWK(s).")

    print("Iterating jwks_set.keys:")

    chosen = jwks_set["key-b"]
    print(f"jwks_set['key-b'] -> PyJWK with kid={chosen.key_id!r}")
    print(f"  chosen.key is a usable verification key: {type(chosen.key).__name__}")

"""05 · Selecting the right key by ``kid`` from a PyJWKSet.

Now we combine module 10's pattern with module 11's tools. The verifier holds a
``PyJWKSet`` (its local copy of the provider's JWKS). When a token arrives:

    1. ``get_unverified_header(token)`` -> read the ``kid``.
    2. Index the set: ``jwks_set[kid]`` -> the matching ``PyJWK``.
    3. ``jwt.decode(token, pyjwk.key, algorithms=["RS256"])`` -> verified claims.

This is the real JWKS verification flow, just with the JWKS coming from a local
dict instead of an HTTPS fetch. The selection logic is byte-for-byte what
``PyJWKClient`` does internally (see script 07).

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/11-jwks-and-key-rotation/05_select_key_by_kid.py
"""

import json

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def public_jwk(public_key, kid: str) -> dict:
    jwk = json.loads(RSAAlgorithm.to_jwk(public_key))
    jwk.update({"kid": kid, "use": "sig", "alg": "RS256"})
    return jwk


def main() -> None:
    # Provider side: two keys, both published in the JWKS.
    key_a = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    key_b = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    jwks = {
        "keys": [
            public_jwk(key_a.public_key(), "key-a"),
            public_jwk(key_b.public_key(), "key-b"),
        ]
    }

    # Issue a token signed by key-b, advertising kid=key-b in the header.
    token = jwt.encode(
        {"user": "erin"}, key_b, algorithm="RS256", headers={"kid": "key-b"}
    )

    # Verifier side: load the public JWKS.
    jwks_set = jwt.PyJWKSet.from_dict(jwks)

    # 1. Read kid (unverified) to choose a key.
    kid = jwt.get_unverified_header(token)["kid"]
    print(f"Token advertises kid={kid!r}")

    # 2. Select the matching PyJWK.
    signing_key = jwks_set[kid]
    print(f"Selected PyJWK kid={signing_key.key_id!r} from the set of "
          f"{len(jwks_set.keys)} keys")

    # 3. Verify with that key.
    claims = jwt.decode(token, signing_key.key, algorithms=["RS256"])
    print(f"✅ Verified claims: {claims}")
    print()

    # Sanity check: the *other* key must NOT validate this token.
    other = jwks_set["key-a"]
    try:
        jwt.decode(token, other.key, algorithms=["RS256"])
    except jwt.InvalidSignatureError:
        print("Cross-check: key-a correctly FAILS to verify a key-b token "
              "(InvalidSignatureError).")


if __name__ == "__main__":
    main()

06 Key Rotation Flow06_key_rotation_flow.py ▾

06 · A key-rotation flow, simulated locally.

Key rotation is the reason JWKS exists. You periodically retire an old signing key and start using a new one — but you can't flip a switch instantly, because tokens signed by the old key are still circulating and valid. The solution: publish both keys at once for an overlap window.

The lifecycle this script simulates:

Phase 1 — only key A exists. Tokens signed by A. JWKS = {A}.
Phase 2 — rotation begins. New key B added. JWKS = {A, B}.
          Start signing new tokens with B (kid=B).
          Verifier with JWKS={A,B} validates BOTH old-A and new-B tokens.
Phase 3 — A is fully retired. JWKS = {B}.
          Old A-signed tokens now FAIL (their kid isn't in the set).

This is precisely how providers rotate without downtime: overlap, then drop.

"""06 · A key-rotation flow, simulated locally.

Key rotation is *the* reason JWKS exists. You periodically retire an old signing
key and start using a new one — but you can't flip a switch instantly, because
tokens signed by the old key are still circulating and valid. The solution:
**publish both keys at once** for an overlap window.

The lifecycle this script simulates:

    Phase 1 — only key A exists. Tokens signed by A. JWKS = {A}.
    Phase 2 — rotation begins. New key B added. JWKS = {A, B}.
              Start signing new tokens with B (kid=B).
              Verifier with JWKS={A,B} validates BOTH old-A and new-B tokens.
    Phase 3 — A is fully retired. JWKS = {B}.
              Old A-signed tokens now FAIL (their kid isn't in the set).

This is precisely how providers rotate without downtime: overlap, then drop.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/11-jwks-and-key-rotation/06_key_rotation_flow.py
"""

import json

import jwt
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm


def public_jwk(public_key, kid: str) -> dict:
    jwk = json.loads(RSAAlgorithm.to_jwk(public_key))
    jwk.update({"kid": kid, "use": "sig", "alg": "RS256"})
    return jwk


def make_jwks(*pairs) -> dict:
    """Build a JWKS from (public_key, kid) pairs."""
    return {"keys": [public_jwk(pub, kid) for pub, kid in pairs]}


def try_verify(token: str, jwks: dict) -> str:
    """Verify a token against a JWKS, returning a human-readable outcome."""
    jwks_set = jwt.PyJWKSet.from_dict(jwks)
    kid = jwt.get_unverified_header(token)["kid"]
    try:
        signing_key = jwks_set[kid]  # KeyError-like failure if kid not published
    except KeyError:
        return f"REJECTED — kid {kid!r} is not in the current JWKS"
    try:
        claims = jwt.decode(token, signing_key.key, algorithms=["RS256"])
    except jwt.PyJWTError as exc:
        return f"REJECTED — {type(exc).__name__}"
    return f"VERIFIED — {claims}"


def main() -> None:
    key_a = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    key_b = rsa.generate_private_key(public_exponent=65537, key_size=2048)

    # A token issued early in life, signed by key A.
    token_old = jwt.encode({"era": "old"}, key_a, algorithm="RS256", headers={"kid": "A"})

    # --- Phase 1: only A is published ---
    jwks_v1 = make_jwks((key_a.public_key(), "A"))
    print("Phase 1 — JWKS = {A}")
    print(f"  old token (kid=A): {try_verify(token_old, jwks_v1)}")
    print()

    # --- Phase 2: rotation — A and B both published; new tokens signed by B ---
    jwks_v2 = make_jwks((key_a.public_key(), "A"), (key_b.public_key(), "B"))
    token_new = jwt.encode({"era": "new"}, key_b, algorithm="RS256", headers={"kid": "B"})
    print("Phase 2 — JWKS = {A, B}  (overlap window)")
    print(f"  old token (kid=A): {try_verify(token_old, jwks_v2)}")
    print(f"  new token (kid=B): {try_verify(token_new, jwks_v2)}")
    print()

    # --- Phase 3: A retired; only B remains ---
    jwks_v3 = make_jwks((key_b.public_key(), "B"))
    print("Phase 3 — JWKS = {B}  (A retired)")
    print(f"  old token (kid=A): {try_verify(token_old, jwks_v3)}")
    print(f"  new token (kid=B): {try_verify(token_new, jwks_v3)}")
    print()
    print("✅ Overlap keeps old tokens valid; dropping A finally invalidates them.")


if __name__ == "__main__":
    main()
