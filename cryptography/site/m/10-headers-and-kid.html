Module 10 · Headers & kid

🧠 Mental Model — Behind the Scenes

A JWT is three base64url segments — header.payload.signature — and the first one, the JOSE header, is the verifier's instruction sheet. It's a small JSON object that answers, "how do I process this token before I trust anything in it?" The two parameters that carry the weight are alg (which algorithm signed it — HS256, RS256, …) and kid (a key identifier string naming which key signed it). Other parameters you'll meet are typ (the media type of the whole token, e.g. JWT or at+jwt) and cty (the media type of the payload, used mainly for nested JWTs).

Here's the subtle, important part: to verify a token you need to know which key to verify with — but that information lives in the header, which you haven't verified yet. So there's an unavoidable bootstrap step. jwt.get_unverified_header(token) simply base64url-decodes the first segment without touching the signature or any key. That gives you alg and kid before verification. You then use kid to look up the right key in your keystore, and only then call jwt.decode to do the real, signature-checked validation. The golden rule: the unverified header is attacker-controlled data, safe to use only for key selection, never for an authorization or trust decision.

This kid → look up key → verify pattern is the entire conceptual foundation of JWKS (Module 11). A real identity provider holds many keys at once — for rotation, for multiple environments — and publishes their public halves as a JWKS document. The verifier reads kid from each incoming token, finds the matching key in its cached copy of that document, and verifies. Swap the in-memory {kid: key} dict in this module's scripts for "a JSON document fetched over HTTPS and cached," and you've literally built what PyJWKClient does. The mechanics are identical — only the source of the keys changes.

flowchart LR A[Token arrives] --> B[get_unverified_header] B --> C{Read kid + alg} C --> D[Look up key in keystore] D --> E["jwt.decode(token, key, algorithms=[whitelist])"] E --> F{Signature valid?} F -- yes --> G[Trusted claims] F -- no --> H[InvalidSignatureError]

🔍 A concrete analogy

The header is the address and routing line on an envelope. The postal sorter reads "destination: branch 5" before opening anything, and uses it only to route the letter to the right desk — never as proof the letter is genuine. The kid is that routing label: it tells the verifier which key (which "desk") should examine the contents, but the contents aren't trusted until the signature inside is actually checked.

⚙️ What actually happens when you run the code

  1. The issuer keeps a keystore — a {kid: key} map of several active keys.
  2. When signing, it picks one key and stamps that key's kid into the header via headers={"kid": kid}; PyJWT adds alg automatically.
  3. A token arrives at the verifier; jwt.get_unverified_header(token) base64url-decodes the first segment — no signature check, no key needed.
  4. The verifier reads kid and looks it up in its own keystore; an unknown kid is rejected immediately (InvalidKeyError).
  5. With the resolved key, jwt.decode(token, key, algorithms=ALLOWED_ALGS) performs the full, signature-checked validation against a fixed algorithm whitelist.
  6. A valid signature returns the claims; tampering or a wrong key raises InvalidSignatureError.

👀 What to notice when you run the examples

  • In 01_default_header.py, the header is {"alg":"HS256","typ":"JWT"} even though you never set typ or alg — PyJWT supplies them.
  • In 04_get_unverified_header.py, you read alg/kid with no key at all — a vivid reminder the header is unauthenticated.
  • In 06_header_drives_key_selection.py, two tokens signed under different kids each route to the correct secret and verify cleanly.
  • In that same script, a token with kid: "ghost" is rejected with InvalidKeyError before any signature math runs — selection fails fast.
  • In 05_typ_and_cty.py, notice typ describes the envelope (at+jwt) while cty describes the payload (nested JWTs).

⚠️ Common misconceptions

  • "The header is verified, so I can trust kid/alg." It is not verified by get_unverified_header. Use it only to select a key.
  • "Just pass the token's own alg into decode." That enables algorithm-confusion attacks (Module 14). Always pin a fixed algorithms=[...] whitelist.
  • "kid is optional trivia." The moment you have more than one key, kid is the linchpin of verification — add it from day one.
  • "typ and cty are the same thing." typ is the token's media type; cty is the payload's media type, used chiefly for nested JWTs.

🪪 Module 10 · Headers & kid

The payload gets all the attention, but the tiny JSON object at the front of every JWT — the JOSE header — is what makes multi-key systems, key rotation, and JWKS possible. This module is all about that header.

🧠 The big idea

A JWT is header.payload.signature. The header answers a single question for the verifier: "how do I process this token?" Two parameters carry most of the weight:

  • alg — which algorithm signed it (HS256, RS256, …).
  • kid — which key signed it, so the verifier can pick the right one from a set of many.

Once a service has more than one signing key (which every real service eventually does), kid stops being optional trivia and becomes the linchpin of verification. The pattern you learn here — read kid from the unverified header, look up the key, then verify — is exactly how JWKS works in module 11.

🔄 How header-driven key selection works

flowchart LR A[Token arrives] --> B[get_unverified_header] B --> C{Read kid} C --> D[Look up key in keystore] D --> E[jwt.decode with that key + alg whitelist] E --> F{Signature valid?} F -- yes --> G[✅ Trusted claims] F -- no --> H[❌ InvalidSignatureError]

The key insight: you must read the header before you can verify, because the header tells you which key to verify with. That read is unverified — so you use it only to select a key, never to make a trust decision.

🗝️ Common header parameters

Param Meaning Example
alg Signing algorithm (PyJWT sets this for you) HS256, RS256
typ Media type of the token JWT, at+jwt
cty Media type of the payload JWT (nested), application/json
kid Key identifier for verification-key lookup key-1, 2025-key

✅ Key takeaways

  • jwt.encode(..., headers={...}) adds custom header params; PyJWT always supplies alg itself, so don't put alg in headers=.
  • jwt.get_unverified_header(token) decodes the header without the key and without checking the signature — use it purely to choose a verification key.
  • kid lets one verifier hold many keys and pick the correct one per token.
  • typ describes the envelope (use explicit types like at+jwt defensively); cty describes the payload (mainly for nested JWTs).
  • The kid → key → decode flow is the conceptual core of JWKS (module 11).

⚠️ Pitfalls

  • Trusting unverified data. The header (and unverified payload) are attacker-controlled. Only use them to select a key, never to authorize.
  • Echoing alg back into decode. Always pass a fixed, trusted algorithms=[...] whitelist. Feeding the token's own alg into decode enables algorithm-confusion attacks (module 14).
  • Forgetting kid exists until rotation. Add kid from day one; retrofitting it during an incident is painful.
  • Assuming a missing kid is fine. Decide explicitly how to handle tokens with no kid (reject, or fall back to a default key).

01 · The default JOSE header.

Every JWT begins with a header — a small JSON object, base64url-encoded, that tells a verifier how to process the token. When you call jwt.encode() without specifying any extra headers, PyJWT writes a minimal default:

{"alg": "HS256", "typ": "JWT"}
  • alg — the signing algorithm. PyJWT requires this and uses it (after you whitelist it in decode(algorithms=[...])) to know how to verify.

This script signs a token and reads the header back with jwt.get_unverified_header — which decodes the header without checking the signature (perfectly safe here, the header is public anyway).

Every JWT begins with a *header* — a small JSON object, base64url-encoded, that

import json

import jwt

SECRET = "teaching-secret-key-with-at-least-32-bytes!"


def main() -> None:
    # Encode with NO explicit headers — PyJWT supplies the defaults.
    token = jwt.encode({"some": "payload"}, SECRET, algorithm="HS256")
    print("Encoded token:")
    print(token)
    print()

    # get_unverified_header decodes ONLY the first segment (the header).
    # It does not validate the signature — and it doesn't need the secret.
    header = jwt.get_unverified_header(token)
    print("Default header (decoded):")
    print(json.dumps(header, indent=2))
    print()

    # Prove the defaults are exactly what we expect.
    assert header["alg"] == "HS256", "alg should default to the chosen algorithm"
    assert header["typ"] == "JWT", "typ should default to 'JWT'"
    print("✅ Confirmed default header: {'alg': 'HS256', 'typ': 'JWT'}")


if __name__ == "__main__":
    main()

03 · kid — the Key ID header.

A single service often has multiple signing keys at once: an old one being phased out, a current one, maybe a future one. The kid header is how a token announces which key was used, so the verifier can pick the matching key from its keystore instead of guessing (or trying them all).

Here we keep an in-memory keystore mapping kid -> secret. The issuer stamps each token with the kid of the secret it used. The verifier reads that kid and looks up the correct secret. Use the wrong secret and verification fails — so getting the lookup right matters.

"""03 · ``kid`` — the Key ID header.

A single service often has **multiple** signing keys at once: an old one being
phased out, a current one, maybe a future one. The ``kid`` header is how a token
announces *which* key was used, so the verifier can pick the matching key from
its keystore instead of guessing (or trying them all).

Here we keep an in-memory keystore mapping ``kid -> secret``. The issuer stamps
each token with the ``kid`` of the secret it used. The verifier reads that
``kid`` and looks up the correct secret. Use the wrong secret and verification
fails — so getting the lookup right matters.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/10-headers-and-kid/03_kid_key_id.py
"""

import jwt

# A keystore: each key has a name (kid) and a secret value.
KEYSTORE = {
    "key-1": "secret-for-key-one-padded-to-32-plus-bytes!",
    "key-2": "secret-for-key-two-padded-to-32-plus-bytes!",
}


def issue(payload: dict, kid: str) -> str:
    """Sign a token using the secret named by ``kid`` and stamp ``kid`` in the header."""
    secret = KEYSTORE[kid]
    return jwt.encode(payload, secret, algorithm="HS256", headers={"kid": kid})


def verify(token: str) -> dict:
    """Read the kid from the (unverified) header, pick the right secret, then verify."""
    kid = jwt.get_unverified_header(token)["kid"]
    secret = KEYSTORE[kid]  # the right key for THIS token
    return jwt.decode(token, secret, algorithms=["HS256"])


def main() -> None:
    # Issue two tokens signed with two different keys.
    token_a = issue({"user": "alice"}, kid="key-1")
    token_b = issue({"user": "bob"}, kid="key-2")

    for label, token in (("token_a (key-1)", token_a), ("token_b (key-2)", token_b)):
        claims = verify(token)
        chosen_kid = jwt.get_unverified_header(token)["kid"]
        print(f"{label}: kid={chosen_kid} -> verified claims {claims}")

    print()

    # Show what happens if the kid points at the WRONG secret: verification fails.
    print("Tampering demo — verify token_a with key-2's secret:")
    try:
        jwt.decode(token_a, KEYSTORE["key-2"], algorithms=["HS256"])
    except jwt.InvalidSignatureError:
        print("  ❌ InvalidSignatureError (as expected — wrong key for this token)")

    print()
    print("✅ kid lets a verifier select the correct key per token.")


if __name__ == "__main__":
    main()

04 Get Unverified Header04_get_unverified_header.py ▾

04 · get_unverified_header — reading the header BEFORE you verify.

This is one of the most important — and most misunderstood — functions in PyJWT.

To verify a token you need the right key. But for asymmetric tokens (and any multi-key setup) you don't know which key until you read the kid from the header... which lives inside the token you haven't verified yet. Chicken, meet egg.

The resolution: jwt.get_unverified_header(token) decodes the header segment without checking the signature. You use it ONLY to discover alg and kid so you can choose the verification key — and then you do a full, signature-checked jwt.decode with that key.

⚠️ UNVERIFIED means UNTRUSTED. An attacker fully controls these values. Never make a security decision based on unverified header/claims beyond "which key should I try". Always whitelist algorithms in decode(algorithms=[...]) — do NOT feed the header's alg straight back in, or you enable algorithm-confusion attacks (module 14).

"""04 · ``get_unverified_header`` — reading the header BEFORE you verify.

This is one of the most important — and most misunderstood — functions in PyJWT.

To verify a token you need the right key. But for asymmetric tokens (and any
multi-key setup) you don't know *which* key until you read the ``kid`` from the
header... which lives *inside the token you haven't verified yet*. Chicken, meet
egg.

The resolution: ``jwt.get_unverified_header(token)`` decodes the header segment
**without checking the signature**. You use it ONLY to discover ``alg`` and
``kid`` so you can choose the verification key — and then you do a *full*,
signature-checked ``jwt.decode`` with that key.

⚠️  UNVERIFIED means UNTRUSTED. An attacker fully controls these values. Never
make a security decision based on unverified header/claims beyond "which key
should I try". Always whitelist algorithms in ``decode(algorithms=[...])`` — do
NOT feed the header's ``alg`` straight back in, or you enable algorithm-confusion
attacks (module 14).

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/10-headers-and-kid/04_get_unverified_header.py
"""

import json

import jwt

KEYSTORE = {
    "key-1": "secret-one-padded-to-at-least-32-bytes-long!",
    "key-2": "secret-two-padded-to-at-least-32-bytes-long!",
}
ALLOWED_ALGS = ["HS256"]  # our trusted whitelist — fixed, never taken from the token


def main() -> None:
    token = jwt.encode(
        {"user": "carol"}, KEYSTORE["key-2"], algorithm="HS256", headers={"kid": "key-2"}
    )

    # STEP 1: peek at the header — no key, no signature check.
    header = jwt.get_unverified_header(token)
    print("Unverified header (do NOT trust yet):")
    print(json.dumps(header, indent=2))
    print()

    alg = header["alg"]
    kid = header["kid"]
    print(f"Header advertises alg={alg!r}, kid={kid!r}")

    # STEP 2: use kid to select the key. Use our OWN whitelist for algorithms,
    # not the header's alg value.
    if alg not in ALLOWED_ALGS:
        raise ValueError(f"Refusing untrusted algorithm {alg!r}")
    key = KEYSTORE[kid]

    # STEP 3: NOW verify for real — this is the trusted result.
    verified = jwt.decode(token, key, algorithms=ALLOWED_ALGS)
    print(f"✅ Verified claims (trusted): {verified}")
    print()
    print("Remember: get_unverified_header is for KEY SELECTION only — never trust it.")


if __name__ == "__main__":
    main()

05 Typ And Cty05_typ_and_cty.py ▾

05 · typ and cty — token type vs. content type.

Two header parameters describe what kind of thing the token is:

  • typ (type) — the media type of the whole JWT object. Conventionally "JWT". RFC 8725 / RFC 9068 recommend using an explicit type to prevent cross-service token confusion. For OAuth2 access tokens, RFC 9068 mandates typ="at+jwt". Other examples: "dpop+jwt", "logout+jwt".

  • cty (content type) — the media type of the payload. You only need this when the payload is itself something structured that a recipient must be told how to interpret — most famously a nested JWT (a JWT whose payload is another JWT), where you'd set cty="JWT".

Rule of thumb: typ is about the envelope; cty is about the contents.

This script issues an access-token-style JWT with typ="at+jwt" and shows a verifier explicitly requiring that type — a good defensive habit.

import json

import jwt

SECRET = "teaching-secret-key-with-at-least-32-bytes!"


def main() -> None:
    # An OAuth2-style access token: RFC 9068 says typ MUST be "at+jwt".
    access_token = jwt.encode(
        {"sub": "user-123", "scope": "read:profile"},
        SECRET,
        algorithm="HS256",
        headers={"typ": "at+jwt"},
    )
    print("Access token header:")
    print(json.dumps(jwt.get_unverified_header(access_token), indent=2))
    print()

    # A defensive verifier: only accept tokens that declare the expected type.
    header = jwt.get_unverified_header(access_token)
    expected_typ = "at+jwt"
    if header.get("typ") != expected_typ:
        raise ValueError(f"Wrong token type: expected {expected_typ!r}")
    claims = jwt.decode(access_token, SECRET, algorithms=["HS256"])
    print(f"✅ typ check passed; verified access-token claims: {claims}")
    print()

    # cty demo: a token whose payload is described as JSON content.
    typed_payload = jwt.encode(
        {"data": {"nested": True}},
        SECRET,
        algorithm="HS256",
        headers={"cty": "application/json"},
    )
    print("Token declaring its payload content type (cty):")
    print(json.dumps(jwt.get_unverified_header(typed_payload), indent=2))
    print()
    print("Takeaway: typ = type of the envelope; cty = type of the payload.")


if __name__ == "__main__":
    main()

06 · The header drives key selection — the foundation of JWKS.

This script ties the whole module together into the pattern that every JWKS-based system (Auth0, Okta, Microsoft Entra ID, Google, ...) uses under the hood:

1. The issuer holds a KEYSTORE: {kid -> key}.
2. When signing, it picks a key and stamps that key's ``kid`` into the header.
3. The verifier reads the ``kid`` from the *unverified* header.
4. It looks up the matching key in its own copy of the keystore.
5. It performs a full, signature-checked ``jwt.decode`` with that key.

Swap the in-memory dict for "a JWKS document fetched over HTTPS and cached" and you have exactly what PyJWKClient does (module 11). The mechanics are identical; only the source of the keys differs.

We use HMAC secrets here to keep the focus on the selection pattern. In module 11 the same flow runs with RSA public keys from a real JWKS.

"""06 · The header drives key selection — the foundation of JWKS.

This script ties the whole module together into the pattern that every JWKS-based
system (Auth0, Okta, Microsoft Entra ID, Google, ...) uses under the hood:

    1. The issuer holds a KEYSTORE: {kid -> key}.
    2. When signing, it picks a key and stamps that key's ``kid`` into the header.
    3. The verifier reads the ``kid`` from the *unverified* header.
    4. It looks up the matching key in its own copy of the keystore.
    5. It performs a full, signature-checked ``jwt.decode`` with that key.

Swap the in-memory dict for "a JWKS document fetched over HTTPS and cached" and
you have exactly what ``PyJWKClient`` does (module 11). The mechanics are
identical; only the *source* of the keys differs.

We use HMAC secrets here to keep the focus on the selection pattern. In module 11
the same flow runs with RSA public keys from a real JWKS.

Run:
    /home/astro/catalyst/jwt-test/.venv/bin/python \
        pyjwt-course/10-headers-and-kid/06_header_drives_key_selection.py
"""

import jwt

# The issuer's keystore — multiple active keys, each addressable by kid.
KEYSTORE = {
    "2024-key": "secret-from-last-year-padded-to-32-bytes-ok!",
    "2025-key": "secret-currently-in-use-padded-to-32-bytes!",
}
ALLOWED_ALGS = ["HS256"]


def sign(payload: dict, kid: str) -> str:
    """Issuer side: pick the key by kid and advertise that kid in the header."""
    return jwt.encode(payload, KEYSTORE[kid], algorithm="HS256", headers={"kid": kid})


def verify(token: str) -> dict:
    """Verifier side: kid -> key lookup -> signature-checked decode."""
    header = jwt.get_unverified_header(token)
    kid = header.get("kid")
    if kid is None:
        raise jwt.InvalidTokenError("Token has no 'kid' header")
    if kid not in KEYSTORE:
        raise jwt.InvalidKeyError(f"Unknown kid: {kid!r}")
    key = KEYSTORE[kid]
    return jwt.decode(token, key, algorithms=ALLOWED_ALGS)


def main() -> None:
    print("Keystore kids:", list(KEYSTORE))
    print()

    for kid in KEYSTORE:
        token = sign({"resource": f"signed-with-{kid}"}, kid)
        claims = verify(token)
        print(f"kid={kid}: verified -> {claims}")

    print()

    # An unknown kid (e.g. a retired or forged key id) is cleanly rejected.
    forged = jwt.encode(
        {"x": 1}, "whatever-secret-padded-to-at-least-32-bytes", algorithm="HS256",
        headers={"kid": "ghost"},
    )
    print("Token with unknown kid 'ghost':")
    try:
        verify(forged)
    except jwt.InvalidKeyError as exc:
        print(f"  ❌ {type(exc).__name__}: {exc}")

    print()
    print("✅ This kid -> key -> decode flow IS the heart of JWKS (next module).")


if __name__ == "__main__":
    main()
