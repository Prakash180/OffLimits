Module 05 — HMAC Algorithms (HS256 / HS384 / HS512)

🧠 Mental Model — Behind the Scenes

The HMAC family — HS256, HS384, HS512 — is one algorithm with three hash sizes bolted in. HMAC means Hash-based Message Authentication Code, and the formula is the heart of the whole module: signature = HMAC_SHA(secret, base64url(header) + "." + base64url(payload)). The number in the name (256/384/512) is simply which SHA-2 hash runs inside. Everything else — the symmetry, the trust model, the verification dance — is identical across all three.

HMAC isn't a plain hash; it's a keyed construction. Internally it mixes the secret into the message in two passes (an inner and outer hash, each with the secret XOR'd against a pad), which is what stops an attacker from extending or forging a digest without knowing the key. The practical upshot you can hold in your head: the signature is the raw hash digest, and its length equals the digest size — HS256 → 32 bytes, HS384 → 48, HS512 → 64. A bigger hash means a longer signature and a marginally longer token; all three are cryptographically secure, and HS256 is the sensible default.

The defining trait of the entire family is symmetry: there is exactly one secret, and it both signs and verifies. This is the same coin from Module 02, now seen as a trust model. Because verifying requires the same key as signing, whoever can verify can also forge. That's why HMAC fits a single party or a tight cluster of mutually trusted services sharing a secret out-of-band — and why it's the wrong choice the moment an untrusted third party needs to verify (that's RSA/ECDSA territory in later modules).

Two operational realities round out the model. First, key length matters per algorithm: RFC 7518 recommends a key at least as long as the hash output, and PyJWT 2.13 emits an InsecureKeyLengthWarning for short keys. Second, rotation is just a list: sign new tokens with the newest secret, but accept verification against [newest, …older] so in-flight tokens keep working, then retire the old secret once its tokens have all expired.

🔍 A concrete analogy

HMAC is a tamper-evident seal pressed from a secret die, and the SHA size is how finely the die is engraved. SHA-256 is a 32-notch die; SHA-512 is a 64-notch die — more notches, a longer impression, but the same kind of seal. Anyone holding a copy of the die can both make genuine seals and check them — which is exactly why you'd only ever share the die inside your own workshop, never with outside vendors.

⚙️ What actually happens when you run the code

  1. jwt.encode(payload, SECRET, algorithm="HS384") builds the header.payload string, with the header recording "alg": "HS384".
  2. PyJWT runs HMAC_SHA384(SECRET, "header.payload"), producing a 48-byte digest.
  3. That digest is base64url-encoded and appended as the third segment; a str token is returned.
  4. jwt.decode(token, SECRET, algorithms=["HS384"]) re-computes the same HMAC over the received header.payload and constant-time-compares it to the signature.
  5. In 04_compare_signature_sizes.py, the script base64url-decodes the signature segment and measures its raw byte length, proving 32/48/64 bytes for 256/384/512.
  6. In rotation (06_secret_rotation_hmac.py), decode() is retried across a candidate list of secrets until one verifies — the others raise InvalidSignatureError and are skipped.

👀 What to notice when you run the examples

  • Across 01–03, only the algorithm name changes — the API and round-trip are identical, hammering home that it's one family.
  • In 01_hs256.py, reading the unverified header shows alg matches the algorithm you signed with.
  • In 04_compare_signature_sizes.py, the measured signature lengths come out exactly 32/48/64 bytes — the digest size is the signature size.
  • In 05_shared_secret_model.py, two simulated parties using the same secret both verify successfully — and that's precisely why each could also forge.
  • In 06_secret_rotation_hmac.py, a token signed with the old secret still verifies during the overlap window because the verifier tries multiple candidate secrets.

⚠️ Common misconceptions

  • ❌ "HS512 is more secure than HS256, so always use it." Overstated — all three are secure; the difference is signature length, and HS256 is a fine default.
  • ❌ "The 256 is the key length." False — it's the SHA hash size; the key should be at least that many bytes (PyJWT 2.13 warns with InsecureKeyLengthWarning if shorter).
  • ❌ "I can give the verify secret to third parties to verify tokens." Dangerous — with HMAC, verify == sign, so they could forge. Use RSA/ECDSA for that.
  • ❌ "Rotating secrets means an instant cutover." False — you accept a list of secrets during overlap, then drop the old one once its tokens expire.

🔑 Module 05 — HMAC Algorithms (HS256 / HS384 / HS512)

The shared-secret family. One key signs and verifies. Simple, fast, and perfect when the same party (or tightly trusted services) issues and checks tokens.

🧠 What is HMAC signing?

HMAC stands for Hash-based Message Authentication Code. For JWTs it works like this:

signature = HMAC_SHA(secret, base64url(header) + "." + base64url(payload))

The number in the algorithm name is the SHA-2 hash used inside:

Algorithm Hash Digest / signature size
HS256 SHA-256 32 bytes (256 bits)
HS384 SHA-384 48 bytes (384 bits)
HS512 SHA-512 64 bytes (512 bits)

HMAC is symmetric: there is exactly one secret. Because verifying and signing both need that same secret, anyone who can verify can also forge. That is the defining trait — and limitation — of this family.

🔐 Naming note: HS = HMAC + SHA. HS256 = HMAC using SHA-256.

🗺️ The shared-secret trust model

flowchart LR subgraph Trusted Boundary A[Issuer] -- "sign with secret 🔑" --> T[JWT] T -- "verify with same secret 🔑" --> B[Verifier] end A -. shares secret out-of-band .-> B note["Same secret on both sides:<br/>verify == sign"]

Both sides hold the same secret, exchanged ahead of time over a trusted channel. Guard that secret like a password.

✨ Key takeaways

  • One secret, both directions. With HMAC, can verify == can sign.
  • Bigger hash ⇒ bigger signature. HS256→32B, HS384→48B, HS512→64B. HS256 is a perfectly secure, common default.
  • Rotation = a list of accepted secrets. Sign with the newest, verify against [newest, …older], then drop the oldest once its tokens expire.

⚠️ Pitfalls

  • 🚫 Short/weak secrets. RFC 7518 recommends a key at least as long as the hash output (≥32/48/64 bytes for HS256/384/512). PyJWT 2.13 emits an InsecureKeyLengthWarning for short keys — use long, random secrets.
  • 🚫 Sharing the secret too widely. Every holder can mint valid tokens. If untrusted third parties must verify, you want RSA (Module 06), not HMAC.
  • 🚫 Algorithm mismatch. You must list the exact algorithm in algorithms= (e.g. ["HS384"]), and never accept ["none"].
  • 🚫 Hard-coding secrets in source. Load from a secret manager / env var.

➡️ Next

When the same secret on both sides is no longer acceptable — because you need others to verify but not sign — move on to Module 06 — RSA algorithms.

"""01_hs256.py — Signing and verifying a JWT with HS256.

HS256 = "HMAC using SHA-256". It is a *symmetric* (shared-secret) algorithm:
the SAME secret string is used to both create (sign) and verify the token.

Mental model:
    signature = HMAC_SHA256(secret, base64url(header) + "." + base64url(payload))

This is the most common "getting started" JWT algorithm because it needs
nothing more than a single secret string — no key pairs, no PEM files.
"""

import jwt

# A secret only the signer (and trusted verifiers) should know.
# In production this MUST be long, random, and stored securely. We use a
# 64+ byte secret so it satisfies even HS512's recommended key length.
SECRET = "super-secret-shared-key-keep-me-safe-please-and-make-it-nice-and-long"

payload = {"user": "ada", "role": "admin"}

# --- Encode (sign) -------------------------------------------------------
# jwt.encode(payload, key, algorithm) returns a compact JWT string.
token = jwt.encode(payload, SECRET, algorithm="HS256")
print("Encoded JWT (HS256):")
print(token)
print()

# --- Inspect the header WITHOUT verifying -------------------------------
# The header is just base64url-encoded JSON; anyone can read it.
header = jwt.get_unverified_header(token)
print("JOSE header:", header)
print("Algorithm in header (alg):", header["alg"])  # -> "HS256"
print()

# --- Decode (verify) -----------------------------------------------------
# We must pass the SAME secret and list the algorithm(s) we accept.
decoded = jwt.decode(token, SECRET, algorithms=["HS256"])
print("Decoded payload:", decoded)

04_compare_signature_sizes.py — How big is each HMAC signature?

A JWT has three dot-separated parts: header.payload.signature Each part is base64url-encoded. The signature is the raw output of the HMAC function, which is exactly as long as the underlying hash digest:

HS256 -> SHA-256 -> 256 bits -> 32 bytes
HS384 -> SHA-384 -> 384 bits -> 48 bytes
HS512 -> SHA-512 -> 512 bits -> 64 bytes

This script signs the SAME payload with all three algorithms and measures the raw signature length to prove the relationship above.

"""04_compare_signature_sizes.py — How big is each HMAC signature?

A JWT has three dot-separated parts:  header.payload.signature
Each part is base64url-encoded. The signature is the raw output of the HMAC
function, which is exactly as long as the underlying hash digest:

    HS256 -> SHA-256 -> 256 bits -> 32 bytes
    HS384 -> SHA-384 -> 384 bits -> 48 bytes
    HS512 -> SHA-512 -> 512 bits -> 64 bytes

This script signs the SAME payload with all three algorithms and measures the
raw signature length to prove the relationship above.
"""

import base64

import jwt

# 64+ bytes so HS256/384/512 are all happy with the key length.
SECRET = "super-secret-shared-key-keep-me-safe-please-and-make-it-nice-and-long"
payload = {"user": "ada", "role": "admin"}


def b64url_decode(segment: str) -> bytes:
    """Decode a base64url string, restoring any stripped '=' padding."""
    # JWT strips base64url padding; we add it back before decoding.
    padding = "=" * (-len(segment) % 4)
    return base64.urlsafe_b64decode(segment + padding)


print("Raw HMAC signature size = the hash digest size:\n")
for alg, expected_bytes in [("HS256", 32), ("HS384", 48), ("HS512", 64)]:
    token = jwt.encode(payload, SECRET, algorithm=alg)

    # The signature is the 3rd part of the compact token.
    signature_segment = token.split(".")[2]
    raw_signature = b64url_decode(signature_segment)

    print(
        f"  {alg}: {len(raw_signature):>2} bytes "
        f"({len(raw_signature) * 8} bits)  "
        f"-> matches SHA-{alg[2:]} digest: {len(raw_signature) == expected_bytes}"
    )

print()
print("Takeaway: a stronger hash => longer signature => slightly longer token.")
print("All three are secure; HS256 is the common default.")

05 Shared Secret Model05_shared_secret_model.py ▾

05_shared_secret_model.py — The shared-secret (symmetric) trust model.

HMAC is symmetric: there is exactly ONE secret, and that single secret is used for BOTH signing and verifying. Anyone who can verify a token can also forge one, because verifying and signing require the same key.

That makes HMAC perfect when the SAME party (or a small set of mutually trusting services) both issues and checks the tokens. It is a poor fit when you need to let untrusted third parties verify but not mint tokens — that is RSA/ECDSA territory (see module 06).

"""05_shared_secret_model.py — The shared-secret (symmetric) trust model.

HMAC is *symmetric*: there is exactly ONE secret, and that single secret is
used for BOTH signing and verifying. Anyone who can verify a token can also
forge one, because verifying and signing require the same key.

That makes HMAC perfect when the SAME party (or a small set of mutually
trusting services) both issues and checks the tokens. It is a poor fit when
you need to let untrusted third parties verify but not mint tokens — that is
RSA/ECDSA territory (see module 06).

Below we simulate two parties, an Issuer and a Verifier, that share one
secret out-of-band.
"""

import jwt
from jwt.exceptions import InvalidSignatureError

# The single secret both parties agreed on ahead of time (out-of-band).
# Kept comfortably long (>=32 bytes) to satisfy HS256 recommendations.
SHARED_SECRET = "the-one-secret-we-both-hold-and-keep-very-safe-indeed"


def issuer_sign(payload: dict) -> str:
    """The Issuer mints a token using the shared secret."""
    return jwt.encode(payload, SHARED_SECRET, algorithm="HS256")


def verifier_check(token: str, secret: str) -> dict:
    """The Verifier validates a token using the secret it holds."""
    return jwt.decode(token, secret, algorithms=["HS256"])


# --- Happy path: both sides hold the SAME secret -------------------------
token = issuer_sign({"order_id": 42})
print("Issuer produced token:")
print(token, "\n")

result = verifier_check(token, SHARED_SECRET)
print("Verifier (correct secret) accepted payload:", result, "\n")

# --- Failure path: a verifier with the WRONG secret ----------------------
# This proves verification truly depends on possessing the shared secret.
try:
    verifier_check(token, "an-attacker-guess-that-is-also-comfortably-long-but-wrong")
except InvalidSignatureError:
    print("Verifier (wrong secret) -> InvalidSignatureError, as expected.")

print()
print("Lesson: with HMAC, 'can verify' == 'can sign'. Guard the secret like")
print("a password and only share it with parties you fully trust.")

06 Secret Rotation HMAC06_secret_rotation_hmac.py ▾

06_secret_rotation_hmac.py — Rotating HMAC secrets without downtime.

Secrets should be rotated periodically. But you cannot flip every issuer and verifier to a new secret at the same instant — tokens signed with the OLD secret are still in flight and valid until they expire.

The classic pattern: keep a SHORT LIST of accepted secrets. Sign new tokens with the newest secret, but when verifying, try each candidate secret in turn until one validates. Once all old tokens have expired, drop the old secret.

This script demonstrates that fallback loop.

"""06_secret_rotation_hmac.py — Rotating HMAC secrets without downtime.

Secrets should be rotated periodically. But you cannot flip every issuer and
verifier to a new secret at the same instant — tokens signed with the OLD
secret are still in flight and valid until they expire.

The classic pattern: keep a SHORT LIST of accepted secrets. Sign new tokens
with the newest secret, but when verifying, try each candidate secret in turn
until one validates. Once all old tokens have expired, drop the old secret.

This script demonstrates that fallback loop.
"""

import jwt
from jwt.exceptions import InvalidSignatureError

# Newest secret first; we always SIGN with the first entry.
# Kept >=32 bytes each to satisfy HS256's recommended key length.
OLD_SECRET = "secret-v1-being-retired-but-still-accepted-for-now"
NEW_SECRET = "secret-v2-current-and-freshly-rotated-into-service"

# Ordered list of secrets a verifier will accept during the overlap window.
CANDIDATE_SECRETS = [NEW_SECRET, OLD_SECRET]


def verify_with_rotation(token: str, candidates: list[str]) -> dict:
    """Try each candidate secret until one verifies; else raise."""
    for index, secret in enumerate(candidates):
        try:
            decoded = jwt.decode(token, secret, algorithms=["HS256"])
            print(f"  -> verified with candidate #{index} ({secret!r})")
            return decoded
        except InvalidSignatureError:
            print(f"  -> candidate #{index} ({secret!r}) did not match, trying next")
    raise InvalidSignatureError("Token did not verify against any known secret")


# --- A token still signed with the OLD secret (in flight) ----------------
old_token = jwt.encode({"sub": "legacy-session"}, OLD_SECRET, algorithm="HS256")
print("Verifying a token signed with the OLD secret:")
print(verify_with_rotation(old_token, CANDIDATE_SECRETS), "\n")

# --- A freshly issued token signed with the NEW secret -------------------
new_token = jwt.encode({"sub": "fresh-session"}, NEW_SECRET, algorithm="HS256")
print("Verifying a token signed with the NEW secret:")
print(verify_with_rotation(new_token, CANDIDATE_SECRETS), "\n")

# --- A token signed with a secret we no longer accept --------------------
bogus_token = jwt.encode(
    {"sub": "evil"},
    "secret-we-never-knew-and-will-never-accept-at-all",
    algorithm="HS256",
)
print("Verifying a token signed with an UNKNOWN secret:")
try:
    verify_with_rotation(bogus_token, CANDIDATE_SECRETS)
except InvalidSignatureError as exc:
    print("  -> rejected:", exc)

print()
print("Rotation recipe: sign with newest, verify against [newest, ...older],")
print("then remove the oldest secret once its tokens can no longer be valid.")
terminal
