Module 01 · Foundations — What a JWT actually is

🧠 Mental Model — Behind the Scenes

A JWT looks like one opaque blob of gibberish, but it is really just three pieces of text glued together with dots: header.payload.signature. The first two pieces are nothing more than JSON dictionaries that have been run through base64url encoding — a reversible transport trick, not a lock. If you split the string on the dot and decode the chunks, the JSON pops right back out in plaintext. No key required. That single fact reorganizes everything: a JWT is a public postcard with a tamper-evident seal, not a sealed envelope.

The third piece — the signature — is where the cryptography lives. It is the raw output of an HMAC (for HS256) computed over the exact ASCII string base64url(header) + "." + base64url(payload). Notice what gets signed: the encoded bytes, not your original Python dict. That is why even a single flipped character in the payload produces a completely different signature. The signature doesn't hide anything; it binds the header and payload together so that any change is detectable by anyone holding the secret.

base64url itself is worth internalizing. Standard base64 uses +, /, and = — all awkward inside URLs and HTTP headers. base64url swaps +→-, /→_, and drops the = padding so a token can be dropped straight into a Authorization header or query string. The cost: when you decode by hand you must re-add the padding back to a multiple of four, which is exactly what the scripts here do with (-len(seg)) % 4.

The deepest lesson of this module is the distinction between integrity and confidentiality. The signature gives you integrity (was this changed?) and authenticity (was this signed by someone with the key?). It gives you zero confidentiality. Reading the payload requires no secret at all — so anything secret you place inside is effectively public.

🔍 A concrete analogy

Think of a JWT as a wax-sealed letter written in plain ink. Anyone who intercepts it can read every word — the seal doesn't hide the text. But the seal is pressed with a unique signet ring (the secret). If a meddler scratches out a word and rewrites it, the seal cracks and no longer matches. You can't read the seal to learn the message; you only check whether it's intact.

⚙️ What actually happens when you run the code

  1. jwt.encode({...}, SECRET, algorithm="HS256") serializes your dict to compact JSON, base64url-encodes the header and payload, joins them with a ., and computes the HMAC-SHA256 over that joined string.
  2. The HMAC digest is itself base64url-encoded and appended as the third segment, producing one str (PyJWT 2.x returns str, not bytes).
  3. The scripts call token.split(".") to recover the three segments as raw text.
  4. b64url_decode re-adds the stripped = padding, then base64.urlsafe_b64decode turns each segment back into JSON bytes — without any key.
  5. jwt.decode(token, ..., options={"verify_signature": False}) reads the same claims while explicitly skipping the integrity check.
  6. Tampering scripts mutate a byte in the payload segment, re-join the token, and call decode() with verification on — PyJWT recomputes the HMAC, finds a mismatch, and raises InvalidSignatureError.

👀 What to notice when you run the examples

  • In 02_base64url_decode.py, the header and payload print as readable JSON with no secret supplied — proof the payload is public.
  • In 05_jwt_is_signed_not_encrypted.py, a "secret" placed in the payload is recovered verbatim by anyone — the script is a live demonstration that JWTs are not encrypted.
  • In 06_tampering_breaks_signature.py, changing one character flips the verification from success to InvalidSignatureError — the seal cracks.
  • In 07_get_unverified_header.py, get_unverified_header() reads alg/kid before any key is chosen — useful for routing, never for trust.
  • The signature segment is shorter and more random-looking than header/payload because it encodes 32 raw HMAC bytes, not JSON.

⚠️ Common misconceptions

  • ❌ "JWTs are encrypted." False — they are signed. The payload is plain base64url JSON anyone can read.
  • ❌ "I need the secret to read the claims." False — decoding requires no key; only verifying the signature does.
  • ❌ "A successful unverified decode means the token is trustworthy." False — verify_signature: False and get_unverified_header return attacker-controllable data.
  • ❌ "base64url is the same as base64." False — different alphabet (-/_) and no = padding, so manual decoding needs the padding restored first.

🧱 Module 01 · Foundations — What a JWT actually is

Before you sign anything, encrypt anything, or wire up an auth flow, you need to understand what a JSON Web Token is at the byte level. This module strips a JWT down to its raw pieces and rebuilds your mental model from scratch.

🎯 What you'll learn

A signed JWT is deceptively simple: three base64url-encoded chunks joined by dots.

header . payload . signature
  • The header is a tiny JSON object saying how the token was signed.
  • The payload is JSON carrying claims (data about a user/session).
  • The signature is raw cryptographic bytes proving the first two parts weren't tampered with.

The single most important takeaway of this module: a JWT is signed, not encrypted. Anyone can read the payload — the signature only guarantees integrity, never confidentiality.

🔑 Key takeaways

  1. Three parts, always. A signed JWT is header.payload.signature. Splitting on . is the first thing every JWT library does.
  2. base64url, not base64. The -/_ alphabet and dropped = padding make tokens URL- and header-safe. You must re-add padding when decoding by hand.
  3. The payload is public. It's just encoded JSON. Decoding needs no key.
  4. The signature provides integrity. Change one byte → verification fails.
  5. Unverified reads are hints, not trust. verify_signature: False and get_unverified_header are for setting up verification (e.g. picking a key), never for authorization.

⚠️ Common pitfalls

  • ❌ "It's encrypted, so I'll store the user's password in it." No — anyone can read the payload. Never put secrets in a JWT.
  • ❌ Trusting an unverified decode. Reading claims without checking the signature gives you attacker-controlled data.
  • ❌ Forgetting = padding when decoding base64url manually → binascii errors. Pad to a multiple of 4 first.
  • ❌ Assuming decode() is optional about algorithms=. It's required in PyJWT 2.x; you'll see why in module 02.

02 Base64url Decode02_base64url_decode.py ▾

The header and payload of a JWT are JSON objects that have been encoded with base64url (RFC 4648 §5), NOT standard base64. This script decodes them manually — no PyJWT helpers — so you understand exactly what is happening.

Why base64url instead of standard base64? * Standard base64 uses '+' and '/' and '=' padding. * Those characters are unsafe/awkward inside URLs, HTTP headers, and cookies ('+' becomes a space, '/' is a path separator, '=' needs escaping). * base64url swaps '+' -> '-' and '/' -> '_' and DROPS the '=' padding, making the token safe to drop straight into a URL or header.

Because the '=' padding is removed, we must add it back before decoding.

"""
02 · base64url decoding by hand
===============================

The header and payload of a JWT are JSON objects that have been encoded with
**base64url** (RFC 4648 §5), NOT standard base64. This script decodes them
manually — no PyJWT helpers — so you understand exactly what is happening.

Why base64url instead of standard base64?
  * Standard base64 uses '+' and '/' and '=' padding.
  * Those characters are unsafe/awkward inside URLs, HTTP headers, and cookies
    ('+' becomes a space, '/' is a path separator, '=' needs escaping).
  * base64url swaps '+' -> '-' and '/' -> '_' and DROPS the '=' padding,
    making the token safe to drop straight into a URL or header.

Because the '=' padding is removed, we must add it back before decoding.
"""

import base64
import json

import jwt

# Build a token to dissect (self-contained; see module 02 for encode details).
SECRET = "a-32-byte-or-longer-demo-signing-secret!"
token = jwt.encode({"user": "alice", "scope": ["read", "write"]}, SECRET, algorithm="HS256")
header_segment, payload_segment, signature_segment = token.split(".")


def b64url_decode(segment: str) -> bytes:
    """Decode a base64url string, restoring the stripped '=' padding.

    base64 requires the input length to be a multiple of 4. JWT segments have
    their padding removed, so we re-add the right number of '=' characters.
    """
    # How many padding chars are missing? base64 works in blocks of 4.
    padding_needed = (-len(segment)) % 4
    segment_padded = segment + ("=" * padding_needed)
    # urlsafe_b64decode understands the '-' and '_' alphabet of base64url.
    return base64.urlsafe_b64decode(segment_padded)


print("=" * 60)
print("HEADER segment -> JSON")
print("=" * 60)
print(f"encoded : {header_segment}")
header_bytes = b64url_decode(header_segment)
print(f"raw json: {header_bytes.decode('utf-8')}")
print(f"as dict : {json.loads(header_bytes)}")
print()

print("=" * 60)
print("PAYLOAD segment -> JSON")
print("=" * 60)
print(f"encoded : {payload_segment}")
payload_bytes = b64url_decode(payload_segment)
print(f"raw json: {payload_bytes.decode('utf-8')}")
print(f"as dict : {json.loads(payload_bytes)}")
print()

print("=" * 60)
print("WHY base64url (and not base64)?")
print("=" * 60)
print("base64url replaces '+' -> '-', '/' -> '_', and removes '=' padding,")
print("so the token is safe inside URLs, HTTP headers, and cookies.")
print("We re-added the missing '=' padding before decoding above.")

Now that we can decode the segments, let's clearly separate the THREE roles:

  • HEADER — a small JSON object describing HOW the token is signed (e.g. {"alg": "HS256", "typ": "JWT"}).
  • PAYLOAD — a JSON object of "claims" (the actual data).
  • SIGNATURE — NOT JSON. It is raw cryptographic bytes computed over header.payload. Trying to read it as JSON is meaningless.

This script pretty-prints the header and payload dicts, and proves the signature is binary, not text/JSON.

"""
03 · Header vs Payload vs Signature
===================================

Now that we can decode the segments, let's clearly separate the THREE roles:

  * HEADER    — a small JSON object describing HOW the token is signed
                (e.g. {"alg": "HS256", "typ": "JWT"}).

print("=" * 60)

04 Decode Without Verification04_decode_without_verification.py ▾

PyJWT can decode the claims of a token without checking the signature and without a key if you pass options={"verify_signature": False}.

This is genuinely useful in a few narrow cases (e.g. reading the kid or iss to decide WHICH key to fetch before doing a real verification).

But it is also DANGEROUS if misused: the claims are completely untrusted. Anyone could have forged or altered them. Never make a security decision based on an unverified token.

05 JWT Is Signed Not Encrypted05_jwt_is_signed_not_encrypted.py ▾

The single most common JWT misconception: "the token is encrypted, so I can put secrets in it." FALSE.

A standard signed JWT (JWS) is: * INTEGRITY-protected — the signature proves it wasn't altered. * NOT confidential — the payload is just base64url-encoded JSON that ANYONE can read without any key.

This script proves it: we read the payload of a token using nothing but base64 decoding — no secret, no library verification.

LESSON: Never put passwords, API keys, credit-card numbers, or any secret in a JWT payload. Assume the whole world can read it.

"""
05 · A JWT is SIGNED, not ENCRYPTED
===================================

The single most common JWT misconception: "the token is encrypted, so I can
put secrets in it." FALSE.

A standard signed JWT (JWS) is:
  * INTEGRITY-protected — the signature proves it wasn't altered.
  * NOT confidential    — the payload is just base64url-encoded JSON that
                          ANYONE can read without any key.

This script proves it: we read the payload of a token using nothing but
base64 decoding — no secret, no library verification.

LESSON: Never put passwords, API keys, credit-card numbers, or any secret in a
JWT payload. Assume the whole world can read it.
"""

import base64
import json

import jwt

"""
06 · Tampering breaks the signature
===================================

The whole point of the signature is INTEGRITY: if even a single byte of the
header or payload changes, verification must fail.

This script demonstrates an attack and its defeat:
  1. Issue a legit token for a normal user (role='user').
  2. Decode the payload, change role -> 'admin' (privilege escalation attempt).
  3. Re-encode the modified payload and reassemble a forged token, reusing the
     ORIGINAL signature (the attacker doesn't know the secret, so they can't
     compute a new valid signature).
  4. Verify the forged token with the real secret -> InvalidSignatureError.
"""

import base64
import json

import jwt
from jwt.exceptions import InvalidSignatureError

SECRET = "server-side-secret-attacker-does-not-know"

# --- Step 1: a legitimate, low-privilege token -------------------------------
token = jwt.encode({"user": "mallory", "role": "user"}, SECRET, algorithm="HS256")
header_seg, payload_seg, signature_seg = token.split(".")
print("Original token (role=user):")
print(token)
print()


def b64url_decode(segment: str) -> bytes:
    return base64.urlsafe_b64decode(segment + "=" * ((-len(segment)) % 4))


def b64url_encode(raw: bytes) -> str:
    # base64url with the '=' padding stripped, exactly like JWT segments.
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode("ascii")


# --- Step 2: attacker edits the payload --------------------------------------
payload = json.loads(b64url_decode(payload_seg))
print(f"Decoded payload: {payload}")
payload["role"] = "admin"  # privilege escalation attempt!
print(f"Tampered payload: {payload}")
print()

# --- Step 3: reassemble a forged token (old signature reused) ----------------
# json.dumps with compact separators to mimic the original encoding style.
forged_payload_seg = b64url_encode(
    json.dumps(payload, separators=(",", ":")).encode("utf-8")
)
forged_token = f"{header_seg}.{forged_payload_seg}.{signature_seg}"
print("Forged token (role=admin, but signature is now stale):")
print(forged_token)
print()

# --- Step 4: verification fails ----------------------------------------------
print("=" * 60)
print("VERIFYING THE FORGED TOKEN WITH THE REAL SECRET")
print("=" * 60)
try:
    jwt.decode(forged_token, SECRET, algorithms=["HS256"])
    print("BUG: forged token was accepted (should never happen)!")
except InvalidSignatureError:
    print("InvalidSignatureError raised — tampering DETECTED and rejected. ✅")
    print()
    print("The signature was computed over the ORIGINAL header.payload. Because")
    print("the payload changed and the attacker can't recompute a valid MAC")
    print("without the secret, verification fails. Integrity wins.")

07 Get Unverified Header07_get_unverified_header.py ▾

Sometimes you need to look at the JOSE header BEFORE you can verify the token — most importantly to read: * 'alg' — which algorithm was used (so you know how to verify), and * 'kid' — the Key ID, telling you WHICH public key to fetch from a JWKS.

PyJWT exposes jwt.get_unverified_header(token) for exactly this. It only parses the header segment; it does NOT verify the signature.

As always: anything "unverified" is a HINT used to set up verification, never a trust decision by itself.

"""
08 · Full encode -> decode round trip (HS256)
=============================================

Putting it all together: the simplest complete life cycle of a JWT.

  ENCODE:  dict of claims  + secret + algorithm  ->  compact token string
  DECODE:  token string    + secret + algorithms ->  dict of claims back

This script prints each stage so you can watch the data transform and return
unchanged, proving the round trip is lossless when the secret matches.
"""

import jwt

SECRET = "round-trip-secret-at-least-32-bytes-long"

# --- Stage 1: the claims we want to put in the token -------------------------
original_claims = {"user": "alice", "role": "admin", "count": 3}
print("=" * 60)
print("STAGE 1 — original claims (a plain Python dict)")
print("=" * 60)
print(original_claims)
print()

# --- Stage 2: encode -> a compact token string -------------------------------
# In PyJWT 2.x, encode() returns a `str` (not bytes). algorithm= is singular.
token = jwt.encode(original_claims, SECRET, algorithm="HS256")
print("=" * 60)
print("STAGE 2 — encoded token (str)")
print("=" * 60)
print(f"type  : {type(token).__name__}")
print(f"value : {token}")
print()

# --- Stage 3: decode -> claims dict back -------------------------------------
# On decode, algorithms= is a REQUIRED list naming the algorithm(s) you accept.
decoded_claims = jwt.decode(token, SECRET, algorithms=["HS256"])
print("=" * 60)
print("STAGE 3 — decoded claims (back to a dict)")
print("=" * 60)
print(f"type  : {type(decoded_claims).__name__}")
print(f"value : {decoded_claims}")
print()

# --- Stage 4: confirm the round trip is lossless -----------------------------
print("=" * 60)
print("STAGE 4 — round-trip check")
print("=" * 60)
print(f"original == decoded ? {original_claims == decoded_claims}")
print()
print("That's the core loop you'll use everywhere: encode to hand a token out,")
print("decode (with the same secret + pinned algorithm) to read it back safely.")
