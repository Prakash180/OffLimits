Module 04 · Custom Claims & Validation Options

🧠 Mental Model — Behind the Scenes

A JWT payload is open-ended JSON, so beyond the seven registered names you can add any private claim your app needs — roles, tenant, email, feature flags. PyJWT treats them as opaque data: it signs them like everything else, but it has no opinion about their meaning. That means reading them is trivial (decoded["roles"]), and trusting them is entirely a function of whether you verified the signature first. The whole module orbits one idea: the signature decides trust; the claims decide policy, and you must never blur the two.

The real subject here is decode()'s control surface — the options, require, and leeway knobs. By default PyJWT is strict in the ways that matter: it verifies the signature, and it enforces exp when present. Each knob relaxes or tightens one specific guardrail. options={"verify_signature": False} turns decoding into a pure base64url read — fast for inspection, but the returned claims are attacker-controllable and must never drive authorization. Critically, disabling signature verification also disables the dependent claim checks, because there's nothing trustworthy left to check.

require=[...] is about presence, not value: it forces certain claims to exist, raising MissingRequiredClaimError if not. Think of it as a schema gate — "every token must carry exp, iss, sub" — that runs before your value-level logic. It pairs naturally with the value checks (issuer=, audience=) from Module 03: require ensures the claim is there, those parameters check it's correct.

leeway exists because clocks drift. Two servers rarely agree to the millisecond, so a token that expired "one second ago" by your clock may be perfectly fresh by the issuer's. leeway=timedelta(seconds=10) widens the exp/nbf/iat boundaries by that grace window — PyJWT effectively compares against exp + leeway. The danger is obvious once you see it: every second of leeway is a second of extra replay window past expiry, so it should be seconds, never minutes.

🔍 A concrete analogy

Picture a nightclub door. The bouncer first checks the wristband is genuine (signature) — fake band, you're out, no further questions. require is the rule "everyone must show ID and a ticket" — missing either and you're turned away before they even read them. The value checks are reading the ID's name against the guest list. And leeway is the bouncer letting in someone whose ticket says "valid until 11:00" at 11:00:08 because the club clock and the ticket printer disagree by a few seconds — generous by seconds, never by an hour.

⚙️ What actually happens when you run the code

  1. jwt.encode() packs registered and custom claims into one signed payload — PyJWT doesn't distinguish them while signing.
  2. A normal jwt.decode(token, secret, algorithms=[...]) verifies the signature, enforces exp, then returns the full claims dict including your custom keys.
  3. With options={"require": ["exp", "iss", "sub"]}, PyJWT checks each listed claim exists before value checks; a gap raises MissingRequiredClaimError.
  4. With leeway=timedelta(seconds=N), the exp/nbf comparisons are widened by N seconds, so a just-expired token can still pass.
  5. With options={"verify_signature": False}, PyJWT skips the HMAC check (and the dependent exp/aud checks) and simply base64url-decodes the payload — untrusted.
  6. Your code then reads custom claims (e.g. roles) and makes the authorization decision — which is only sound if step 2's signature check actually ran.

👀 What to notice when you run the examples

  • In 01_custom_claims.py, custom keys come back exactly as inserted — they're just JSON the signature protects.
  • In 02_options_verify_signature.py, the claims still decode with verification off, underscoring that an unverified read is data, not trust.
  • In 05_require_claims.py, removing a required claim raises MissingRequiredClaimError before any value comparison — presence is checked first.
  • In 06_leeway.py, a token that fails without leeway passes with a small leeway at the exp boundary — clock-skew tolerance made visible.
  • In 08_role_based_access_demo.py, authorize() grants or denies based on the roles claim — but only meaningfully because the token was verified first.

⚠️ Common misconceptions

  • ❌ "I can authorize on claims I read with verify_signature: False." False — those claims are attacker-controlled; never authorize on them.
  • ❌ "require checks the claim's value." False — it only checks presence; value checks (issuer=, audience=) are separate.
  • ❌ "More leeway is safer." Backwards — leeway extends the validity window past exp, widening the replay window. Keep it to seconds.
  • ❌ "Custom claims are private/hidden." False — the payload is base64url-encoded plaintext; anyone can read your roles/email. Never store secrets there.

🧩 Module 04 · Custom Claims & Validation Options

Registered claims (Module 03) are the shared vocabulary. Custom claims are where your application data lives — roles, tenant, email, feature flags. And jwt.decode()'s options=, require=, and leeway= knobs let you decide exactly how strict verification should be.

🧠 The big idea

A JWT payload is open-ended JSON. You can add any private claim your app needs. The flip side is control: PyJWT applies sensible defaults, but you can tighten verification (demand certain claims) or — carefully — loosen it (skip a check). Knowing which knob does what, and the risk of each, is the heart of safe token handling.

The decode() control surface

Knob Purpose Default
options={"verify_signature": False} Read claims without trust signature is verified
options={"verify_exp": False} Accept expired tokens exp is enforced
options={"verify_aud": False} Skip audience check aud checked when audience= given
options={"require": [...]} Demand claims be present nothing required
leeway=timedelta(...) Grace window for clock skew 0

🌊 Choosing how strict to be

flowchart TD A[Need to read a token] --> B{Do you trust the source?} B -- "No / debugging" --> C[verify_signature False<br/>read-only, never authorize] B -- Yes --> D[Verify signature] D --> E{Enforce presence?} E -- yes --> F["options require: exp, iss, sub"] E -- no --> G[Skip] F --> H{Clocks may drift?} G --> H H -- yes --> I[Add small leeway] H -- no --> J[Decode strictly] I --> K[Read custom claims -> authorize] J --> K

✅ Key takeaways

  • Custom claims are just JSON. Read them with decoded["key"] or decoded.get("key", default).
  • verify_signature: False = untrusted. Great for inspection, never for authorization decisions.
  • Disabling checks shifts risk to you. verify_exp: False and verify_aud: False remove guardrails — justify every use.
  • require enforces presence; value checks come after. Use it to mandate exp/iss/sub.
  • leeway should be small. Seconds of grace for clock skew, not minutes.
  • Namespace custom claims (URL-style) to avoid collisions, as OIDC does.

⚠️ Pitfalls

  • 🕳️ Authorizing on unverified data. If you decoded with verify_signature: False, the roles you read are attacker-controlled.
  • 🕳️ Leaving verify_exp: False in production. Expired/stolen tokens never die.
  • 🕳️ Skipping aud by habit. Invites audience-confusion attacks across services.
  • 🕳️ Over-wide leeway. A 5-minute leeway is a 5-minute replay window past expiry.
  • 🕳️ Putting secrets in claims. The payload is only base64url-encoded — anyone can read it. Never store passwords or PII you wouldn't log.

"""

import jwt

SECRET = "super-secret-shared-key-please-change-me"


def main() -> None:
    token = jwt.encode({"sub": "user-123", "roles": ["admin"]}, SECRET, algorithm="HS256")

    # --- Read claims WITHOUT verifying the signature ---------------------
    # No key is required; PyJWT just base64url-decodes the payload.
    unsafe = jwt.decode(
        token,
        options={"verify_signature": False},
        algorithms=["HS256"],
    )
    print("[UNVERIFIED] Claims read without checking the signature:")
    print("    ", unsafe)
    print("    ⚠️ Treat this data as untrusted — do NOT authorize on it.")

    # --- Proof that tampering is undetectable in this mode ---------------
    # Splice the (untrusted) header+payload of a token with a bogus signature.
    header_b64, payload_b64, _ = token.split(".")
    forged = f"{header_b64}.{payload_b64}.not-a-real-signature"
    still_reads = jwt.decode(forged, options={"verify_signature": False}, algorithms=["HS256"])
    print("\n[UNVERIFIED] Even a token with a garbage signature decodes:")
    print("    ", still_reads)

    # --- The safe path, for contrast -------------------------------------
    verified = jwt.decode(token, SECRET, algorithms=["HS256"])
    print("\n[VERIFIED] With the secret, the signature is checked:")
    print("    ", verified)


if __name__ == "__main__":
    main()

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"


def main() -> None:
    now = datetime.now(UTC)

    # A token that expired an hour ago.
    expired = jwt.encode(
        {"sub": "user-123", "exp": now - timedelta(hours=1)},
        SECRET,
        algorithm="HS256",
    )

    # --- Default behaviour: rejected -------------------------------------
    try:
        jwt.decode(expired, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError as exc:
        print("[DEFAULT] Expired token rejected:", exc)

    # --- Opt out of the expiry check (signature STILL verified) ----------
    decoded = jwt.decode(
        expired,
        SECRET,
        algorithms=["HS256"],
        options={"verify_exp": False},
    )
    print("\n[verify_exp=False] Accepted the expired token:")
    print("    ", decoded)
    print("    ⚠️ Signature was still checked, but the deadline was ignored.")

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"
REQUIRED = ["exp", "iss", "sub"]


def main() -> None:
    now = datetime.now(UTC)

    # --- A complete token satisfies the requirement ----------------------
    complete = jwt.encode(
        {
            "iss": "https://auth.example.com",
            "sub": "user-123",
            "exp": now + timedelta(minutes=10),
        },
        SECRET,
        algorithm="HS256",
    )
    decoded = jwt.decode(
        complete,
        SECRET,
        algorithms=["HS256"],
        options={"require": REQUIRED},
    )
    print("[OK] All required claims present:", sorted(decoded.keys()))

    # --- A token missing `iss` is rejected -------------------------------
    missing_iss = jwt.encode(
        {"sub": "user-123", "exp": now + timedelta(minutes=10)},
        SECRET,
        algorithm="HS256",
    )
    try:
        jwt.decode(
            missing_iss,
            SECRET,
            algorithms=["HS256"],
            options={"require": REQUIRED},
        )
    except jwt.MissingRequiredClaimError as exc:
        print("\n[EXPECTED FAILURE] MissingRequiredClaimError:")
        print("    ", exc)
        print("    `require` guarantees presence; value checks come after.")


if __name__ == "__main__":
    main()

06 Leeway06_leeway.py ▾

06 · leeway — tolerating small clock differences.

Servers' clocks are never perfectly in sync. A token that expired "0.5 seconds ago" according to your clock may still be valid by the issuer's. leeway gives time-based checks (exp, nbf, iat) a grace window so honest tokens near a boundary aren't rejected over millisecond skew.

You can pass leeway as a number of seconds or as a :class:datetime.timedelta.

⚠️ Keep leeway small (seconds, not minutes). It widens the window in which an expired token is still accepted.

"""06 · leeway — tolerating small clock differences.

Servers' clocks are never perfectly in sync. A token that expired "0.5 seconds

gives time-based checks (`exp`, `nbf`, `iat`) a grace window so honest tokens

Run me:
    .venv/bin/python pyjwt-course/04-custom-claims-and-validation/06_leeway.py
"""

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"


def main() -> None:
    now = datetime.now(UTC)

    # Expired 10 seconds ago — just over the edge.
    just_expired = jwt.encode(
        {"sub": "user-123", "exp": now - timedelta(seconds=10)},
        SECRET,
        algorithm="HS256",
    )

    # --- Without leeway: rejected ----------------------------------------
    try:
        jwt.decode(just_expired, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError as exc:
        print("[NO LEEWAY] Rejected (expired 10s ago):", exc)

    # --- With 30s leeway: accepted ---------------------------------------
    decoded = jwt.decode(
        just_expired,
        SECRET,
        algorithms=["HS256"],
        leeway=timedelta(seconds=30),
    )
    print("\n[leeway=30s] Accepted despite being 10s past exp:")
    print("    ", decoded)

    # --- But leeway is finite: 40s past exp with 30s leeway still fails ---
    more_expired = jwt.encode(
        {"sub": "user-123", "exp": now - timedelta(seconds=40)},
        SECRET,
        algorithm="HS256",
    )
    try:
        jwt.decode(more_expired, SECRET, algorithms=["HS256"], leeway=timedelta(seconds=30))
    except jwt.ExpiredSignatureError as exc:
        print("\n[leeway=30s] Still rejected when 40s past exp:", exc)


if __name__ == "__main__":
    main()

07 Nested And Namespaced Claims07_nested_and_namespaced_claims.py ▾

07 · Nested and namespaced custom claims.

Two patterns you'll meet in real tokens:

  1. Nested objects — group related data under one key, e.g. a context object holding tenant + device info. The value is just nested JSON.

  2. Namespaced / URL-style keys — to avoid collisions, identity providers prefix custom claims with a URI, e.g. "https://example.com/roles". OIDC and Auth0 use exactly this style. The key is an ordinary string; the URL has no network meaning here.

Both decode back as plain Python dict entries.

"""08 · Role-Based Access Control (RBAC) demo with JWT claims.

This ties the module together: tokens carry a `roles` custom claim, and a tiny
``authorize()`` helper enforces that a caller holds a required role before an
action runs.

The flow mirrors a real API gateway:
    1. Verify the token's signature (and any registered claims).
    2. Read the `roles` claim from the trusted payload.
    3. Allow or deny based on the required role for the operation.

Run me:
    .venv/bin/python pyjwt-course/04-custom-claims-and-validation/08_role_based_access_demo.py
"""

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"
ISSUER = "https://auth.example.com"
AUDIENCE = "https://api.example.com"


def issue_token(user_id: str, roles: list[str]) -> str:
    """Mint a signed token for a user carrying their roles."""
    now = datetime.now(UTC)
    return jwt.encode(
        {
            "iss": ISSUER,
            "aud": AUDIENCE,
            "sub": user_id,
            "iat": now,
            "exp": now + timedelta(minutes=15),
            "roles": roles,
        },
        SECRET,
        algorithm="HS256",
    )


class AccessDenied(Exception):
    """Raised when a verified token lacks the required role."""


def authorize(token: str, required_role: str) -> dict:
    """Verify a token and ensure it grants `required_role`.

    Returns the decoded payload on success; raises on failure.
    """
    # Step 1: fully verify the token (signature + iss/aud + exp).
    payload = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],
        issuer=ISSUER,
        audience=AUDIENCE,
    )
    # Step 2: read roles from the *trusted* payload.
    roles = payload.get("roles", [])
    # Step 3: enforce the requirement.
    if required_role not in roles:
        raise AccessDenied(
            f"user {payload['sub']} has roles {roles}; '{required_role}' required"
        )
    return payload


def attempt(token: str, required_role: str, label: str) -> None:
    """Try an authorized action and print the outcome."""
    try:
        payload = authorize(token, required_role)
        print(f"[ALLOW] {label}: {payload['sub']} has '{required_role}'.")
    except AccessDenied as exc:
        print(f"[DENY]  {label}: {exc}")
    except jwt.InvalidTokenError as exc:
        print(f"[DENY]  {label}: invalid token ({exc}).")


def main() -> None:
    admin_token = issue_token("alice", ["admin", "editor"])
    editor_token = issue_token("bob", ["editor"])

    print("Required role for deleting a record: 'admin'\n")
    attempt(admin_token, "admin", "alice deletes record")   # allowed
    attempt(editor_token, "admin", "bob deletes record")    # denied

    print("\nRequired role for editing a record: 'editor'\n")
    attempt(admin_token, "editor", "alice edits record")    # allowed (has editor)
    attempt(editor_token, "editor", "bob edits record")     # allowed


if __name__ == "__main__":
    main()
