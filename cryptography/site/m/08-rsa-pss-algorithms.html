Module 08 · RSA-PSS Algorithms (PS256 / PS384 / PS512)

🧠 Mental Model — Behind the Scenes

RSA-PSS uses the exact same RSA key pair and the same trapdoor as Module 06 — the only thing that changes is the padding applied to the hash before the private-key transform. Where RS* uses the rigid, deterministic PKCS#1 v1.5 template, PS* uses RSASSA-PSS (Probabilistic Signature Scheme). PSS folds in a freshly generated random salt on every signature, runs it through a mask-generation function (MGF1) to spread the bits across the whole padded block, and only then applies the trapdoor. That single design choice has a stronger, cleaner security proof — which is why PSS is the recommended padding for new RSA signatures.

The headline behavioural consequence is that PSS is probabilistic. Sign the identical payload twice with the identical key and you get two different tokens, because each one carries a different random salt baked into its signature. This feels alarming the first time you see it, but both tokens verify perfectly — the salt is recovered and checked as part of verification. Contrast this with RS256, which is deterministic: same input, byte-for-byte identical token every time.

Because only the padding differs, one RSA-2048 key pair serves every variant: RS256/384/512 and PS256/384/512, all three hash sizes, from the same key. The hash is independent of the key size (unlike ECDSA, where the algorithm fixes the curve). But the algorithm string is still a hard security boundary at verification time: a PS256 token will not validate if your verifier only allows ["RS256"], even with the correct key — PyJWT raises InvalidAlgorithmError. The padding scheme is part of the contract, so you must pin the exact algorithms you expect.

flowchart LR K[One RSA-2048 keypair] --> H[SHA-256 digest of header.payload] H --> S[Add fresh random salt] S --> M[MGF1 mask -> PSS-encoded block] M --> T[Private-key trapdoor] T --> Sig[Signature - differs every run] Sig --> V[Public key verifies and recovers salt]

🔍 A concrete analogy

It's like signing a contract with invisible-ink confetti sprinkled on top each time. The signature underneath is yours, but the random sparkle pattern is different on every copy. A verifier holding your reference card can still confirm the signature is genuine and that the confetti was applied correctly — yet no two signed copies ever look identical, which makes certain forgery and replay tricks far harder.

⚙️ What actually happens when you run the code

  1. rsa.generate_private_key(...) creates one ordinary RSA-2048 key pair — nothing PSS-specific yet.
  2. jwt.encode(payload, private_pem, algorithm="PS256") SHA-256-hashes the signing input.
  3. PSS generates a random salt, runs MGF1 to build the padded block, and applies the private-key trapdoor — producing signature A.
  4. Calling jwt.encode again with the same payload draws a new salt, producing signature B ≠ A.
  5. jwt.decode(..., algorithms=["PS256"]) uses the public key to undo the trapdoor, recovers the salt, and confirms the PSS encoding is valid for the recomputed digest.
  6. Both A and B verify; the same key also produces valid RS256 tokens, which are identical run-to-run.

👀 What to notice when you run the examples

  • In 03_pss_is_probabilistic.py, two PS256 calls print "Tokens identical? False" while two RS256 calls print "True" — the probabilistic-vs-deterministic split, live.
  • Both differing PS256 tokens still pass jwt.decode — randomness is a feature, not corruption.
  • In 05_same_key_both_schemes.py, the same key signs both PS256 and RS256; mixing them at verify time raises InvalidAlgorithmError.
  • In 02_ps384_ps512.py, one RSA key yields PS384 and PS512 — the hash is free to vary without touching the key.

⚠️ Common misconceptions

  • "PS* needs a special RSA key." No — it's the same key as RS*. Only the padding inside the signature differs.
  • "A changing token means something is broken." PSS intends to change every time. Don't cache or deduplicate by token string.
  • "If the key matches, any RSA algorithm verifies." The algorithms=[...] whitelist is enforced; PS256 ≠ RS256 even with one key.
  • "Probabilistic means less reliable." The randomness strengthens the security proof; verification remains deterministic and exact.

🔵 Module 08 · RSA-PSS Algorithms (PS256 / PS384 / PS512)

Same RSA keys you already know — but with modern, probabilistic padding. Meet the PS* family: the cryptographically preferred way to do RSA signatures in JWTs.

🧠 PSS vs PKCS#1 v1.5 — the one idea that matters

RSA signing has two padding schemes, and the JWT algorithm name tells you which one is in play:

Family Padding scheme Behaviour Status
RS256/384/512 PKCS#1 v1.5 (1993) Deterministic Legacy, ubiquitous
PS256/384/512 RSASSA-PSS Probabilistic (random salt) Modern, recommended

Both use the same RSA keypair. The only difference is the encoding/padding step inside the signature. PSS has a stronger security proof and injects a random salt on every signature, which is why it's the recommendation for new systems.

flowchart TD K[One RSA-2048 keypair] --> R[RS* · PKCS#1 v1.5] K --> P[PS* · RSASSA-PSS] R --> RD[Deterministic: same input → same token] P --> PD[Probabilistic: same input → different token each time] RD --> V[Both verify with the public key] PD --> V
Algorithm Padding Hash Min key
PS256 RSASSA-PSS SHA-256 RSA-2048
PS384 RSASSA-PSS SHA-384 RSA-2048
PS512 RSASSA-PSS SHA-512 RSA-2048

🔁 Unlike ECDSA, the hash is independent of the key size — one RSA key can produce PS256, PS384 and PS512 signatures.

🔬 The probabilistic demo (script 03)

Sign the identical payload twice:

PS256 → token A ≠ token B   (random salt each time)
RS256 → token A = token B   (deterministic)

Both PS256 tokens still verify perfectly. The randomness is a feature, not corruption — it's what makes PSS provably secure.

⚠️ Pitfalls

  • The verifier's algorithms=[...] is a security boundary. A PS256 token will not verify if you only allow ["RS256"] — even with the same key — raising InvalidAlgorithmError (script 05). Pin the algorithms you expect.
  • Don't assume tokens are stable. If you cache or deduplicate by token string, remember PS* tokens change every signing call.
  • RSA-2048 is the floor. Use 2048-bit minimum; 3072-bit for higher assurance.
  • PS ⊄ RS interop. Older verifiers may not understand PSS — keep RS256 for legacy interoperability, choose PS* for new designs.

🔑 Key takeaways

  • PS* = RSA + RSASSA-PSS padding; RS* = RSA + PKCS#1 v1.5 padding.
  • PSS is probabilistic (random salt) → identical inputs yield different tokens; PKCS#1 v1.5 is deterministic.
  • The same RSA keypair works for both families and all three hash sizes.
  • Prefer PS256/384/512 for new systems; keep RS* only for compatibility.

"""
08 · RSA-PSS · 01 — Signing & verifying with PS256
==================================================

The **PS** family (PS256, PS384, PS512) is RSA signing using the modern
**RSASSA-PSS** padding scheme ("Probabilistic Signature Scheme").

    PS256 = RSA + PSS padding + SHA-256

It uses the *same* RSA keypair you'd use for RS256 — the only difference is the
padding/encoding step inside the signature. PSS is the cryptographically
preferred padding for new systems (RS* uses the older PKCS#1 v1.5 padding).

This script generates a fresh RSA-2048 keypair and does a PS256 round-trip.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def main() -> None:
    # RSA-2048 is the practical minimum modern size. PSS works with any RSA key.
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "alice", "scheme": "RSASSA-PSS"}

    # SIGN with the private key using PS256.
    token = jwt.encode(payload, private_pem, algorithm="PS256")
    print("=" * 70)
    print("PS256 token (RSA + PSS padding + SHA-256):")
    print(token)
    print("=" * 70)

    print("\nJOSE header:", jwt.get_unverified_header(token))  # alg == 'PS256'

    # VERIFY with the public key.
    decoded = jwt.decode(token, public_pem, algorithms=["PS256"])
    print("Verified payload:", decoded)


if __name__ == "__main__":
    main()

Just like PS256, the larger PSS variants pair RSA + PSS padding with a bigger SHA-2 hash:

PS384 = RSA + PSS + SHA-384
PS512 = RSA + PSS + SHA-512

Crucially — unlike ECDSA, where the algorithm dictates the curve — the RSA key size is independent of the hash. The same RSA-2048 key can produce PS256, PS384, and PS512 signatures. You pick the hash strength via the algorithm string; the key stays the same.

"""
08 · RSA-PSS · 02 — PS384 and PS512
===================================

Just like PS256, the larger PSS variants pair RSA + PSS padding with a bigger
SHA-2 hash:

    PS384 = RSA + PSS + SHA-384
    PS512 = RSA + PSS + SHA-512

Crucially — unlike ECDSA, where the algorithm dictates the curve — **the RSA
key size is independent of the hash**. The *same* RSA-2048 key can produce
PS256, PS384, and PS512 signatures. You pick the hash strength via the
algorithm string; the key stays the same.

This script signs the same payload with both PS384 and PS512 using one key.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def main() -> None:
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "bob"}

    for alg in ("PS384", "PS512"):
        token = jwt.encode(payload, private_pem, algorithm=alg)
        header = jwt.get_unverified_header(token)
        decoded = jwt.decode(token, public_pem, algorithms=[alg])

        print("=" * 70)
        print(f"{alg}  (same RSA-2048 key, hash = SHA-{alg[2:]})")
        print("=" * 70)
        print("Header  :", header)
        print("Token   :", token)
        print("Verified:", decoded)
        print()

    print("One key, three hash strengths — the RSA key size is independent")
    print("of the chosen SHA-2 variant.")


if __name__ == "__main__":
    main()

"""
08 · RSA-PSS · 03 — PSS is PROBABILISTIC (RS is deterministic)
==============================================================

This is the defining behavioural difference between the two RSA schemes:

    PS256 (RSASSA-PSS)        -> randomised: signing injects a random *salt*,
                                  so signing the SAME payload twice yields TWO
                                  DIFFERENT tokens.

    RS256 (RSASSA-PKCS1-v1.5) -> deterministic: signing the SAME payload twice
                                  with the SAME key yields the SAME token,
                                  byte-for-byte.

Both are perfectly valid and both verify correctly. The randomness in PSS is a
security feature (it strengthens the proof of security and resists certain
attacks), not a bug.

We sign the identical payload twice with each scheme and compare.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def main() -> None:
    # One key used for everything below.
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "carol", "msg": "sign me twice"}

    # --- PS256: expect TWO DIFFERENT tokens ---
    ps_a = jwt.encode(payload, private_pem, algorithm="PS256")
    ps_b = jwt.encode(payload, private_pem, algorithm="PS256")

    print("=" * 70)
    print("PS256 — sign identical payload twice")
    print("=" * 70)
    print("token A:", ps_a)
    print("token B:", ps_b)
    print("Tokens identical? ", ps_a == ps_b, " <- expect False (random salt)")
    # Both still verify just fine:
    jwt.decode(ps_a, public_pem, algorithms=["PS256"])
    jwt.decode(ps_b, public_pem, algorithms=["PS256"])
    print("Both PS256 tokens verify correctly. ✔")

    # --- RS256: expect TWO IDENTICAL tokens ---
    rs_a = jwt.encode(payload, private_pem, algorithm="RS256")
    rs_b = jwt.encode(payload, private_pem, algorithm="RS256")

    print("\n" + "=" * 70)
    print("RS256 — sign identical payload twice")
    print("=" * 70)
    print("token A:", rs_a)
    print("token B:", rs_b)
    print("Tokens identical? ", rs_a == rs_b, " <- expect True (deterministic)")
    print("\nSummary: PSS adds per-signature randomness; PKCS#1 v1.5 does not.")


if __name__ == "__main__":
    main()

"""
08 · RSA-PSS · 04 — PSS vs PKCS#1 v1.5  (PS* vs RS*)
===================================================

Two padding schemes, one RSA key. Which should you choose?

  ┌─────────────┬──────────────────────────┬─────────────────────────────┐
  │             │ RS*  (PKCS#1 v1.5)        │ PS*  (RSASSA-PSS)           │
  ├─────────────┼──────────────────────────┼─────────────────────────────┤
  │ Padding     │ PKCS#1 v1.5 (1993)        │ PSS (provably secure)        │
  │ Randomness  │ Deterministic             │ Probabilistic (random salt)  │
  │ Status      │ Legacy, still widely used │ Modern, recommended for new  │
  │ Security    │ Adequate, older proofs    │ Stronger security reduction  │
  │ Same key?   │ ────────  yes, both schemes share one RSA keypair  ──── │
  └─────────────┴──────────────────────────┴─────────────────────────────┘

Guidance: for NEW systems prefer **PS256/PS384/PS512**. Keep **RS256** when you
must interoperate with older verifiers that don't understand PSS (still the
default in much of the OAuth/OIDC ecosystem).

This script signs one payload with RS256 and PS256 using the SAME key and
verifies both.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def main() -> None:
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "dave"}

    rs = jwt.encode(payload, private_pem, algorithm="RS256")
    ps = jwt.encode(payload, private_pem, algorithm="PS256")

    print("RS256 (PKCS#1 v1.5, deterministic, legacy):")
    print("  ", rs)
    print("   verified ->", jwt.decode(rs, public_pem, algorithms=["RS256"]))

    print("\nPS256 (RSASSA-PSS, randomised, modern):")
    print("  ", ps)
    print("   verified ->", jwt.decode(ps, public_pem, algorithms=["PS256"]))

    print("\nSame RSA key, two padding schemes. Prefer PS* for new designs.")


if __name__ == "__main__":
    main()

We established that a single RSA keypair can sign with both RS256 and PS256. But the verifier must whitelist the correct algorithm. A token signed with PS256 will NOT verify if you tell PyJWT to expect only RS256 — even though the exact same key pair is involved — because the padding differs.

This protects you: the algorithms=[...] allow-list on jwt.decode() is a security control. Never set it to a permissive catch-all.

"""
08 · RSA-PSS · 05 — One RSA key, both schemes; algorithms aren't interchangeable
================================================================================

We established that a single RSA keypair can sign with both RS256 and PS256.
But the **verifier must whitelist the correct algorithm**. A token signed with
PS256 will NOT verify if you tell PyJWT to expect only RS256 — even though the
exact same key pair is involved — because the padding differs.

This protects you: the `algorithms=[...]` allow-list on `jwt.decode()` is a
security control. Never set it to a permissive catch-all.

This script proves:
    1. RS256 token verifies as RS256.            ✔
    2. PS256 token verifies as PS256.            ✔
    3. PS256 token FAILS to verify as RS256.     ✘ (caught & explained)
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa


def main() -> None:
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "erin"}

    rs_token = jwt.encode(payload, private_pem, algorithm="RS256")
    ps_token = jwt.encode(payload, private_pem, algorithm="PS256")

    print("1) RS256 token verified as RS256:")
    print("   ", jwt.decode(rs_token, public_pem, algorithms=["RS256"]))

    print("\n2) PS256 token verified as PS256:")
    print("   ", jwt.decode(ps_token, public_pem, algorithms=["PS256"]))

    print("\n3) PS256 token verified as RS256 (EXPECTED TO FAIL):")
    try:
        jwt.decode(ps_token, public_pem, algorithms=["RS256"])
        print("   !! Unexpected success.")
    except jwt.InvalidAlgorithmError as exc:
        print("   Caught InvalidAlgorithmError:", exc)
        print("   The token's alg (PS256) is not in the allow-list ['RS256'].")
    except jwt.InvalidSignatureError as exc:
        print("   Caught InvalidSignatureError:", exc)

    print("\nThe decode-time algorithms allow-list is a real security boundary.")


if __name__ == "__main__":
    main()
