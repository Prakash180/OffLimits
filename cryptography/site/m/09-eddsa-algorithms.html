Module 09 · EdDSA Algorithms (Ed25519 / Ed448)

🧠 Mental Model — Behind the Scenes

EdDSA is built on twisted Edwards curves — a reformulation of elliptic curves whose addition formula is complete (it works for every pair of points with no awkward special cases). That mathematical tidiness is what makes EdDSA so hard to misuse: there are far fewer edge cases where an implementation can leak secrets. The two flavours are Ed25519 (Curve25519, ~128-bit security, a tiny 32-byte public key, 64-byte signature) and Ed448 (Curve448, ~224-bit security, 57-byte key, 114-byte signature). Both are fast because they avoid the big-integer modular inversions that slow RSA and classic ECDSA.

The defining trick is deterministic nonces. Recall ECDSA's fatal dependence on a fresh random k per signature (Module 07) — reuse it and your private key spills out. EdDSA eliminates that risk entirely: instead of drawing k from a random number generator, it derives k by hashing the private key together with the message. No RNG is consulted at signing time. Sign the same message twice and you get the byte-for-byte identical signature — and crucially, two different messages can never accidentally collide on the same nonce. An entire category of catastrophic real-world failures (the Sony PS3 break, various wallet key leaks) simply cannot happen.

In the JWT world there's one quirk to internalize: both flavours share a single alg value, "EdDSA". There is no "Ed25519" or "Ed448" algorithm string in the JOSE header. You always pass algorithm="EdDSA" to jwt.encode, and the key object itself — whether it's an Ed25519PrivateKey or an Ed448PrivateKey — silently determines which curve is used. The curve is a property of the key, not the header.

flowchart LR A["jwt.encode(payload, key, algorithm='EdDSA')"] --> B{Key type?} B -->|Ed25519PrivateKey| C[Ed25519 signature, 64 bytes] B -->|Ed448PrivateKey| D[Ed448 signature, 114 bytes] C --> E["Header alg = 'EdDSA' either way"] D --> E

🔍 A concrete analogy

Think of a tamper-evident notary stamp whose ink is mixed from the document's own text. Because the ink recipe is computed deterministically from what's being stamped, the same document always produces the same imprint — and there's no separate ink bottle (random nonce) that could be refilled wrong, run dry, or get reused on the next document. One predictable, self-contained process, every time.

⚙️ What actually happens when you run the code

  1. Ed25519PrivateKey.generate() produces a compact 32-byte secret scalar and its 32-byte public point.
  2. The keys serialize to PEM (PKCS#8 / SubjectPublicKeyInfo) so PyJWT can take the bytes directly.
  3. jwt.encode(payload, private_pem, algorithm="EdDSA") hashes the private key + message to derive the nonce deterministically — no RNG involved.
  4. It computes the signature and stamps {"alg": "EdDSA", "typ": "JWT"} into the header — note the curve is not recorded there.
  5. Signing the identical payload again derives the same nonce, yielding an identical token, byte-for-byte.
  6. jwt.decode(token, public_pem, algorithms=["EdDSA"]) verifies against the public point and returns the claims.

👀 What to notice when you run the examples

  • In 03_eddsa_is_deterministic.py, two signings print "Tokens identical? True" — the opposite of Module 08's PSS, and no RNG was touched.
  • In 01_ed25519_sign_verify.py, the JOSE header reads "alg": "EdDSA" — never "Ed25519", even though the key is Ed25519.
  • In 04_eddsa_key_sizes.py, the raw Ed25519 public key is just 32 bytes — a fraction of RSA-2048's 256-byte modulus.
  • In 05_eddsa_vs_ecdsa.py, EdDSA and ECDSA sit side by side: EdDSA needs no sign-time randomness, ECDSA does.

⚠️ Common misconceptions

  • "The alg should be Ed25519." It's always "EdDSA"; passing algorithm="Ed25519" fails. The key picks the curve.
  • "Deterministic signatures are insecure." The opposite — determinism removes ECDSA's nonce-reuse vulnerability entirely.
  • "Identical tokens for identical input is a bug." It's correct, intended behaviour — don't try to "fix" it.
  • "You still need algorithms=[...] only for RSA/ECDSA." Pin algorithms=["EdDSA"] at decode time too — the whitelist matters for every scheme.

🟣 Module 09 · EdDSA Algorithms (Ed25519 / Ed448)

The modern default. Tiny keys, blazing speed, deterministic by design, and hard to misuse. If you're choosing a signature scheme for a new system in 2025+, this is usually the right answer.

🧠 What is EdDSA?

EdDSA (Edwards-curve Digital Signature Algorithm) is an elliptic-curve scheme built on twisted Edwards curves. It comes in two flavours:

Flavour Curve Security Public key Signature
Ed25519 Curve25519 ~128-bit 32 bytes 64 bytes
Ed448 Curve448 ~224-bit 57 bytes 114 bytes

⚠️ One algorithm string for both: "EdDSA"

This is the EdDSA gotcha. In JWT, both Ed25519 and Ed448 use the same JOSE header value:

{ "alg": "EdDSA", "typ": "JWT" }

There is no "Ed25519" or "Ed448" alg value. The key type itself (the curve baked into the key object) determines which curve is used. You always pass algorithm="EdDSA" to jwt.encode().

flowchart LR A["jwt.encode(payload, key, algorithm='EdDSA')"] --> B{Key type?} B -->|Ed25519 key| C[Ed25519 signature] B -->|Ed448 key| D[Ed448 signature] C --> E["Header alg = 'EdDSA' either way"] D --> E

✨ Why EdDSA wins

  • Deterministic. No random nonce at signing time — signing the same message twice gives the identical signature. This kills an entire class of ECDSA disasters where a bad/repeated nonce leaks the private key (e.g. the Sony PS3 break).
  • Fast. No big-integer math, no modular inversion — among the fastest schemes to both sign and verify.
  • Tiny. A 32-byte Ed25519 public key vs a 256-byte RSA-2048 modulus.
  • Misuse-resistant. The curve and parameters are fixed; far fewer footguns.

RNG at sign time Required Not needed
Misuse risk Bad nonce → key leak Resistant by design

JWT alg value ES256/ES384/ES512/ES256K EdDSA (both)

⚠️ Pitfalls

  • Don't look for an "Ed25519" alg. The header always says "EdDSA"; the curve is implied by the key. Passing algorithm="Ed25519" will fail.
  • Pin algorithms=["EdDSA"] at decode time like every other scheme.
  • Ed448 ≠ Ed25519 keys. A token signed with an Ed25519 key must be verified with the matching Ed25519 public key (and vice versa for Ed448).
  • Determinism is intended. Identical tokens for identical input is correct behaviour, not a bug — don't "fix" it.

🔑 Key takeaways

  • EdDSA = deterministic, fast, tiny-keyed, misuse-resistant signatures.
  • One alg string, "EdDSA", covers both Ed25519 and Ed448; the key picks the curve.
  • It removes ECDSA's dangerous dependence on a per-signature secure RNG.
  • For most new services, EdDSA (Ed25519) is the recommended default.

"""
09 · EdDSA · 01 — Ed25519 sign & verify
=======================================

**EdDSA** (Edwards-curve Digital Signature Algorithm) is the newest signature
family in the JWT world and, for most new systems, the best default. It comes
in two flavours defined by their curve:

    Ed25519  — built on Curve25519,  ~128-bit security, 32-byte keys
    Ed448    — built on Curve448,    ~224-bit security, 57-byte keys

⚠️  In JWT, BOTH flavours use the SAME algorithm string: **"EdDSA"**.
There is no "Ed25519" alg value in the JOSE header — the header just says
`"alg": "EdDSA"`, and the *key type* (the curve baked into the key) determines
whether Ed25519 or Ed448 is actually used.

This script generates an Ed25519 keypair and does a round-trip.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey


def main() -> None:
    # Ed25519 keys take no parameters — the curve is fixed by definition.
    private_key = Ed25519PrivateKey.generate()
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "alice", "curve": "Ed25519"}

    # Sign with algorithm="EdDSA" — note the header alg will be "EdDSA".
    token = jwt.encode(payload, private_pem, algorithm="EdDSA")
    print("=" * 70)
    print("EdDSA / Ed25519 token:")
    print(token)
    print("=" * 70)

    header = jwt.get_unverified_header(token)
    print("\nJOSE header:", header, " <- note alg is 'EdDSA', not 'Ed25519'")

    decoded = jwt.decode(token, public_pem, algorithms=["EdDSA"])
    print("Verified payload:", decoded)


if __name__ == "__main__":
    main()

03 EdDSA Is Deterministic03_eddsa_is_deterministic.py ▾

A defining property of EdDSA: signing is deterministic. The per-signature "nonce" is derived deterministically from the private key and the message (via a hash), so there is no reliance on an external random number generator at signing time.

Consequences: - Signing the SAME payload twice with the SAME Ed25519 key produces the EXACT SAME token, byte-for-byte. - This sidesteps a whole class of catastrophic ECDSA failures, where a bad/repeated random nonce can leak the private key (famously, the 2010 Sony PS3 ECDSA break).

Contrast: - ECDSA (ES256 etc.) -> needs a fresh secure random nonce per signature. - RSASSA-PSS (PS256) -> randomised (random salt) -> tokens differ. - EdDSA -> deterministic -> tokens identical.

We sign the same payload twice with Ed25519 and show the tokens match.

"""
09 · EdDSA · 03 — EdDSA is DETERMINISTIC
========================================

A defining property of EdDSA: signing is **deterministic**. The per-signature
"nonce" is derived deterministically from the private key and the message
(via a hash), so there is *no* reliance on an external random number generator
at signing time.

Consequences:
    - Signing the SAME payload twice with the SAME Ed25519 key produces the
      EXACT SAME token, byte-for-byte.
    - This sidesteps a whole class of catastrophic ECDSA failures, where a
      bad/repeated random nonce can leak the private key (famously, the 2010
      Sony PS3 ECDSA break).

Contrast:
    - ECDSA (ES256 etc.)  -> needs a fresh secure random nonce per signature.
    - RSASSA-PSS (PS256)  -> randomised (random salt) -> tokens differ.
    - EdDSA               -> deterministic -> tokens identical.

We sign the same payload twice with Ed25519 and show the tokens match.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey


def main() -> None:
    private_key = Ed25519PrivateKey.generate()
    private_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    public_pem = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    payload = {"sub": "carol", "msg": "sign me twice"}

    token_a = jwt.encode(payload, private_pem, algorithm="EdDSA")
    token_b = jwt.encode(payload, private_pem, algorithm="EdDSA")

    print("=" * 70)
    print("Ed25519 — sign identical payload twice")
    print("=" * 70)
    print("token A:", token_a)
    print("token B:", token_b)
    print("\nTokens identical? ", token_a == token_b, " <- expect True (deterministic)")

    # Both verify, of course.
    jwt.decode(token_a, public_pem, algorithms=["EdDSA"])
    jwt.decode(token_b, public_pem, algorithms=["EdDSA"])
    print("Both verify correctly. ✔")

    print("\nDeterminism removes the 'must have good RNG at sign time' footgun")
    print("that plagues classic ECDSA.")


if __name__ == "__main__":
    main()

"""
09 · EdDSA · 04 — EdDSA key sizes: tiny and fast
================================================

EdDSA keys are astonishingly small. An Ed25519 **public key is just 32 raw
bytes** — the actual point on Curve25519. Compare that with a 2048-bit RSA
public key (256-byte modulus) or even a P-256 EC key.

This script prints:
    - the raw (Encoding.Raw) Ed25519 public key and its length (32 bytes)
    - the PEM-wrapped Ed25519 public key (slightly larger due to ASN.1 framing)
    - a side-by-side size comparison against EC P-256 and RSA-2048 PEMs

Small keys + deterministic signing + no big-integer math = EdDSA is also one of
the **fastest** signature schemes, which is why it's popular for high-volume
token issuance and constrained devices.
"""

from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec, rsa
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey


def main() -> None:
    ed_key = Ed25519PrivateKey.generate()
    ed_pub = ed_key.public_key()

    # RAW encoding gives the bare 32-byte public key point.
    ed_pub_raw = ed_pub.public_bytes(
        encoding=serialization.Encoding.Raw,
        format=serialization.PublicFormat.Raw,
    )
    ed_pub_pem = ed_pub.public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )

    print("=" * 70)
    print("Ed25519 PUBLIC KEY")
    print("=" * 70)
    print("Raw bytes length:", len(ed_pub_raw), "bytes  (the bare curve point)")
    print("Raw bytes (hex) :", ed_pub_raw.hex())
    print("\nPEM form:")
    print(ed_pub_pem.decode())

    # --- size comparison against EC P-256 and RSA-2048 (PEM public keys) ---
    ec_pub_pem = (
        ec.generate_private_key(ec.SECP256R1())
        .public_key()
        .public_bytes(
            serialization.Encoding.PEM,
            serialization.PublicFormat.SubjectPublicKeyInfo,
        )
    )
    rsa_pub_pem = (
        rsa.generate_private_key(public_exponent=65537, key_size=2048)
        .public_key()
        .public_bytes(
            serialization.Encoding.PEM,
            serialization.PublicFormat.SubjectPublicKeyInfo,
        )
    )

    print("=" * 70)
    print("PUBLIC-KEY PEM SIZE COMPARISON")
    print("=" * 70)
    print(f"  Ed25519  : {len(ed_pub_pem):>5} bytes  (raw key only 32 bytes!)")
    print(f"  EC P-256 : {len(ec_pub_pem):>5} bytes")
    print(f"  RSA-2048 : {len(rsa_pub_pem):>5} bytes")

    print("\nEdDSA: smallest keys, fastest signing, hard to misuse.")


if __name__ == "__main__":
    main()

EdDSA and ECDSA are both elliptic-curve signature schemes, but they differ in ways that matter for real systems:

"""
09 · EdDSA · 05 — EdDSA vs ECDSA, head to head
==============================================

EdDSA and ECDSA are both elliptic-curve signature schemes, but they differ in
ways that matter for real systems:

  ┌────────────────────┬───────────────────────────┬──────────────────────────┐
  │                    │ ECDSA (ES256, ES384, …)    │ EdDSA (Ed25519/Ed448)    │
  ├────────────────────┼───────────────────────────┼──────────────────────────┤
  │ Randomness at sign │ REQUIRES secure RNG nonce  │ Deterministic (no RNG)   │
  │ Misuse risk        │ Bad nonce -> key leak      │ Resistant by design      │
  │ Curve choice       │ alg fixes the curve        │ curve fixed by key type  │
  │ JWT alg string     │ ES256 / ES384 / ES512 / …  │ "EdDSA" (both flavours)  │
  │ Speed              │ Fast                       │ Typically faster         │
  │ Determinism        │ No (randomised)            │ Yes                      │
  └────────────────────┴───────────────────────────┴──────────────────────────┘

The big practical win for EdDSA: removing the random-nonce requirement
eliminates an entire category of devastating implementation bugs.

This script signs & verifies a token with BOTH schemes so you can see them
working back to back.
"""

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey


def pem_pair_from(private_key) -> tuple[bytes, bytes]:
    priv = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption(),
    )
    pub = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )
    return priv, pub


def main() -> None:
    payload = {"sub": "dave"}

    # --- ECDSA (ES256 on P-256) ---
    es_priv, es_pub = pem_pair_from(ec.generate_private_key(ec.SECP256R1()))
    es_token = jwt.encode(payload, es_priv, algorithm="ES256")
    es_decoded = jwt.decode(es_token, es_pub, algorithms=["ES256"])

    print("ECDSA  (ES256, needs secure RNG per signature):")
    print("  header :", jwt.get_unverified_header(es_token))
    print("  token  :", es_token)
    print("  verify :", es_decoded)

    # --- EdDSA (Ed25519) ---
    ed_priv, ed_pub = pem_pair_from(Ed25519PrivateKey.generate())
    ed_token = jwt.encode(payload, ed_priv, algorithm="EdDSA")
    ed_decoded = jwt.decode(ed_token, ed_pub, algorithms=["EdDSA"])

    print("\nEdDSA  (Ed25519, deterministic, misuse-resistant):")
    print("  header :", jwt.get_unverified_header(ed_token))
    print("  token  :", ed_token)
    print("  verify :", ed_decoded)

    print("\nBoth are elliptic-curve schemes; EdDSA removes the RNG footgun and")
    print("uses one alg string ('EdDSA') regardless of curve.")


if __name__ == "__main__":
    main()
