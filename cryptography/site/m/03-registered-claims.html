Module 03 · Registered Claims

🧠 Mental Model — Behind the Scenes

The registered claims (iss, sub, aud, exp, nbf, iat, jti) are just seven short keys in the same plain JSON payload you met in Module 01 — nothing magical lives in them. What makes them special is a shared agreement: RFC 7519 reserves these three-letter names so every issuer and verifier on Earth interprets them the same way. PyJWT's job is to turn that social contract into automatic checks.

The most important mental split is time claims vs. identity claims. The time claims (exp, nbf, and a future-dated iat) are checked automatically the moment they're present — PyJWT compares them against the current UTC clock with no arguments from you. The identity claims (iss, aud, sub) are opt-in: PyJWT ignores iss entirely unless you pass issuer=, ignores aud unless you pass audience=, and ignores sub unless you pass subject=. A token "valid for service A" sails through service B unless B explicitly verifies aud. This asymmetry is the single biggest source of real-world JWT bugs.

Under the hood, time claims are stored as NumericDate — plain integer seconds since the Unix epoch, not ISO strings. When you hand PyJWT a timezone-aware datetime, it calls .timestamp() to flatten it to that integer. On decode, PyJWT compares now >= exp (reject) and now < nbf (reject). This is why naive datetime.now() is dangerous: without a timezone the epoch conversion is ambiguous and can drift by hours. Always use datetime.now(timezone.utc).

aud has its own quirk worth picturing: matching is a set intersection. The token's aud may be a single string or a list, and your audience= may also be one or many. The token passes if the two sets overlap by any value. And jti? PyJWT will store and return it, but it does nothing automatically — replay protection is your application's job, typically a denylist keyed by the jti UUID.

🔍 A concrete analogy

Think of a JWT as a boarding pass. The exp is the gate-closing time — the scanner rejects you automatically once it passes, no human judgment needed. The aud is the destination printed on the pass — but the gate agent only checks it if they care about destination; otherwise a London pass might scan fine at the Paris gate. The jti is the unique ticket number: it prevents the same pass being used twice only if someone keeps a list of used numbers.

⚙️ What actually happens when you run the code

  1. You build a payload mixing identity claims (iss, sub, aud) and time claims (exp, nbf, iat), passing datetime objects for the times.
  2. jwt.encode() converts each datetime to NumericDate (integer epoch seconds) and signs the result.
  3. On jwt.decode(), PyJWT first verifies the signature, then automatically checks exp (reject if now >= exp) and nbf (reject if now < nbf).
  4. PyJWT checks iss/aud/sub only because you passed issuer=, audience=, subject=; a mismatch raises InvalidIssuerError / InvalidAudienceError / InvalidSubjectError.
  5. For aud, PyJWT intersects the token's audience(s) with your accepted audience(s) and passes on any overlap.
  6. jti is returned in the claims dict; the script's own in-memory denylist decides whether the token was already used.

👀 What to notice when you run the examples

  • In 05_exp_expiration.py, an already-past exp raises ExpiredSignatureError with no extra options — time enforcement is automatic.
  • In 06_nbf_not_before.py, a future nbf raises ImmatureSignatureError — the token is valid, just "not yet."
  • In 01_iss_issuer.py/03_aud_audience.py, omitting issuer=/audience= silently skips the check — the "aha" that identity claims are opt-in.
  • In 04_aud_multiple.py, a list aud passes when any member matches — set-intersection in action.
  • In 08_jti_jwt_id.py, the first use of a jti succeeds and the second is rejected only because the script tracks it — PyJWT didn't do that for you.
  • In 10_datetime_handling.py, a datetime and a raw int epoch produce equivalent claims — proof of the NumericDate conversion.

⚠️ Common misconceptions

  • ❌ "If a token has an aud, PyJWT checks it." False — only if you pass audience=; otherwise aud is ignored.
  • ❌ "jti gives me replay protection for free." False — PyJWT stores it; you must keep the denylist.
  • ❌ "iat is just informational and never blocks." Mostly true, but in PyJWT 2.13 a future iat raises ImmatureSignatureError (disable with options={"verify_iat": False}).
  • ❌ "Naive datetime.now() is fine for exp." False — without a timezone the epoch conversion is ambiguous; use datetime.now(timezone.utc).

🪪 Module 03 · Registered Claims

The JWT spec (RFC 7519 §4.1) reserves a handful of short, three-letter claim names with agreed-upon meanings. They are registered with IANA. This module walks through all seven and shows exactly how PyJWT 2.13 validates each one.

🧠 The big idea

A JWT payload is just JSON — you could put anything in it. The registered claims are the seven names everyone agrees on, so that issuers and verifiers speak the same language about who, for whom, and when.

Claim Name Meaning Validated by PyJWT?
iss Issuer Who created the token Only if you pass issuer=
sub Subject Who the token is about Only if you pass subject=
aud Audience Who the token is for Only if you pass audience=
exp Expiration Reject at/after this time ✅ Automatic when present
nbf Not Before Reject before this time ✅ Automatic when present
iat Issued At When it was created Future iat rejected (verify_iat)
jti JWT ID Unique token identifier ❌ Your app must track it

🔑 Key distinction: the time claims (exp, nbf) are checked automatically. The identity claims (iss, sub, aud) are opt-in — you must tell PyJWT what value to expect, or it won't look at them at all.

🌊 How PyJWT validates a token

flowchart TD A[jwt.decode called] --> B{Signature valid?} B -- no --> X[InvalidSignatureError] B -- yes --> C{exp present?} C -- yes & past --> X2[ExpiredSignatureError] C -- ok --> D{nbf present?} D -- yes & future --> X3[ImmatureSignatureError] D -- ok --> E{issuer= passed?} E -- yes & mismatch --> X4[InvalidIssuerError] E -- ok --> F{audience= passed?} F -- yes & no overlap --> X5[InvalidAudienceError] F -- ok --> G{subject= passed?} G -- yes & mismatch --> X6[InvalidSubjectError] G -- ok --> Z[Return decoded payload]

✅ Key takeaways

  • Time claims are automatic. If exp/nbf are present, PyJWT enforces them with no extra arguments.
  • Identity claims are opt-in. Without issuer=, audience=, or subject=, PyJWT will happily ignore iss, aud, and sub.
  • aud matching is set intersection. A token valid for many audiences passes if any accepted value is present.
  • datetime objects are first-class. Pass timezone-aware datetimes; PyJWT converts them to epoch seconds (NumericDate).
  • jti is yours to police. PyJWT stores it; replay protection is your job.

⚠️ Pitfalls

  • 🕳️ Forgetting audience=. A token minted for service A will pass at service B unless B verifies aud. Always check it.
  • 🕳️ Naive datetimes. datetime.now() (no tz) is ambiguous. Use datetime.now(timezone.utc).
  • 🕳️ Misjudging iat. In PyJWT 2.13 a future iat raises ImmatureSignatureError (disable via options={"verify_iat": False}). It is still informational for age checks — enforce those yourself.
  • 🕳️ Treating jti as automatic replay protection. Without a denylist it does nothing.
  • 🕳️ exp too far out. Long-lived tokens are a security risk; prefer short lifetimes plus refresh.

01 ISS Issuer01_iss_issuer.py ▾

01 · The iss (issuer) registered claim.

The iss claim identifies who issued the token. It is a free-form string — typically a URL or a stable identifier for your auth server (e.g. "https://auth.example.com").

PyJWT does not validate iss automatically. You opt in by passing issuer="..." to :func:jwt.decode. When you do, PyJWT compares the token's iss against the expected value and raises :class:jwt.InvalidIssuerError on a mismatch.

"""01 · The `iss` (issuer) registered claim.

The `iss` claim identifies *who* issued the token. It is a free-form string —
typically a URL or a stable identifier for your auth server (e.g.
``"https://auth.example.com"``).

PyJWT does not validate `iss` automatically. You opt in by passing

:class:`jwt.InvalidIssuerError` on a mismatch.

Run me:
    .venv/bin/python pyjwt-course/03-registered-claims/01_iss_issuer.py
"""

import jwt

SECRET = "super-secret-shared-key-please-change-me"
EXPECTED_ISSUER = "https://auth.example.com"


def main() -> None:
    # --- Encode a token that declares its issuer -------------------------
    token = jwt.encode(
        {"iss": EXPECTED_ISSUER, "sub": "user-123"},
        SECRET,
        algorithm="HS256",
    )
    print("Encoded token:", token)

    # --- Happy path: decode with the matching expected issuer ------------
    decoded = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],
        issuer=EXPECTED_ISSUER,  # opt in to issuer validation
    )
    print("\n[OK] Issuer matched. Decoded payload:")
    print("    ", decoded)

    # --- Failure path: expect a *different* issuer -----------------------
    # PyJWT compares token['iss'] to the value we pass; a mismatch raises.
    try:
        jwt.decode(
            token,
            SECRET,
            algorithms=["HS256"],
            issuer="https://evil.example.com",
        )
    except jwt.InvalidIssuerError as exc:
        print("\n[EXPECTED FAILURE] InvalidIssuerError raised:")
        print("    ", exc)
        print("    The token's `iss` did not match the expected issuer.")


if __name__ == "__main__":
    main()

"""02 · The `sub` (subject) registered claim.

The `sub` claim identifies the *principal* the token is about — usually the
user ID. It should be unique and stable within the issuer's namespace.

Since PyJWT 2.x you can validate it by passing ``subject="..."`` to

Run me:
    .venv/bin/python pyjwt-course/03-registered-claims/02_sub_subject.py
"""

import jwt

SECRET = "super-secret-shared-key-please-change-me"
EXPECTED_SUBJECT = "user-123"


def main() -> None:
    token = jwt.encode(
        {"sub": EXPECTED_SUBJECT, "iss": "https://auth.example.com"},
        SECRET,
        algorithm="HS256",
    )
    print("Encoded token:", token)

    # --- Happy path: subject matches -------------------------------------
    decoded = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],
        subject=EXPECTED_SUBJECT,  # opt in to subject validation
    )
    print("\n[OK] Subject matched. Decoded payload:")
    print("    ", decoded)

    # --- Failure path: wrong expected subject ----------------------------
    try:
        jwt.decode(
            token,
            SECRET,
            algorithms=["HS256"],
            subject="user-999",
        )
    except jwt.exceptions.InvalidSubjectError as exc:
        print("\n[EXPECTED FAILURE] InvalidSubjectError raised:")
        print("    ", exc)

    # --- Failure path: token has no `sub` but we REQUIRE one -------------
    # Important: passing `subject=` alone validates the VALUE when `sub` is
    # present, but it does NOT force the claim to exist. To demand presence,
    # combine it with options={"require": [...]}.
    no_sub = jwt.encode({"iss": "https://auth.example.com"}, SECRET, algorithm="HS256")
    try:
        jwt.decode(
            no_sub,
            SECRET,
            algorithms=["HS256"],
            subject=EXPECTED_SUBJECT,
            options={"require": ["sub"]},
        )
    except jwt.MissingRequiredClaimError as exc:
        print("\n[EXPECTED FAILURE] MissingRequiredClaimError raised:")
        print("    ", exc)
        print("    `subject=` checks the value; `require` guarantees presence.")


if __name__ == "__main__":

    decoded = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],

    try:

            SECRET,
            algorithms=["HS256"],
            audience=["https://nope.example.com"],

    except jwt.InvalidAudienceError as exc:

"""05 · The `exp` (expiration time) registered claim.

`exp` is a NumericDate (seconds since the Unix epoch) after which the token

import jwt

def main() -> None:

    fresh = jwt.encode(
        {"sub": "user-123", "exp": now + timedelta(hours=1)},

    stale = jwt.encode(
        {"sub": "user-123", "exp": now - timedelta(hours=1)},
        SECRET,
        algorithm="HS256",
    )
    try:
        jwt.decode(stale, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError as exc:
        print("\n[EXPECTED FAILURE] ExpiredSignatureError raised:")
        print("    ", exc)
        print("    `exp` is checked automatically; no decode parameter required.")

07 · The iat (issued at) registered claim.

iat records when the token was created (a NumericDate). It is primarily informational — you can use it to compute a token's age or to reject very old tokens with your own logic.

Behaviour notes for PyJWT 2.13: * iat is decoded and made available in the payload. * PyJWT treats iat like a "not before" hint: an iat in the FUTURE makes the token immature and raises ImmatureSignatureError. * You can switch that check off with options={"verify_iat": False} and/or enforce your own freshness policy by comparing iat to "now".

"""07 · The `iat` (issued at) registered claim.

`iat` records *when* the token was created (a NumericDate). It is primarily
**informational** — you can use it to compute a token's age or to reject very
old tokens with your own logic.

Behaviour notes for PyJWT 2.13:
  * `iat` is decoded and made available in the payload.
  * PyJWT treats `iat` like a "not before" hint: an `iat` in the FUTURE makes
    the token immature and raises `ImmatureSignatureError`.
  * You can switch that check off with ``options={"verify_iat": False}`` and/or
    enforce your own freshness policy by comparing `iat` to "now".

Run me:
    .venv/bin/python pyjwt-course/03-registered-claims/07_iat_issued_at.py
"""

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"


def main() -> None:
    now = datetime.now(UTC)

    # --- Normal: iat = now -----------------------------------------------
    token = jwt.encode({"sub": "user-123", "iat": now}, SECRET, algorithm="HS256")
    decoded = jwt.decode(token, SECRET, algorithms=["HS256"])
    issued = datetime.fromtimestamp(decoded["iat"], tz=UTC)
    print("[OK] Decoded `iat`:", decoded["iat"], "->", issued.isoformat())

    # --- iat far in the FUTURE: PyJWT rejects it as immature -------------
    future = jwt.encode(
        {"sub": "user-123", "iat": now + timedelta(days=365)},
        SECRET,
        algorithm="HS256",
    )
    try:
        jwt.decode(future, SECRET, algorithms=["HS256"])
    except jwt.ImmatureSignatureError as exc:
        print("\n[EXPECTED FAILURE] A future `iat` is treated as not-yet-valid:")
        print("    ", exc)

    # --- Read it anyway by disabling just the iat check ------------------
    decoded_future = jwt.decode(
        future,
        SECRET,
        algorithms=["HS256"],
        options={"verify_iat": False},
    )
    print("\n[verify_iat=False] Decoded the future-iat token:")
    print("     iat:", decoded_future["iat"])

    # --- Enforce your own freshness policy on top ------------------------
    # Example: flag anything claiming to be issued more than 1 day ahead.
    age = decoded_future["iat"] - now.timestamp()
    if age > timedelta(days=1).total_seconds():
        print("\n[CUSTOM POLICY] `iat` is implausibly far in the future")
        print(f"    (about {age / 86400:.0f} days ahead of now).")


if __name__ == "__main__":
    main()

08 · The jti (JWT ID) registered claim.

jti is a unique identifier for the token. Its purpose is to give each token an identity you can track — most importantly to prevent replay by keeping a denylist (or, for one-time tokens, an allowlist that is consumed on first use).

PyJWT does NOT track jti for you; uniqueness/replay logic lives in your app. Below we simulate an in-memory denylist of already-used token IDs.

"""08 · The `jti` (JWT ID) registered claim.

`jti` is a unique identifier for the token. Its purpose is to give each token
an identity you can track — most importantly to **prevent replay** by keeping a
denylist (or, for one-time tokens, an allowlist that is consumed on first use).

PyJWT does NOT track `jti` for you; uniqueness/replay logic lives in your app.
Below we simulate an in-memory denylist of already-used token IDs.

Run me:
    .venv/bin/python pyjwt-course/03-registered-claims/08_jti_jwt_id.py
"""

import uuid

import jwt

SECRET = "super-secret-shared-key-please-change-me"

# A real system would use Redis / a database with TTLs. An in-memory set is
# enough to demonstrate the idea.
USED_TOKEN_IDS: set[str] = set()


def consume(token: str) -> None:
    """Decode a token and reject it if its `jti` has already been seen."""
    payload = jwt.decode(token, SECRET, algorithms=["HS256"])
    jti = payload["jti"]
    if jti in USED_TOKEN_IDS:
        print(f"    [DENIED] jti={jti} was already used -> possible replay!")
        return
    USED_TOKEN_IDS.add(jti)
    print(f"    [ACCEPTED] jti={jti} consumed for the first time.")


def main() -> None:
    # Each token gets a fresh, collision-resistant id from uuid4().
    token = jwt.encode(
        {"sub": "user-123", "jti": str(uuid.uuid4())},
        SECRET,
        algorithm="HS256",
    )
    print("Issued a token with a unique `jti`.\n")

    print("First presentation of the token:")
    consume(token)

    print("\nSecond presentation of the SAME token (replay attempt):")
    consume(token)

    print("\nA brand-new token has a different `jti`, so it is accepted:")
    consume(jwt.encode({"sub": "user-123", "jti": str(uuid.uuid4())}, SECRET, algorithm="HS256"))


if __name__ == "__main__":
    main()

"""09 · All seven registered claims, together.

import uuid
from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"
ISSUER = "https://auth.example.com"
SUBJECT = "user-123"
AUDIENCE = "https://api.example.com"


def main() -> None:
    now = datetime.now(UTC)

    payload = {
        "iss": ISSUER,
        "sub": SUBJECT,
        "aud": AUDIENCE,
        "iat": now,
        "nbf": now - timedelta(seconds=5),       # already active
        "exp": now + timedelta(minutes=15),      # valid for 15 minutes
        "jti": str(uuid.uuid4()),
    }

    decoded = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],
        issuer=ISSUER,
        audience=AUDIENCE,
        subject=SUBJECT,
    )

    print("[OK] Fully validated. Claims:")
    for name in ("iss", "sub", "aud", "iat", "nbf", "exp", "jti"):

10 Datetime Handling10_datetime_handling.py ▾

10 · How PyJWT handles datetimes for the time-based claims.

The time claims (exp, nbf, iat) are defined by RFC 7519 as NumericDate values: the number of seconds since 1970-01-01T00:00:00Z (the Unix epoch), ignoring leap seconds.

You almost never compute that number by hand. PyJWT accepts a :class:datetime.datetime object directly and converts it to epoch seconds for you. A plain int epoch works too. This script proves all three are equivalent.

Always use timezone-AWARE datetimes (datetime.now(timezone.utc)); a naive datetime is interpreted as UTC by PyJWT but is ambiguous in your own code.

"""10 · How PyJWT handles datetimes for the time-based claims.

The time claims (`exp`, `nbf`, `iat`) are defined by RFC 7519 as **NumericDate**
values: the number of seconds since 1970-01-01T00:00:00Z (the Unix epoch),
ignoring leap seconds.

You almost never compute that number by hand. PyJWT accepts a
:class:`datetime.datetime` object directly and converts it to epoch seconds for
you. A plain ``int`` epoch works too. This script proves all three are
equivalent.

Always use timezone-AWARE datetimes (``datetime.now(timezone.utc)``); a naive
datetime is interpreted as UTC by PyJWT but is ambiguous in your own code.

Run me:
    .venv/bin/python pyjwt-course/03-registered-claims/10_datetime_handling.py
"""

from datetime import UTC, datetime, timedelta

import jwt

SECRET = "super-secret-shared-key-please-change-me"


def main() -> None:
    now = datetime.now(UTC)
    exp_dt = now + timedelta(hours=1)

    # --- (a) pass a datetime object --------------------------------------
    token_dt = jwt.encode({"sub": "u", "exp": exp_dt}, SECRET, algorithm="HS256")
    decoded_dt = jwt.decode(token_dt, SECRET, algorithms=["HS256"])
    print("(a) datetime input -> stored as epoch int:", decoded_dt["exp"])
    print("    type in decoded payload:", type(decoded_dt["exp"]).__name__)

    # --- (b) pass the equivalent int epoch directly ----------------------
    exp_epoch = int(exp_dt.timestamp())
    token_int = jwt.encode({"sub": "u", "exp": exp_epoch}, SECRET, algorithm="HS256")
    decoded_int = jwt.decode(token_int, SECRET, algorithms=["HS256"])
    print("\n(b) int epoch input -> stored unchanged:", decoded_int["exp"])

    # --- They describe the same instant ----------------------------------
    print("\nBoth represent the same expiry second:", decoded_dt["exp"] == decoded_int["exp"])

    # --- Round-trip back to a human-readable datetime --------------------
    restored = datetime.fromtimestamp(decoded_dt["exp"], tz=UTC)
    print("Restored expiry:", restored.isoformat())

    # --- All three time claims accept datetimes simultaneously ----------
    full = jwt.encode(
        {
            "iat": now,
            "nbf": now,
            "exp": now + timedelta(minutes=5),
        },
        SECRET,
        algorithm="HS256",
    )
    decoded_full = jwt.decode(full, SECRET, algorithms=["HS256"])
    print("\nAll time claims as ints:", {k: decoded_full[k] for k in ("iat", "nbf", "exp")})


if __name__ == "__main__":
    main()
